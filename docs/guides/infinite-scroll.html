Infinite scroll

Shoji has no dedicated infinite-scroll plugin, and isn't going to grow one — its actual footprint in a scrolling gallery is small: one method (updateSlides()), one lookup convention for opening the right slide (data-shoji-id), and a plugin choice. Everything else — the sentinel/scroll-position logic that decides when to fetch more, how the on-page grid renders or virtualizes its tiles, any scroll-anchoring math — is plain host code Shoji never sees or participates in. The Infinite scroll example has that code in full; this guide is about the handful of places Shoji itself is actually touched.

updateSlides(): the only thing Shoji needs to know

Every time the host's own list of loaded items changes — a new page appended, an older page prepended, or nothing at all if a scroll tick only changed which tiles are currently rendered — call gallery.updateSlides(items) with the full, current, correctly-ordered array. That's the entire contract. Shoji diffs the new array against what it already knew by id (see the Methods guide), so it doesn't matter whether items were added at the start, the end, or both — there's no separate "append" vs. "prepend" API to call.

One real bug this surfaces if missed: the bidirectional example keeps its loaded items in a Map, and Map iteration order is insertion order, not numeric order — loading an older page inserts smaller ids that still land last in that order. Handing Shoji that raw, unsorted iteration order would make next/prev inside the lightbox jump around instead of following the visual grid. Every updateSlides() call sorts first, exactly once, right before handing the array over.

Opening a slide: data-shoji-id, not a captured index

A thumbnail's click handler shouldn't close over the index it happened to render at — by the time it's clicked, updateSlides() may have grown or reordered the array underneath it. Both demos instead store the item's id on the element (a.dataset.shojiId = item.id) and re-resolve the index fresh, at click time, from whatever the current array actually is: 

function openById(id) {
  const index = sortedItems().findIndex((i) => i.id === id);
  if (index !== -1) gallery.open(index);
}

This is also why Shoji's own origin lookup (Gallery.getOriginElement()) checks for a data-shoji-id-marked element first, before falling back to a selector-mode scan — dynamic mode has no scanned DOM to fall back to at all, so the marker is the only way Shoji can find the on-page thumbnail a given slide opened from (for the zoom-from-thumbnail transition, and anywhere else it needs that element).

Plugin choice: ActiveThumbnail only where nothing gets unmounted

Forward-only enables it — tiles are only ever appended, never removed, so there's no way the plugin ends up tracking an element that's since vanished. Bidirectional deliberately leaves it off: its on-page grid is virtualized (see the example), meaning the exact tile ActiveThumbnail would be highlighting can be unmounted the moment it scrolls outside the rendered window — a real interaction worth avoiding by not combining them, rather than adding recovery logic for it.

If you build a virtualized grid like the bidirectional example's, it only stays compatible with Shoji's Layout plugin in grid mode (uniform tile sizes) — not masonry or justified, which size rows from each photo's real aspect ratio, so there's no fixed row height for a virtual list's position math to rely on.

See the Infinite scroll example for the actual scroll-position and DOM-virtualization code — the sentinel/IntersectionObserver pattern for forward-only, and the fixed-row virtual list for bidirectional. None of it is Shoji-specific; it's ordinary host code that happens to call updateSlides() and open() at the right moments.
