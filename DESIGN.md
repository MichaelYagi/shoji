# DESIGN.md — Shoji

A zero-dependency, plugin-first lightbox/gallery library. Feature parity with lightGallery's core, plus slideshow, video, and a layout engine (grid/masonry/justified) — with a smaller, cleaner core.

---

## 1. Goals & non-goals

**Goals**

- Drop-in replacement use case for lightGallery: open a lightbox from thumbnails or programmatically (dynamic mode), navigate with touch/drag/keyboard, virtual slides for huge galleries.
- Everything beyond the minimal lightbox is a plugin with a stable, documented API.
- First-class: slideshow, video (HTML5 + YouTube), active-thumbnail sync, fullscreen, rotate/flip (view), zoom, layout (grid/masonry/justified), responsive images, a11y.
- Buttery performance: hardware-accelerated CSS transitions, ≤ 3 slides in DOM, no layout thrash in gesture paths.

**Non-goals**

- No framework wrappers in core (React/Vue adapters can come later as thin packages).
- No server component — zero backend dependency, nothing in core or an official plugin ever calls out to a server.
- No IE / legacy support. Baseline: last 2 versions of evergreen browsers + iOS Safari 16+.

---

### 2.1 Item model

```ts
interface GalleryItem {
  id?: string;               // stable id — updateSlides() diffing, ActiveThumbnail's data-shoji-id match, zoom-transition origin lookup. Falls back to src.
  src: string;               // full-size source
  srcset?: string;           // responsive sources
  sizes?: string;
  sources?: MediaSource[];   // <picture>/video sources incl. webp/avif
  thumb?: string;
  poster?: string;           // video poster
  video?: VideoDescriptor;   // html5 | youtube | vimeo | custom — all four have a renderer today (§4.3)
  width?: number; height?: number;  // for aspect-ratio placeholder
  alt?: string;
  caption?: string | HTMLElement | DangerousHtmlCaption;
  download?: string | false;
  data?: Record<string, unknown>;   // user payload, untouched by core
}

type MediaSource = { src: string; type: string };  // mirrors a <source src type> child

type VideoDescriptor =
  | { provider: 'html5' }                                    // sources[] on GalleryItem carries the <source> list
  | { provider: 'youtube' | 'vimeo'; id: string; url?: string }
  | { provider: 'custom'; render: (el: HTMLElement, item: GalleryItem) => void | (() => void) };  // §4 "custom provider registration"

type DangerousHtmlCaption = { dangerouslySetInnerHTML: string };  // named after React's own escape hatch on purpose; Shoji does not sanitize it
```

Items come from DOM scanning (`selector` mode), or arrays (**dynamic mode**), and can be mutated live via `gallery.updateSlides(items, currentIndex?)` — core diffs by `id` (fallback: `src`), preserving the active slide when possible, matching lightGallery's updateSlides semantics. `gallery.addSlides(items, atIndex?)` (default: append) and `gallery.removeSlides(match)` (a single `id`/index, or an array mixing both — index resolved against the list as it is *before* any removal, so `[0, 1]` always means "the first two," not a shifting target) are pure sugar over `updateSlides` for the two most common cases — passing `items.concat(...)`/`items.filter(...)` by hand still works identically, these just read more clearly at the call site.

**Zero-config quickstart.** Every option in this document has a default chosen so that this is a complete integration:

```html
<div id="gallery">
  <a href="photo-1-full.jpg"><img src="photo-1-thumb.jpg" alt="Sunset over the bay"></a>
  <a href="photo-2-full.jpg"><img src="photo-2-thumb.jpg" alt="Mountain trail"></a>
</div>
```
```ts
new Shoji('#gallery');
```

No items array, no plugins, no options object. This works because `selector` mode has a default `selector` and a default DOM→`GalleryItem` attribute mapping, so it doesn't need either specified:

- Default `selector`: `':scope > a, :scope > [data-shoji-src], :scope > [data-shoji-video]'` — direct children that are anchors or carry `data-shoji-src`/`data-shoji-video` (the last one matters on its own: a video-only element with neither `href` nor `data-shoji-src` still needs to be selected in the first place for the video-detection case below to ever run on it).
- Attribute mapping per matched element: `href` (or `data-shoji-src`) → `src`; a nested `<img>`'s `src` (or `data-shoji-thumb`) → `thumb`; that `<img>`'s `alt` (or `data-shoji-alt`) → `alt`; `data-shoji-caption` → `caption` (a separate, optional field — not backfilled from `alt`, since alt text and a display caption are allowed to say different things); `data-shoji-width`/`data-shoji-height` → `width`/`height`; `data-shoji-id` → `id` (falls back to `src`, per the diffing rule above).
- **Any other `data-shoji-*` attribute → `item.data`**: an attribute that isn't one of the named mappings above (or `data-shoji-no-drag`, §2.4's drag-opt-out marker) is captured into `item.data`, keyed by the attribute name with the `data-shoji-` prefix stripped verbatim — `data-shoji-metadata-id="123"` becomes `item.data['metadata-id']`, no camelCasing. This is the same free-form bucket dynamic-mode items already use for host payloads (`data?: Record<string, unknown>`, §2.1's item model) — populated from the DOM here instead of host-constructed, and only set at all when at least one such attribute is present (`item.data` stays `undefined` otherwise, same as before this existed). `src/core/scan.ts`.
- **Video detection** — two cases, checked in this order:
  1. A nested `<video>` element (progressive-enhancement friendly: plain HTML5 video markup just works) → `video: { provider: 'html5' }`, its `poster` attribute → `poster`, and each child `<source src type>` → an entry in `sources`. The matched element's own `href`/`data-shoji-src` is ignored in this case; the `<video>` is the source of truth.
  2. No nested `<video>`, but the matched element has `data-shoji-video` → that URL is checked against known provider hosts (`youtube.com`/`youtu.be`/`youtube-nocookie.com`, `vimeo.com`/`player.vimeo.com`) and becomes `video: { provider, id, url }` with `id` extracted from the URL; `data-shoji-poster` → `poster` (if omitted, the item just has no poster — oEmbed poster-fetch was scoped to the Video plugin, which is not being built, see §4's roster). A `data-shoji-video` URL matching neither known host is treated as `{ provider: 'html5' }` with that URL as the sole `sources` entry, so a bare MP4 link works without a `<video>` tag too. `data-shoji-video-provider` (§4.3) can force `html5` on a URL that would otherwise be detected, or make the youtube/vimeo claim explicit (trusting an id even off an unrecognized host) — any other value, `wistia` included, is unrecognized and ignored with a warning.
  3. Neither present → not a video item; falls through to the image mapping above.
- **Click-to-open is automatic in selector mode**: each matched element gets a click listener that opens the gallery at its index and calls `preventDefault()` (so a real `<a href>` never navigates away). This is the one piece of behavior, not just config, that has to have a sane default for the quickstart above to do anything — without it, `open()` would need to be wired up by hand for every gallery, which is exactly the boilerplate a "drop-in replacement" shouldn't require.
- Dynamic mode (`items: GalleryItem[]`) has no equivalent auto-open, since there's no DOM element to attach a listener to by default — the host calls `gallery.open(index)` itself (e.g. from its own thumbnail grid's click handler).
- **Closed by default, in both modes, until a click or an explicit `open()` call** — the lightbox DOM builds eagerly at construction (§3.1, for the layout plugin's benefit) but stays hidden (`display: none`) and `isOpen` stays `false` until something actually opens it. `openOnInit: true` (default `false`) is the explicit opt-out of that default: the gallery opens immediately at construction, to `index` (default 0) — meant for hash/deep-link-style integrations that should land straight in the lightbox on page load, not a normal-usage default. A gallery that pops open without a click is surprising in every other case, which is why this stays off unless asked for.

### 2.2 Lifecycle & events

Typed event bus; every feature is observable and cancelable where sensible:

```
beforeOpen → open → afterOpen
beforeSlide(from,to) → slideItemLoad → afterSlide
beforeClose → close → afterClose
itemsUpdated · dragStart/drag/dragEnd · zoomChange
select:change · edit:open/apply/save/restore · scroll:append/prepend
posterDefined · fullscreenChange · autoplayStart/Stop
```

`autoplayStart`/`autoplayStop` are implemented (§4.1) — `Progress` deliberately isn't: the progress bar there is driven by a single CSS `transition` per interval (set width to 0, force reflow, transition to 100% over `interval`ms), not a JS-side ticking event, since that's simpler and avoids a `requestAnimationFrame` loop for something CSS already does natively.

`gallery.on(event, fn)` returns an unsubscribe function. Events carry typed detail objects. Cancelable events (`before*`) support `event.preventDefault()`.

### 2.2a Navigation & looping

```ts
new Shoji(el, { loop: false })   // default true
```

- **`next()`/`prev()`** (and everything that calls them — arrow keys, Home/End's own boundary aside, the prev/next toolbar buttons, a completed swipe, §2.4) wrap past the last/first item by default: `next()` at the last item goes to index 0; `prev()` at index 0 goes to the last item. `loop: false` restores the old clamp-at-the-ends behavior instead (`next()`/`prev()` become no-ops at the boundary).
- **`goTo(index)`** always clamps an out-of-range `index` to `[0, length-1]`, regardless of `loop` — it's a directed jump to a specific slide, not a step, so there's no boundary to wrap around. `next()`/`prev()` are the only two callers that decide whether to wrap *before* calling `goTo`.
- **`Home`/`End`** (§2.6) jump to the first/last item directly (`goTo(0)`/`goTo(length-1)`) and are unaffected by `loop` either way — they're already an explicit "go to the boundary" action, not a step that could wrap past it.
- Single-item galleries are unaffected: `next()`/`prev()` resolve to the same index either way, and `goTo` no-ops when the target already equals the active index.

### 2.3 Virtual slides

Only `currentIndex − 1 … currentIndex + 1` exist in the DOM (`preload: 1` by default, configurable). Slide elements are pooled and recycled; media loads on demand with `loading` states, aspect-ratio placeholders (from `width/height`), and `img.decode()` before enter transitions to avoid progressive-decode/GPU tile seam artifacts. Galleries of 100k items must open in O(1).

**Loading state: a spinner, not the stale previous slide.** An earlier version of this kept the previous slide's content on screen until the next one finished decoding, to avoid a blank window (`decode()` is never synchronous). In practice that read as broken, not helpful — the old image no longer matched the caption/counter/URL that had already moved on. Navigating to an index that needs a fresh decode now clears the slot immediately and shows a `.shoji-slide-spinner` (pure CSS, an animated ring) in its place; `SlideManager.swapIn()` still swaps the spinner out for the real content atomically once it's ready. Video is the one exception, as before: it's inserted immediately rather than behind a spinner, since the native `poster` attribute already shows something meaningful without waiting on `loadedmetadata`.

**Open-transition placeholder: a low-res stand-in, only on `open()`.** Unlike the "stale previous slide" case above — a *different*, wrong slide's content, correctly rejected — a fresh `open()` sometimes has a genuinely correct low-res preview of the *same* slide available (the thumbnail the viewer just clicked). `Gallery.resolveOpenPlaceholderSrc()` checks, in order: `item.thumb`; a live `data-shoji-thumb` attribute read off the origin element found by §2.3b's origin lookup (lets a dynamic-mode host opt in by tagging existing markup, no item-array change needed — same pattern as `data-shoji-id`); the origin element's own already-rendered `<img>`, if any. If none apply, the ordinary spinner shows, unchanged. When one does, `SlideManager.render()` (only ever passed this by `Gallery.open()` — never ordinary navigation) eventually shows a `.shoji-slide-open-placeholder` `<img>` in the centerIndex slot instead of the spinner (see `revealOpenPlaceholder()`'s own real-bug entry below for why not immediately), swapped out for the real content the same atomic way the spinner would be, the instant the real decode resolves. A known, accepted limitation: if the thumbnail's crop/aspect ratio differs from the full image's, the placeholder can briefly show the wrong crop, not just a blurrier version of the right one — considered acceptable rather than worth constraining further.
  - **Sizing: forced to fill the frame, not capped like ordinary slide media.** Every other `.shoji-slide-img` only has `max-width/max-height: 100%` — a cap, never a floor, correct for a real photo (normally bigger than the display area). A thumbnail is the opposite case: deliberately small, so capping alone does nothing and it would render at its own tiny native pixel size, centered, inside the now-fully-grown slide — reported directly ("transitioning from a thumbnail to a thumbnail and suddenly popping up as a full size image" once the real photo, at *its* native size, replaced it). `.shoji-slide-open-placeholder` adds explicit `width: 100%; height: 100%`, forcing it to stretch to the frame — blurry, deliberately — with `object-fit: contain` (inherited from `.shoji-slide-img`) still letterboxing per its own aspect ratio rather than distorting it.
  - **The real content swaps in with no animation of its own — deliberately.** An earlier version also grew the incoming real content in from a smaller, faded start (`scale(0.92)`/`opacity: 0` to natural), the same FLIP technique as the outer zoom. Reported directly after trying it: the two didn't read as one continuous motion — the outer zoom (thumbnail → full slide size) usually finishes well before the real decode does (the whole reason this placeholder exists is a slow decode), so the second animation fired well after the first had already settled, reading as a disconnected, unexplained *second* transition rather than a continuation of it. The outer zoom already does the "growing" job; the content swap underneath it just needs to be instant.
  - Provider-video's own loading path (§4.3) appends its embed *alongside* whatever's already in the slot and only explicitly removes `.shoji-slide-spinner` once the embed reveals — extended to also remove `.shoji-slide-open-placeholder`, or a placeholder would be left behind, invisibly stacked under the now-visible embed forever.
  - **A real bug, reported from real usage: the placeholder itself could show as a blank/black gap, on the exact combination this whole feature exists to help — a large image shown through the Layout plugin (§5).** `revealOpenPlaceholder()` originally inserted the placeholder `<img>` immediately, unconditionally. But `item.thumb` is routinely just `item.src` again — no real thumbnail-generation step exists, and even Shoji's own Layout demo (`demo/pages/layout.ts`) does this deliberately, relying on CSS alone to shrink the *display* of what's still the full-resolution file for the grid tile. A brand-new `<img>` element pointed at that same large file still has to fully decode it before anything paints — decode cost scales with real pixel dimensions, not cache-hit status — so inserting it immediately, unconditionally, left a visibly blank gap (an undecoded `<img>` paints nothing) for exactly as long as that decode took, which could be *longer* than showing the spinner would have been. Fixed by not inserting it until its own `decode()` resolves — the spinner stays up until then. A genuinely small/fast thumb still swaps in almost instantly, unchanged from before; a slow one just leaves the spinner up a little longer instead of showing nothing, never worse than not having a placeholder at all. (A second, smaller bug caught while fixing this: the original immediate-insert used `replaceChildren()`, which — for a provider-video slide specifically — would have destroyed the already-appended, still-hidden embed container alongside the spinner it meant to remove; the fix removes only the spinner.)

**The active slide's own toolbar controls grey out while it's loading.** `SlideManager` tracks per-slot readiness (`Slot.ready`, exposed via `isActiveReady()`); `Gallery.setSlideLoading()` toggles a `shoji-slide-loading` class on `.shoji-outer` and, on every `.shoji-toolbar-button` (zoom, rotate, fullscreen, autoplay, any custom plugin's own button — never `.shoji-close`/`.shoji-nav`, different classes entirely), both `aria-disabled` and `tabIndex = -1` — the latter so a keyboard user tabbing through the toolbar skips them while disabled, not just visually dims them (`pointer-events: none` alone doesn't stop `Enter`/`Space` activating an already-focused button). Deliberately scoped to feature buttons only: prev/next/close are never gated, so a slow-loading image can't trap the viewer into waiting to navigate away or close.

**`preload` actually prevents the spinner within its window, by caching ready content per item index, not per pool slot.** Pool slots are keyed by *structural offset* — a fixed offset's *content* gets reassigned on navigation (the pooling model above) — so a naive "is this slot already showing the right index" check misses the routine case where an already-decoded item needs to move from one physical slot to another (stepping forward moves the `+1` slot's content into the `0` slot, for instance). `SlideManager` keeps a separate `Map<index, {node, item}>` cache, trimmed to the same `centerIndex ± preload` window the slots themselves cover: `render()` checks this cache before starting any decode, and if the target index is already there, moves that exact node into its new slot (no redecode, no spinner, `onLoad` fires synchronously) instead of throwing the work away. Navigating further than `preload` away (a fast flick through several slides, or a direct `goTo()`) still shows the spinner, same as ever — the cache only ever covers what was actually preloaded.
  - **A subtle correctness requirement this introduced**: a slot's outgoing content must never be destructively released (`<video>`'s `pause()`/`removeAttribute('src')`/`load()`) while it might still be needed by a *different* slot within the same `render()` call — e.g. stepping backward shifts every slot's content down by one, all at once. `render()` resolves this in two ordered passes: phase 1 claims every cache hit first (`moveIn()`, which only reparents via `replaceChildren` — always safe, never destructive), so anything still reusable gets relocated before phase 2 releases whatever's genuinely left over as stale. The cache-eviction step at the top of `render()` (dropping entries that fell outside the new window) explicitly releases any `<video>` it drops for the same reason — an evicted entry not caught by phase 1 would otherwise be silently orphaned, paused-in-place but never actually released.
  - **A real bug, found and fixed**: the first version of this cache only stored *completed* decodes — an in-flight decode was still tracked per-slot. Navigating before a preload decode resolved reassigned that slot to a different target, abandoning the decode entirely and starting a duplicate fetch for the same image once the viewer actually arrived — on a slow connection (e.g. images served from a NAS), the decode could never actually catch up, since every navigation before it finished just restarted it elsewhere. Fixed by tracking in-flight image decodes in a second map, `pending: Map<index, HTMLImageElement>`, keyed the same way as `cache`: `ensureImageDecoding()` is a no-op if `index` is already pending, and its `reveal()` callback resolves which slot (if any) currently wants that index by looking up `Slot.assignedIndex` fresh at resolve time, rather than remembering the slot that started the request — correct however many times the pool has reshuffled in between, and a harmless no-op if nothing wants it anymore.
  - **A real bug, reported from real usage: a provider video (§4.3, e.g. YouTube) is never reused across a slot move — always rebuilt fresh instead.** `moveIn()`'s reparent (`replaceChildren`) is safe for an `<img>`/native `<video>` — browsers preserve their loaded state across a same-document reparent — but not for a provider's `<iframe>`: most browsers reload an iframe's content when it's moved to a new parent, even within the same document, which silently breaks its already-wired player API (Autoplay, §4.1, kept looking like it should be playable — `.play` was still wired — but `mute()`/`playVideo()` calls sent to the now-defunct, reloaded iframe never took effect; no error, no rejected promise, just a video that never plays and never fires `ended`). Confirmed directly: the identical code plays fine when the viewer lands on a YouTube slide directly (its container is built once, in place, never moved) but not when reached the ordinary way — preloaded as a `+1` neighbor, then stepped onto, the routine case this whole cache exists to optimize. Originally fixed by excluding `.shoji-slide-provider-video` nodes from the phase-1 cache-reuse loop entirely, always rebuilding fresh in the new slot instead — see the follow-up bug directly below for why that turned out to be its own real cost, and the actual current fix.
  - **A follow-up real bug, reported from real usage: the "always rebuild fresh" fix above traded a correctness bug for a performance one.** Bouncing back and forth across a YouTube slide's neighbor boundary (e.g. clicking through a thumbnail strip faster than a slide settles, or just stepping past it and back) rebuilt the iframe embed from scratch — a brand-new `YT.Player`, a real network round-trip — on *every single crossing*, not just once. That's real, synchronous-ish work landing in the middle of the slide transition, competing for the same frame budget, and read as visibly jerky every time, unlike an ordinary photo neighbor (a cached `<img>`, reused instantly). Root-caused by reproducing the exact reported symptom directly: bouncing between two adjacent slides that stay resident the whole time (never actually leaving the `preload` window) still rebuilt the video, because the *only* way the old pool model could keep content at a new offset was to move it into the physically-fixed slot for that offset — impossible for a live iframe, so provider video was excluded from reuse entirely rather than reworking how reuse itself worked. Fixed at the root: `SlideManager.render()` no longer moves content between slots at all, for *any* type. A slot whose content is already resident and ready just has its own `offset` relabeled to its new pool position — the DOM node never moves, so the original reparent hazard structurally can't apply, and a provider video's `<iframe>` can now be reused exactly like an `<img>`/`<video>` always could. Confirmed directly: the identical `<iframe>` element (and its already-wired `YT.Player`) survives an arbitrary number of crossings, not just the first reuse. `moveIn()` (the old reparent-into-a-different-slot helper) is now only ever used for a node's first insertion into the slot that's already waiting on it, never to relocate one — reparenting across slots no longer happens anywhere in `SlideManager`, for anything.

### 2.3a HTML5 video playback (core baseline)

An item with `video: { provider: 'html5' }` (§2.1) renders as a real, natively-controllable `<video controls playsInline>` — not just a poster image. Native controls give play/pause/seek/volume/fullscreen for free, no custom control UI needed. Deliberately **not** muted and **not** autoplayed: opening a video slide is a click-to-play moment for the viewer, not a background/preview loop, so there is no browser autoplay-policy reason to mute it either.

- `item.sources` (if present) become `<source src type>` children; otherwise `item.poster`/`item.src` are used directly.
- No `src` and no `sources` at all → a `.shoji-slide-placeholder` reading "Video" renders instead (nothing to play).
- Slide-pool slots are reused across navigation (§2.3); before a slot's content is replaced, any `<video>` it held is explicitly `pause()`d, has its `src` removed, and `load()`s — removing it from the DOM alone doesn't stop playback or release network/decoder resources. The same release runs on `destroy()`.
- **A real bug, reported from real usage: a video the viewer started playing kept playing — audibly, invisibly — after `close()`, or after navigating to a different slide entirely.** Neither ever touched it: `close()` never tears down the slide pool at all (reopening is meant to be instant, not rebuilt from scratch), and a slide within the `preload` window stays cached on navigation for the same reason — only genuine eviction from that window ran the destructive release above. Fixed with `SlideManager.pauseMedia()`, a new, non-destructive counterpart to the release path — pauses a native `<video>`, or a provider embed via the same duck-typed `.pause()` contract Autoplay's `findPlayable` already relies on (§4.3), without touching `src`/resetting anything. `Gallery` calls it on `close()` and immediately before every navigation, on whichever slide is being left — the node itself stays exactly as it was, so navigating back to it resumes right where playback stopped instead of rebuilding.
  - **A follow-up real bug, this fix's own side effect racing a plugin's video listeners: `pauseMedia()`'s `.pause()` call fires a native `pause` event, and in `navigate()` that used to happen *before* `beforeSlide`, while the outgoing slide's own listeners (Autoplay's `onVideoPause`, §4.1 point 3) were still attached — a viewer-pause detector, misreading this programmatic pause as a manual one and stopping the whole slideshow, sometimes in the middle of that same slideshow's own `advance()` call trying to move past a stuck video (§4.1 point 12).** `activeIndex` hasn't changed yet at the point either fires, so reordering doesn't change which slide either one sees — only their relative order changed: `navigate()` now emits `beforeSlide` *before* calling `pauseMedia()`, giving a listener (Autoplay's new `beforeSlide` handler, which calls its own `detachVideo()`) a chance to detach before the pause it's about to cause arrives. `close()`'s own `beforeClose`/`pauseMedia()` ordering was already this way round and needed no change — Autoplay only listens for `'close'` (fired later, after the outgoing video is already fully torn down), not `'beforeClose'`, so the same race never applied there.
- Keyboard nav (arrows/Home/End) is suppressed while a `<video>` has focus, so seeking with arrow keys doesn't also navigate the gallery; `Escape` still closes regardless.
- **Play overlay** (`videoPlayOverlay: boolean`, `GalleryOptions`, default **`false` — opt-in**): a faint, semi-transparent `.shoji-video-play-overlay` button sits centered over the video whenever it's paused — native paused-video affordances vary too much across browsers to rely on for "you landed on a video," if a host wants that reliability. It tracks the `<video>` element's own `play`/`pause`/`ended` events (not "is the Autoplay plugin involved"), so it's correct regardless of what calls `.play()` — Autoplay's own `video.play()` (§4.1) hides it the same as a manual click would. Clicking it calls `video.play()` and does not bubble to click-outside-to-close (§2.5). It always stays visible regardless of auto-hide idle state (§2.8) — it's part of the media content, not a chrome control.

  **Flipped from always-on to opt-in, requested directly: a host supplying their own custom play affordance (a styled replacement for native controls, or relying on native controls alone) doesn't want a second, Shoji-drawn button competing with it for the same click.** `false`/omitted skips creating `.shoji-video-play-overlay` entirely — no DOM node, no `play`/`pause`/`ended` listeners — not just hiding it with CSS, the same "opt out costs nothing, not just looks like nothing" pattern `showProgress` (§4.1) already uses. The always-on original design's own reasoning (native paused-state affordances aren't reliable enough to skip an explicit affordance) still holds as the *default recommendation* — a host that hasn't thought about it either way is better served by leaving it on — but isn't forced on hosts who've deliberately decided otherwise. Threaded through as a real `SlideManagerOptions` field (`Gallery.ts`'s `ensureLightbox()` → `new SlideManager({...})`), not a post-hoc CSS toggle. Style it via `.shoji-video-play-overlay` (and `--shoji-video-overlay-size`/`-bg`/`-color`) once enabled, same as before.
  - **A real bug, reported from real usage**: `pause` was wired to reveal the overlay immediately, synchronously. Native `<video controls>`'s own scrub bar genuinely pauses playback for the duration of a drag in most browsers (a real, transient pause, not the viewer choosing to stop) — showing the overlay on every one of those flashed it into view (and briefly made it clickable, dead-center of the video) on every seek interaction, reading as the controls "fighting" the viewer. Fixed with `PAUSE_OVERLAY_DELAY_MS` (200ms, `SlideManager.ts`): `pause` starts a timer instead of revealing immediately, cleared by `play`; the overlay only actually reveals if the video is *still* paused once the timer elapses. A scrub drag's pause-then-resume completes well inside that window and never shows anything; a genuine stop sits paused past it and reveals normally. `ended` is never debounced — always a real, terminal state.
  - **A real bug, reported from real usage**: its click handler called `video.play()` bare (`void video.play()`), with no `.catch()`. A broken or missing `src`/`sources` — a bad path, a removed file, an unsupported format — rejects with `NotSupportedError`; with nothing to catch it, that surfaced as `Uncaught (in promise) NotSupportedError: The element has no supported sources.` `hasSource` (above) only checks that `item.src`/`item.sources` is non-empty, not that it actually resolves to something playable, so this is reachable with entirely valid-looking item data. ### 2.3b Zoom transition (open ↔ thumbnail, close ↔ thumbnail)

Opening animates the active slide's media zooming in from its triggering thumbnail's on-screen position/size; closing reverses it, zooming back down to that same thumbnail. Implemented as a FLIP transition (`src/core/zoomTransition.ts`): on open, the target is instantly transformed (via `translate`+`scale`, no transition) to exactly overlay the origin's `getBoundingClientRect()`, then a transition is kicked off back to natural size/position in the same synchronous call (one reflow, no visible flash of the untransformed state).

`computeTransform`'s `translateX`/`translateY` is **center-to-center** math (delta between the two rects' centers) — it only lands correctly paired with `transform-origin: center`, the CSS default. A real bug shipped once from setting `transform-origin: top left` instead: the math still ran and produced *a* transform, silently landing the scaled box wherever the origin's center happened to sit relative to its own top-left corner rather than on the origin's rect — visually, the zoom appeared to come from the wrong photo entirely. Zero-size mocked rects (jsdom's default) make `computeTransform` return `null` before this math ever runs, so plain unit tests never exercised it; only real, non-zero rects — either a real browser or an explicit rect mock — reproduce it. `tests/unit/zoomTransition.test.ts`'s "regression: the instant jump actually lands the target on top of origin" test pins this down by mocking real geometry and replaying the CSS transform math against it, not just asserting a style string.

`computeTransform`'s scale is a **single uniform factor**, not independent `scaleX`/`scaleY` — a second real bug, this one visual rather than positional. Origin (a thumbnail tile — often cropped to a uniform grid shape, e.g. grid mode's default square `aspectRatio`, §5.1) and target (`.shoji-slide-media`, sized to the lightbox's own viewport-shaped slide area) essentially never share an aspect ratio. Scaling each axis independently to force an exact rect match on both — the original implementation — visibly squeezed/stretched the image non-uniformly for the entire transition, worse the further apart the two shapes were (a square grid tile opening into a wide/tall slide was the worst case). Fixed by using `Math.min(scaleX, scaleY)` as a single factor: the box stays fully *contained* within origin's rect (same tradeoff `object-fit: contain` already makes) rather than exactly filling it on both axes — the center still lands exactly on origin's center either way, only the unconstrained axis's edges fall short of origin's own. Verified both against mocked geometry (`tests/unit/zoomTransition.test.ts`) and by sampling the real, browser-interpolated `getComputedStyle().transform` matrix at several points mid-transition in an actual browser — `scaleX === scaleY` throughout, not just at the start/end.

A third real bug, this one a race rather than a math error: masonry/justified's first layout pass can run before the container reports a real width (`containerWidth <= 0`, §5.4) — when that happens, the pass is skipped entirely and the correction only lands once the `ResizeObserver`'s own *asynchronous* initial notification fires. In the gap between those two points, an unpositioned tile falls back to plain CSS auto-sizing from its `<img>` child — which can be a genuinely 0×0 rect (image not yet decoded) or a wrong-shaped one (some fallback size), but either way it's still a real, clickable rect. A click landing there computes the zoom transition's origin from that bad rect: silently skipped (0×0 trips `computeTransform`'s zero-size guard, §2.3b above) or animated from the wrong place. Reproduced directly: constructing a gallery on a `display: none` container (forcing the skip), then revealing it and opening immediately, before letting the observer correct anything — the clicked tile's transform was still empty and its rect was the degenerate fallback. Fixed in `layout.css`, not core: `.shoji-layout--masonry`/`--justified .shoji-layout-tile` are `visibility: hidden` by default — removed from hit-testing entirely, not just unstyled — and the layout functions (`applyMasonry`, `applyMasonryHorizontal`, `applyJustified`/`applyJustifiedGrouped`) explicitly clear it back to visible the moment they actually set a tile's real geometry. A click during that window now simply doesn't register on the tile at all, rather than registering with broken zoom math. Verified in a real browser: mid-gap, the tile was confirmed both `visibility: hidden` and excluded from `document.elementFromPoint` hit-testing at its own coordinates; once the observer's real correction landed, it was visible with a correct transform.

**A fourth real bug, found building the zoom plugin (§4.6)**: `computeTransform`'s `target` rect was always `target.getBoundingClientRect()` itself — but `target` is `.shoji-slide-media`, which is *always* its full flex-box size (`width/height: 100%` of `.shoji-slide`, roughly the whole dialog), never the actual photo's own rendered size — `object-fit: contain` almost always letterboxes the real image *smaller* than that container. Scaling/translating based on the container's full (too-big) rect made the animation scale from/to a box far bigger than the photo ever actually renders at, so the image visibly shrank to something much smaller than the thumbnail whenever the photo's aspect ratio didn't match the dialog's own shape — the common case, not an edge case; a square-ish container with a wide photo was the worst case. Fixed by `effectiveTargetBox()` (`zoomTransition.ts`): prefers the real rendered media child's own rect if it's already attached (accurate, but usually isn't yet on a fresh *open* — `decode()` is always async); else an analytically-computed `object-fit: contain` box from a supplied `aspectRatio` (`item.width`/`height` when known, else the origin thumbnail's own `naturalWidth`/`naturalHeight` — accurate whenever `item.thumb` is unset, since thumb and full image are the same file); else the container's own rect as a last resort, unchanged from before. Verified with mocked geometry (`tests/unit/zoomTransition.test.ts`) and in a real browser, comparing the captured scale against what the old container-only calculation would have produced.

**A fifth real bug, same investigation, this one a race**: `zoomIn`/`zoomOut`'s cleanup (`clearInlineTransform`, run from `waitForTransitionEnd`'s callback — either a real `transitionend` or its fallback timeout, either of which can land well after the animation visually finishes) used to unconditionally clear `target.style.transform`. Since `target` is the *same* `.shoji-slide-media` element the rotateFlip plugin (§4.5) applies its own rotate/flip transform to, a viewer who rotated the photo quickly after opening — before this transition's own delayed cleanup had fired — would see their rotation silently wiped out from underneath them. Fixed by only clearing `transform` if it still matches the exact value this animation itself last wrote (nothing else has touched it since); `transition`/`transformOrigin` are still always cleared, since nothing else in this codebase sets those. Reproduced and pinned down in a real browser with rotateFlip and zoom both enabled together (rotate immediately on open, wait past the transition's cleanup window, then zoom — the rotation used to disappear at exactly that point) and covered by two regression tests in `tests/unit/zoomTransition.test.ts` (one per direction) that set a foreign transform value mid-flight and assert it survives cleanup.

**A sixth real bug, reported from real usage (a hard refresh, opening the first slide — nothing decoded yet)**: `effectiveTargetBox()`'s first check — "prefer the real rendered media child's own rect, if attached" — trusted *whatever* `target`'s first child happened to be, without checking it was actually the photo. On a fresh open with nothing decoded, that first child is the loading spinner (§2.3), a fixed ~40px circle — `computeTransform` then scaled `.shoji-slide-media` (and everything inside it, the spinner included, since a CSS transform on a parent scales all its descendants along with it) using that tiny rect as the target box instead of the photo's real, much larger, size. Origin (the thumbnail) is bigger than a 40px circle, so the resulting scale factor came out **inverted — greater than 1, not the intended less-than-1 "shrink to thumbnail size and grow back"** — rendering the spinner briefly, visibly oversized (roughly thumbnail-tile-sized) right as the dialog opened, before shrinking back down to its real size over the transition. Reproduced in a real browser: a genuinely cold-cache slide image (never fetched before, unlike the already-warm thumbnail) delayed just enough to keep the spinner showing past the point `effectiveTargetBox()` first runs, confirming `.shoji-slide-media`'s captured transform matrix scaled up (`~2.57×`) instead of down. Fixed by excluding `.shoji-slide-spinner` specifically from the "trust the child's rect" fast path, so it falls through to the intended second choice (an analytically-computed `object-fit: contain` box from `aspectRatio`) instead — exactly the path this was already supposed to take whenever nothing real is attached yet. Covered by a regression test in `tests/unit/zoomTransition.test.ts` mirroring the existing "prefers the real rendered media child" test, but with a spinner in place of a real `<img>`.

**A seventh real bug, same class, introduced by the open-transition placeholder (§2.3) and caught before shipping**: that placeholder is a real, non-spinner `<img>` — so `effectiveTargetBox()`'s "trust the child's rect" fast path trusted it too, the same way it once wrongly trusted the spinner. Its rendered rect reflects *its own* crop/aspect ratio (a small grid thumbnail, often square-cropped), not the real photo's, so the animation would scale toward the placeholder's shape instead of the real photo's — landing at a plausible-looking but wrong size, then visibly jumping again once the real photo swaps in (already past this transition by then). Fixed the same way as the sixth bug: `.shoji-slide-open-placeholder` is excluded from the "trust the child's rect" fast path alongside `.shoji-slide-spinner`, falling through to the same analytical `aspectRatio`-based box either would use — sized for the real photo regardless of what shape the placeholder happens to be. The placeholder still visually scales correctly either way (it's a descendant of `target`, and a CSS transform on a parent scales every descendant along with it) — this only changes what box size *drives* the transform math, not whether the placeholder itself is shown. Covered by a regression test in `tests/unit/zoomTransition.test.ts` mirroring the sixth bug's own test, with the placeholder in place of the spinner.

**An eighth real bug, reported from real usage: zoom-from-thumbnail worked on the first `open()` of a session, then silently stopped working on every `open()` after a `close()`, compounding indefinitely.** `clearInlineTransform()`'s "only clear if nothing else touched it since" safety check (fifth bug, above — same function) compared `target.style.transform` against `expectedTransform`, the *raw string* `computeTransform()` produced — e.g. `scale(0.10416666666666667)`, an arbitrary-precision JS float interpolated directly into the template literal. Setting `element.style.transform` to that string and reading it back does **not** round-trip unchanged: the browser's own CSSOM serializer reformats numeric values on its own terms (observed in Chromium: read back as `scale(0.104167)`) — a real-browser quirk no jsdom unit test can reproduce, since jsdom's simplified CSSOM doesn't reformat anything. The string comparison therefore failed for any scale factor without a short, clean decimal (effectively all of them), so `zoomOut()`'s shrink-to-thumbnail transform was never cleared from `.shoji-slide-media` after `close()` — permanently stuck there, since nothing else ever touches this element's transform between closes. The *next* `open()`'s `computeTransform` then measured that already-shrunk element's `getBoundingClientRect()` (which reflects the currently-applied transform, not the untransformed layout box) as if it were the natural size — computing a near-1, barely-visible scale instead of a real zoom-in, reading as "doesn't zoom, just appears." Every further open/close cycle compounds the same failure, since the stuck transform is still there to be misread again. `zoomIn()`'s own cleanup never hit this — it always compares against the literal string `'none'`, which round-trips through the CSSOM unchanged (no float involved). Fixed by having `zoomOut()` read `target.style.transform` back immediately after assigning it, and pass *that* (already in the browser's own normalized format) as `expectedTransform`, instead of the raw JS string — comparing like-for-like regardless of how the browser chooses to reformat it. Only reproducible in a real browser (`tests/e2e/core-zoom-transition.spec.ts`); confirmed to fail without the fix and pass with it.

**A ninth issue, reported as general open/close sluggishness rather than a specific visual bug**: `computeTransform` emitted a plain 2D `translate()`/`scale()`, and `target` (`.shoji-slide-media`) had no `will-change` hint ahead of the animation — the same GPU raster-tile-seam/compositing class of issue independently found and fixed in the Zoom plugin's own scale animation (§4.6), just not yet applied to this one even though it's the identical technique (a large photo scaled via `transform`) on the same element. Fixed the same way: `translate3d`/`scale3d` instead of the 2D forms, and `target.style.willChange = 'transform'` set right before the animated transform starts, cleared in `clearInlineTransform` once it ends (not left on permanently — `.shoji-slide-media` is the offset-0 pool slot, alive for the gallery's whole lifetime, unlike the Zoom plugin's `will-change`, which is scoped to a CSS class only present while actually zoomed). As with the Zoom plugin fix, this isn't independently reproducible/verifiable in this environment (headless/software rendering doesn't exhibit GPU compositing artifacts) — the standard, well-established mitigation for this bug class, not a guaranteed fix on every GPU/driver.

**A tenth real bug, reported from real usage: a genuinely small photo visibly grew to fill the dialog on open, then snapped back down to its true (small) size the instant the real image finished loading — even with `item.width`/`item.height` correctly supplied.** `effectiveTargetBox()`'s `aspectRatio`-derived fallback (the fourth bug, above) fixed the target box's *shape* but not its *magnitude*: `containedBox()` only ever asked "what's the biggest box of this ratio that fits the container," with no concept of the photo's own true pixel size to cap growth at — correct for the ordinary case (a real photo is normally bigger than the dialog, so growing to fill it is exactly right, the same assumption `.shoji-slide-img`'s CSS itself makes), wrong whenever the photo is genuinely small. Confirmed directly: `aspectRatio` alone was already correct (proportions never looked wrong), only the *size* the animation grew toward was — it grew as if the photo would fill the dialog and only discovered it wouldn't once the real, correctly-capped (`max-width/max-height: 100%`, a cap never a floor) image loaded and rendered at its actual size underneath. Fixed by threading the real photo's true pixel size (`ZoomTransitionTarget.naturalSize` — `item.width`/`item.height` only, deliberately never the origin thumbnail's own `naturalWidth`/`naturalHeight`, which would under-cap a genuinely *large* photo down to thumbnail resolution) into `containedBox()`, capping its result at that size the same `Math.min(1, ...)` way RotateFlip's `fitScaleFor` (§4.5) already caps rotation growth. A host that hasn't supplied `item.width`/`item.height` no longer gets a magnitude-guessing fallback at all — see the twelfth entry below, a deliberate follow-up decision, not a bug fix, that replaced the guess with skipping the animation (and the placeholder, eleventh entry below) entirely rather than risk it being wrong. Covered by unit tests (`tests/unit/zoomTransition.test.ts`, including a "no-op for a genuinely large photo" test proving the common case is unaffected) and an e2e test (`tests/e2e/core-zoom-transition.spec.ts`) reading the FLIP animation's own initial computed transform in a real browser, since `zoomIn()` overwrites it synchronously before `open()` ever returns.

**An eleventh real bug, reported from real usage, found re-testing the tenth's own fix: the small photo still visibly ballooned on open — the fix above didn't actually solve it.** The tenth bug's fix caps the FLIP *transform*'s target box; this one is a second, entirely separate offender doing the exact same "grow to fill the dialog" thing through a different mechanism: the open-transition placeholder (§2.3), whose CSS (`.shoji-slide-open-placeholder { width: 100%; height: 100%; }`) unconditionally force-fills the slide frame — deliberately, by original design, for the common case where the real photo is genuinely bigger. That CSS box is entirely unaffected by anything the FLIP transform does: by the time the placeholder is visible, the transform has *already* settled to its natural (still full-size) resting state (`transform: none`) — the tenth bug's cap only ever governed the transient animation, not this static CSS rule the placeholder sits under afterward. Confirmed directly: with the tenth fix alone, `SlideManager.render()`'s `freeTargets.forEach` never even calls `applyAspect()` (which sets `aspect-ratio` from `item.width`/`height`) until real content actually swaps in via `swapIn`/`moveIn` — during the placeholder phase, `.shoji-slide-media` carries no size hint from the item at all, so the placeholder's forced 100%/100% resolves against the full, unconstrained dialog box every time, regardless of known dimensions. Fixed in `SlideManager.ts`'s `revealOpenPlaceholder()`: when `item.width`/`item.height` are known, sizes the placeholder with an explicit inline `width`/`height` in px, computed via `containedBox()` (`zoomTransition.ts`, exported for this reuse) against `slot.media.getBoundingClientRect()` — the exact same contain-and-cap math the tenth bug's fix already uses, just applied once, directly, at reveal time rather than through an animated transform. The `.shoji-slide-open-placeholder` CSS class itself is left untouched (still needed for identification — the eviction/cleanup `querySelector` in this file, and `zoomTransition.ts`'s own `effectiveTargetBox()` exclusion of it, both key off that class); the inline style simply overrides its `width`/`height: 100%` rule for the known-size case, same as any inline style beats a class selector regardless of specificity. Unknown-size items kept the original force-fill guess at this point — superseded by the twelfth entry below, which removes the guess entirely rather than sizing it. Covered by a unit test (`tests/unit/SlideManager.test.ts`, mocking `getBoundingClientRect()` to confirm the computed inline size) and an e2e test (`tests/e2e/core-zoom-transition.spec.ts`) holding the real image's network request open indefinitely (`page.route`) so the placeholder stays the only thing on screen long enough to measure its real, rendered box in an actual browser.

**A twelfth entry, a deliberate design decision rather than a bug fix, asked for directly after the tenth/eleventh fixes above: stop guessing at all.** Both those fixes made the guess *accurate when right* (capped at the real photo's true size, once known) but did nothing to help the case that was never actually a bug — items with no known dimensions at all, which both mechanisms still guessed "probably fills the dialog" for, same as always. Asked directly: for that case, don't guess — show the ordinary loading spinner instead, same as any other not-yet-decoded slide, and skip both the placeholder and the zoom-in animation entirely rather than risk either being visibly wrong. `Gallery.open()` now computes `naturalSize` (via `resolveNaturalSize()`) once, up front: `resolveOpenPlaceholderSrc()` is only even called (so a placeholder is only even considered) when it's present, and `zoomIn()` is only called when it's present — both entirely skipped otherwise, not called with a "best guess" the way they used to be. This means, for an unknown-dimension item, `open()` no longer plays the "grow out of the thumbnail you clicked" motion at all — by design: that animation's only value is bridging an otherwise-empty *waiting* period with something that looks intentional, and once the real image is actually ready to show, there's no gap left to bridge — appearing immediately (no animation) is exactly as fast as an animation could ever be *and* accurate, whereas playing an animation *after* the file has already finished loading would just be theater, delaying what's already ready to show. `close()` got the same treatment for symmetry, but the fix there is narrower and rarer to hit: if the real content already rendered by the time you close (the overwhelmingly common case — you're closing something you were just looking at), `effectiveTargetBox()` already measures its real, on-screen rect directly and was never guessing in the first place, known dimensions or not — only closing before the real content ever finished loading (no known dimensions *and* nothing real rendered yet) skips `zoomOut()` too, via a new `this.slides?.isActiveReady() || naturalSize` guard, closing instantly instead. Covered by unit tests (`tests/unit/gallery-zoom.test.ts`) proving, per case: no placeholder and no `zoomIn()` call without known dimensions even with a valid thumb/origin available; `zoomIn()` still fires normally once dimensions are known (not a general regression); `zoomOut()` skipped when closing before load with no known dimensions; `zoomOut()` still fires when real content already rendered, dimensions or not.

**A thirteenth real bug, reported from real usage immediately after the eleventh entry shipped: the placeholder still visibly rendered at roughly the origin thumbnail's own tiny size, not scaled up at all — "only the thumbnail shows."** The eleventh entry's fix measured `slot.media` (`.shoji-slide-media`) as "the container" to compute the contained-and-capped box against — but `slot.media` is the *exact* element the zoom-in transition (§2.3b, tenth entry) animates its own `scale()` transform on, growing it from an instant jump to the origin's on-screen size up to the dialog's full size over `--shoji-duration` (~300ms). `getBoundingClientRect()` reflects whatever transform happens to be currently applied — and the placeholder's own `decode()` (a microtask) routinely resolves and calls `reveal()` before the browser has painted even a single frame of that transition, i.e. essentially still at the very start of it. Confirmed directly, instrumented in a real browser: at the moment `reveal()` ran, `.shoji-slide-media`'s measured rect matched the *origin marker's own 50×40 size* almost exactly, not the dialog's — so the placeholder's contained-and-capped box computed against that, landing at roughly the origin's size instead of the real photo's. Fixed by measuring `slot.root` (`.shoji-slide`) instead — `position: absolute; inset: 0`, only ever `translateX`'d for pool-offset positioning (§2.3), never scaled by anything — a stable, true read of the real slide size regardless of what its `.shoji-slide-media` child is mid-animation through. Covered by a unit test (`tests/unit/SlideManager.test.ts`) mocking `.shoji-slide` and `.shoji-slide-media` to *different* rects, proving the computation uses the former; confirmed via the regression-verification discipline (reverting just this one line made the test fail with the exact wrong value, restoring it passed). Also attempted as a real-browser e2e test measuring the instant the placeholder appears rather than after a fixed delay (the *previous* e2e test's own fixed 300ms wait happened to also outlast the animation, masking this bug even when present) — that test consistently passes regardless of the fix, since the microtask-vs-paint race it's trying to catch isn't reliably controllable from outside the page the way Playwright's automation API works; the unit test is the real, deterministic regression coverage for this one, not the e2e test, which is kept anyway as a real-browser sanity check of the final numeric result.

**A fourteenth entry, requested directly: closing while zoomed in (Zoom plugin, §4.6) should continue the shrink-to-thumbnail from the zoomed-in view, not snap back to neutral zoom first.** Before this, the Zoom plugin's own `beforeClose` handler reset scale/pan to neutral *before* `zoomOut()` ever measured or animated anything (needed so that measurement stays correct — Zoom's transform lives on the `<img>`, a child of `target`, and `effectiveTargetBox()` reads exactly that child's rect) — the reset itself is instant, but the net effect was still a real jump-cut: the viewer's zoomed-in view snapped to neutral the instant close began, and only *then* did the ordinary thumbnail shrink play. Three rounds to the working fix, each caught before shipping to the user:

1. **First attempt**: a new `Gallery.registerZoomStartProvider()` (single-slot callback, same pattern as `registerZoomGate` immediately below) let the Zoom plugin hand `beginClose()` its live `{tx, ty, scale}` *before* the `beforeClose` reset ran, and `zoomOut()` replayed those numbers directly onto `target` as an instant FLIP jump — the same technique `dragStart` (thirteenth entry's neighbor, above) already uses for a completed vertical drag-close. **Wrong**: visibly shifted the image toward its top-left corner on close, worse the more zoomed in it was. Root cause: Zoom's own pan/scale math is relative to the `<img>` with `transform-origin: 0 0` (deliberately, §4.6, for tractable pan-toward-a-point math) — `zoomOut()`'s jump lands on `target` with `transform-origin: center` instead, a *different* element and a *different* origin than the numbers were computed for. Reapplying the same raw translate/scale values onto the wrong origin doesn't reproduce the same on-screen appearance.
2. **Second attempt**: replaced the raw scale/pan numbers with the zoomed `<img>`'s own real `getBoundingClientRect()` (captured at the same pre-reset moment) — origin-and-coordinate-system-agnostic, computed into a jump the same center-to-center way `computeTransform` already computes everything else (`transformBetween`, the two functions' now-shared math). **Still wrong, but only when RotateFlip (§4.5) was also active**: closing while both rotated/flipped *and* zoomed still snapped to neutral *rotation* first, then zoomed out, even though the origin-mismatch bug above was fixed. Root cause: RotateFlip applies its own `scaleX/scaleY/rotate()` directly to `target` — the *same* element this jump writes to, unlike Zoom's own transform on the child `<img>` (§4.6's own "nesting instead of sharing" note explains why this normally composes for free while the lightbox is just sitting there open — it's specifically the *close* jump that broke it). The jump's `target.style.transform = <computed value>` wholesale-overwrote whatever RotateFlip had there, erasing the rotation *instantly*, before the real animated transition even started — the same class of jump-cut this whole feature exists to remove, just relocated from "the zoom" to "the rotation."
3. **The actual fix**: the jump composes onto `target`'s existing transform (`\`${existing} ${jump}\``) instead of replacing it outright — RotateFlip's rotation, if present, rides along into the instant jump unchanged, and the subsequent real transition (from "rotated + jumped-to-the-zoomed-rect" to the final plain shrink-to-thumbnail value) matrix-decomposes into a single combined un-rotate-while-un-zoom-while-shrink motion, the same free "mismatched function types force matrix-decomposition interpolation" mechanism that already gives an ordinary rotated close (no zoom involved at all) its own smooth un-rotate for nothing.

The measurement itself (`effectiveTargetBox`, re-read fresh for the jump, cheap) stays correct even mid-rotation: both it and the captured `zoomStart` rect are read at the *same* rotation (RotateFlip never resets on `beforeClose`, only `afterOpen`/`afterSlide`), so the scale/translate delta between two equally-rotated bounding boxes still isolates the zoom-only component correctly, regardless of what that rotation happens to be. Covered by unit tests (`tests/unit/zoomTransition.test.ts` — the jump lands correctly on the captured rect, not `target`'s own natural position or origin's; `dragStart` takes priority if both are somehow present; a pre-existing rotate/flip transform on `target` survives into the jump, composed rather than replaced; `tests/unit/gallery-zoom.test.ts` — `registerZoomStartProvider`'s value is read and captured *before* `beforeClose`'s listeners run, passed through to `zoomOut()`, `undefined` when unregistered/not zoomed) and a real-browser verification pass across zoom-only, rotate-only, and rotate+flip+zoom-together close sequences.

**Origin lookup** (`Gallery.findOriginElement`), checked in this order:

1. An element anywhere in the document carrying `data-shoji-id="<item.id>"` — an explicit, opt-in marker that works in *any* mode, including dynamic mode where Shoji has no automatic knowledge of the host's own thumbnail DOM (there is no scanned element to fall back to at all). This is also how the zero-config demo's video tile — which has no `href`/`data-shoji-src` for scan.ts to key off of — supplies a stable id (`data-shoji-id="sample-video"`) for its thumbnail anchor.
2. In selector mode, `scannedElements[index]` — the actual matched DOM element — with no markup needed at all, since scan.ts already has it.
3. Neither found (e.g. dynamic mode with no marker, or the origin/target has zero size — detached, `display:none`, or a genuine 0×0 element) → the animation is skipped silently, not an error; the gallery still opens/closes normally, just without the zoom.

A marker takes priority over the scanned element even in selector mode, letting a host zoom from some inner element (e.g. just the image, not its wrapping caption card) instead of the default.

**Close is deferred**, not instant: `close()` starts `zoomOut` and does not tear down the dialog (remove `shoji-open`, deactivate the focus trap, emit `close`/`afterClose`) until the transition genuinely ends (`transitionend` on the `transform` property, with a `transitionDuration + 100ms` timeout fallback in case the event never fires — e.g. `prefers-reduced-motion` skips the animation and calls back synchronously instead). An `isClosing` guard makes a second `close()` call while one is already in flight a no-op rather than double-firing `beforeClose`. `destroy()` called mid-close force-finishes immediately without waiting for the transition (does not re-emit `beforeClose` if `close()` already had); `finishClose()` itself is idempotent, so a `transitionend` that fires late — after `destroy()` already force-finished — is a harmless no-op rather than a second `close`/`afterClose`.

Respects `prefers-reduced-motion` (§2.6/§9): the transform is skipped entirely rather than run at `0ms`, since an instant snap-to-position is a worse experience than no zoom at all.

### 2.4 Gesture engine

**Implemented** (`src/gestures/GestureEngine.ts`, wired into `Gallery.ts`). One Pointer-Events-based engine feeding all consumers (core drag, the zoom plugin, vertical-swipe close):

- swipe/drag horizontal → navigate — **core-driven**, calls `next()`/`prev()` directly. Suspended entirely while `Gallery.registerZoomGate()`'s registered predicate returns `true` (§4.6) — the zoom plugin owns pan instead, via its own separate pointer listeners.
- vertical swipe/drag → close (with opacity/scale feedback) — **core-driven**, calls `close()` directly. Also suspended while zoomed, same gate.
- pinch, double-tap, wheel+ctrl → **relayed only**, no built-in effect *in core* — core emits `pinchStart`/`pinchMove`/`pinchEnd`/`doubleTap`/`wheelZoom` on the gallery event bus (§2.2); the zoom plugin (§4.6) is what actually consumes them. `tap` is relayed too, with no consumer yet.
- All thresholds/velocities configurable via `new Shoji(el, { gestures: {...} })`; passive listeners except `pointermove` once a horizontal drag direction has locked (stops the browser's own scroll/back-gesture from fighting the drag) and `wheel` with `ctrlKey` (stops the browser zooming the whole page instead).

Gesture state machine: `idle → pending(dir?) → dragging(h|v) → idle`. No literal blocking `settling` state — `onDragEnd` reports the outcome synchronously and the *caller* (`Gallery.ts`) owns however long its own snap-back/completion animation takes; a new `pointerdown` before that finishes is allowed to interrupt it (matches real touch-carousel UX — grabbing a still-settling slide feels responsive, not broken). Direction lock decided after `lockThreshold` px past the *original* pointerdown; every reported `delta` thereafter is measured from that lock point, not from the pointerdown itself (`onDragStart`'s own delta is always 0). Defaults, tuned for a slide to count as "swiped" without feeling sticky or trigger-happy: `lockThreshold: 10` px, `swipeThreshold: 50` px (distance) *or* `swipeVelocity: 0.3` px/ms (whichever fires first — a fast flick under 50px still navigates). `momentumEasing` (spec default `cubic-bezier(0.2, 0, 0, 1)`) is **not** a `GestureEngineOptions` field — it's the CSS custom property `--shoji-momentum-easing`, consistent with CLAUDE.md's "no hardcoded sizes/timings in JS, everything through `--shoji-*` custom properties"; the engine itself has no opinion on animation, only on when a drag started/moved/ended.

**Horizontal drag mechanics** (`Gallery.ts`): `onDragMove` calls `SlideManager.setDragOffset(px, transition)`, which adds `px` on top of every pooled slot's structural `offset*100%` position (`translateX(calc(${offset*100}% + ${px}px))`) — the whole pool slides together, 1:1 with the pointer, with zero extra DOM/re-render mid-drag (the adjacent slot, already preloaded per §2.3, is what's sliding into view). On release: not completed (or blocked by `loop:false` at an end item) → animates back to `px:0` with `--shoji-momentum-easing`. Completed → animates to a full `±dialog-width` offset, then — in the same synchronous tick, no transition — resets `px` to `0` *and* calls `next()`/`prev()`, which reassigns slot content by structural offset (§2.3); since the slot that just animated into the center position already holds the "new current" item's content (preload kept it rendered), the reset-plus-content-swap is visually seamless, the same instant-jump FLIP trick `zoomTransition.ts` (§2.3b) uses elsewhere, just on a different property/element pairing (`waitForTransitionEnd`, exported from `zoomTransition.ts`, is shared by both).

**Vertical drag mechanics**: `onDragMove` applies live `translateY(delta) scale(1 − progress×0.15)` + `opacity: 1 − progress×0.6` to `.shoji-slides` (`progress` ramps 0→1 over the first 160px of drag — independent of `swipeThreshold`, which is what actually decides completion). Release: not completed → eases the feedback back to neutral. Completed → `GestureController.takeFrozenDragTransform()` reads that same translateY (the raw, unclamped delta — see §2.6a's seventh real bug for why an earlier clamped version was itself a bug)/scale/opacity, instantly resets `.shoji-slides` to neutral, and hands the values to `closeFromSwipe()` → `zoomOut()`'s own `dragStart` (`zoomTransition.ts`), which jumps the photo itself there before transitioning to the thumbnail — one continuous motion on one element, picking up exactly where the drag left off, however far that is. See §2.6a's second through eighth real bugs for the fuller history, including three now-superseded intermediate designs.

**Applied to `.shoji-slides`, not `.shoji-dialog`** — requested directly: the toolbar/nav/counter/caption are siblings of `.shoji-slides` inside `.shoji-dialog` (§2.6a), not descendants of it, so this transform/opacity never touches them at all. Only the photo moves/shrinks/fades as it's dragged; the overlay stays anchored in its fixed screen position throughout — a stationary frame the image is pulled out from under, rather than the whole lightbox translating as one rigid unit (the original behavior, before this was requested). `zoomOut()`'s own continuation (§2.6a's second real bug) is unaffected either way — it measures the active media element's real `getBoundingClientRect()`, which already reflects whichever ancestor's transform is currently in effect, regardless of which one that is.

**Live controls-hide cue past the same distance a release would complete the close** — requested directly: dragging past `swipeThreshold` (the actual completion distance, not the separate 160px `VERTICAL_FEEDBACK_DISTANCE` the dim above ramps over) hides the toolbar/nav/counter/caption entirely, not just dims them — a "let go now and this closes" signal distinct from the image's own continuous dim, which never fully disappears (capped at 0.4 opacity). Fully reversible mid-gesture, tracked only on an actual threshold crossing (not every move): dragging back under it before release reveals them again, exactly as if the threshold was never crossed. `GestureController` reuses `Gallery`'s existing controls-hide plumbing (`forceHideControls()`/`showControls()`, §2.6a) via a new host method, `setControlsHiddenForDrag(hidden)` — hiding bypasses the hover guard the same way a deliberate close already does; revealing checks `controlsHiddenAtGestureStart` first, so retreating under the threshold doesn't resurrect controls that were already, separately hidden (idle auto-hide, or `autoHideDelay: 0`) before this particular gesture ever began. `setControlsHiddenForDrag()` also emits `dragCloseThreshold: { hidden }` on the event bus, unconditionally on every crossing regardless of the `controlsHiddenAtGestureStart` guard above — a plugin (Autoplay, §4.1) needs to know about the crossing itself, not just whether the toolbar happened to visibly move.

  **A real bug, found immediately after shipping this: the live cue fought itself, hiding then instantly re-showing on the very next pointermove.** `Gallery`'s own separate `pointermove` listener (`onActivity`, §2.8 — "any interaction reveals auto-hidden controls") is wired to the same continuous move stream a drag produces, and doesn't know a drag is deliberately managing visibility itself right now — every single frame past the threshold, it dutifully called `showControls()` immediately after `setControlsHiddenForDrag(true)` had just hidden them, in the same event dispatch. The exact same class of conflict as `isClosing`'s own fix above, just for a different activity-suppression window. Fixed with a new flag, `controlsHiddenByDrag`, set alongside the class toggle in `setControlsHiddenForDrag()` itself and checked by `onActivity()` right next to `isClosing` — reset on `finishClose()` (for the next `open()`) same as `autoHidden`/`hoveredControlCount` already are. Covered by unit tests (`tests/unit/gallery-gestures.test.ts`) confirming the class toggles on crossing, reverses on retreat, respects a pre-existing `autoHideDelay: 0` hidden state, and honors a custom `gestures.swipeThreshold`; and an e2e test (`tests/e2e/core-drag-gesture.spec.ts`) confirming a real mouse drag's effect on the toolbar's actual computed opacity, both directions.

**`ignore()`**: a pointerdown whose `composedPath()` includes a `button`, `video`, `input`, `select`, `textarea`, `a[href]`, or an element carrying `data-shoji-no-drag` is never tracked as a gesture at all — real controls keep their native click/touch behavior untouched, and `data-shoji-no-drag` is an explicit host/plugin escape hatch (CLAUDE.md's `data-shoji-*` prefix). The engine attaches to `.shoji-dialog` (not just `.shoji-slides`), so vertical swipe-to-close works from anywhere in the dialog, not only over the image; `.shoji-dialog` also sets `touch-action: none` so touch browsers don't intercept the same gesture for native scroll/pull-to-refresh before JS ever sees it.

Two real bugs were caught building this (both fixed, both covered by regression tests in `tests/unit/GestureEngine.test.ts`): (1) `finishPointer` originally read `state.lastX/lastY/lastTime` — fields only ever updated by `onPointerMove` — when computing a released drag's total delta/velocity/tap-position, silently ignoring the `pointerup`/`pointercancel` event's own coordinates; a release that didn't land exactly on the last recorded move (no intervening move at all, or a coalesced/throttled one) reported a stale position. Fixed by updating those fields from the terminating event itself before computing anything. (2) `lastTapTime`/`lastTapX`/`lastTapY` defaulted to `0`/`0`/`0` as a "no previous tap yet" sentinel — but `event.timeStamp` is time-since-navigation-start, so a tap within the first 300ms of the page's life, near the viewport's top-left corner, would satisfy the double-tap distance/timing check against that phantom "first tap at t=0" and be wrongly reported as a double-tap. Fixed by seeding `lastTapTime = -Infinity` instead, which can never be within `DOUBLE_TAP_MAX_DELAY_MS` of any real timestamp.

**A third, more severe real bug, found while building the zoom plugin's pan feature**: `onPointerDown` used to call `this.target.setPointerCapture(event.pointerId)` unconditionally, on every single pointerdown — including a plain tap/click that never becomes a drag at all. Chromium computes the *target* of the synthesized `mousedown`/`mouseup`/`click` compatibility events using whatever pointer-capture state is already in effect once `pointerdown`'s own synchronous handlers have finished running — so capturing that early silently retargeted every click inside the dialog to the capturing element (`.shoji-dialog`) itself, regardless of what was actually under the cursor. `Gallery.ts`'s click-outside-to-close (`isBackdropClick`, §2.6a) relies on the click's real target/`composedPath()` to tell "clicked the photo" from "clicked the background" — with every click retargeted to the dialog, it could never see `.shoji-slide-img` (or any control) in the path, and treated *every* click, including one dead-center on the photo, as a backdrop click: **a single click on the image closed the lightbox.** Confirmed via a real-browser reproduction with zero zoom-plugin involvement at all (a fresh page, `Shoji.Layout` only) — this was a pre-existing, general bug, not something the zoom plugin introduced, just one its pan feature's own testing happened to surface. Fixed by deferring `setPointerCapture` to the moment `direction` actually locks (inside `onPointerMove`, once past `lockThreshold`) rather than on `pointerdown` — plain taps/clicks are never captured at all and keep their real target, so this closed the single-click case. (A *confirmed* drag still captures, and — see the fifth bug below — still has its own, separate click-retargeting problem to solve.)

**A fourth real bug, same investigation**: `<img>` elements are natively draggable in every browser (press, drag, and the browser starts its own "drag this image out" operation — e.g. to save it elsewhere). With the active slide's `<img>` left at its default `draggable` value, a real drag gesture — navigate, vertical-close, or the zoom plugin's pan — could lose the race to the browser's own native-drag recognition, which fires `pointercancel` and hands the interaction off to `dragstart`/`drag` instead: from the viewer's side, the gesture appeared to move once and then stop dead, since no further pointer events for that pointer ever reach `GestureEngine` again after the cancel. Fixed in `SlideManager.renderImage()`: `img.draggable = false`, so Pointer Events own the gesture unconditionally.

**A fifth real bug, reported from real usage: completing a horizontal mouse drag-to-navigate closed the gallery immediately afterward, instead of just moving to the next/previous slide — desktop mouse only, not touch.** The third bug above fixed the *pointerdown*-time capture, but a *confirmed* drag (direction locked, `setPointerCapture` called as designed) still needs capture — without it, native scroll/back-gesture fights the drag. The bug is what happens on *release*: a captured pointer's `pointerup` still fires a real, ordinary browser `click` afterward, and that click is targeted at the capturing element (`.shoji-dialog`) regardless of where the pointer visually ends up — confirmed directly, instrumenting a document-level capture-phase click listener through a real mouse drag and observing `target`/`composedPath()` rooted at `.shoji-dialog`, not the photo. `Gallery.ts`'s `isBackdropClick` read that retargeted click the same way it read the third bug's retargeted clicks — "landed on nothing recognizable" — and closed the gallery right after every completed drag. (The pre-fix code here previously assumed, incorrectly, that a confirmed drag never fires a native `click` at all; it does, whenever the pointer was captured.) Fixed in `GestureEngine.ts`: track `capturedThisGesture` (true only when a real capture happened this gesture, reset per-pointerdown and again once the gesture ends), and on drag end, if it's set, call a new `suppressRetargetedClick()` — adds a capture-phase `click` listener on `target` that calls `stopPropagation()` and removes itself on the very next click, with a 500ms fallback removal in case a captured release doesn't produce one (platform/input dependent), so the listener can never linger and wrongly swallow a later, unrelated real click. An ordinary tap/click (never captured, per the third bug's fix) is completely unaffected. Covered by unit tests (`tests/unit/GestureEngine.test.ts`, synthetic events — jsdom doesn't synthesize a real post-capture click the way a browser does) and e2e tests (`tests/e2e/core-drag-gesture.spec.ts`, a real Chromium mouse drag) confirming: a horizontal drag navigates and leaves the gallery open; a vertical drag still closes it (the fix suppresses one click, not click-outside-to-close itself); a plain click with no drag at all is unaffected.

**A sixth real bug, found auditing this area for other mouse-specific parity drifts after the fifth**: `.shoji-caption` wasn't in `INTERACTIVE_CONTROL_SELECTOR` (`GestureController.ts`), the shared "starting a pointerdown here shouldn't be captured as a gesture" list — so a mouse click-drag meant to select/copy caption text got tracked as a navigate/close drag instead, and the locked-direction `pointermove`'s `preventDefault()` broke the browser's native text selection along with it. (Right-click-drag and middle-click-drag on the image itself were checked in the same pass and found *not* to be a problem — real browsers already stop tracking the gesture once a context menu opens or a non-primary button is involved, confirmed directly.) Confirmed the caption bug directly: the same drag technique selects real text on a plain `<p>`, but inside `.shoji-caption` it selected almost nothing. Fixed by adding `.shoji-caption` to `INTERACTIVE_CONTROL_SELECTOR` — which also let `Gallery.ts`'s `isBackdropClick` drop its own separate, now-redundant explicit `.shoji-caption` term (it already pulls the constant in), and the zoom plugin's own duplicated exclusion list (`isRealControl`, §4.6 — pan shouldn't hijack caption-text selection either, same reasoning) picked up the same addition. Covered by an e2e test (`tests/e2e/core-drag-gesture.spec.ts`) confirming a mouse drag over caption text selects it and neither navigates nor closes the gallery; skipped on touch/mobile-emulated projects, where text selection is a long-press gesture, not a plain drag, and so is genuinely out of scope rather than untested.

### 2.5 Transitions

**Implemented** (`src/transitions/`, wired into `Gallery.ts` via `navigate()`). Hardware-accelerated CSS3 (`transform`/`opacity` only) — 21 built-in presets (`src/transitions/presets.ts`) generated from a small config→transform DSL rather than hand-written, including the four called out by name: `slide` (default `mode`), `fade`, `zoom`, `deck` (`lg-style deck`). The rest: `slideVertical`, `push`, `fadeUp`/`fadeDown`/`fadeLeft`/`fadeRight`, `zoomOut`, `scaleUp`/`scaleDown`, `rotate`/`rotateLeft`/`rotateRight`, `flipX`/`flipY`, `cube`, `coverflow`, `drop`.

```ts
new Shoji(el, { mode: 'shoji-flip' });
```

**Only affects programmatic navigation** — buttons, keyboard, autoplay, `goTo()`/`next()`/`prev()`. A gesture-completed swipe (§2.4) always plays its own live-drag/settle animation regardless of `mode`; layering a discrete "jump" transition on top of a continuous finger-tracked drag would visibly fight the direct-manipulation feel mid-release. `Gallery.navigate(target, direction, animate)` is the shared path behind all three public navigation methods; `GestureController`'s host callbacks call it with `animate: false` so a completed swipe's own animation is the only one that plays. `goTo()` also accepts `{ animate: false }` directly, for a host that wants an instant jump (e.g. syncing to an external index with no visual flourish).

**Mechanism** (`SlideTransition.ts`): a "ghost" — a clone of the outgoing `.shoji-slide-media` — is absolutely positioned over the real slot and plays the preset's `leave` keyframe while the real content swap (`SlideManager.render()`) runs invisibly underneath it (the ghost fully covers the real slot during the swap, so the reassignment is never visible mid-flight). The newly-swapped-in real active media then plays the preset's `enter` keyframe. Both animate concurrently via the same instant-jump-then-transition FLIP technique `zoomTransition.ts` already established (`zoomIn`'s shape for enter, `zoomOut`'s for leave) — `--shoji-duration`/`--shoji-easing`, no separate speed option. `prefers-reduced-motion` skips the ghost entirely (content swaps instantly). Known, accepted limitation: if the incoming slide is outside the preloaded window (`goTo()` jumping far, or `preload: 0`), its image may not have decoded yet at the moment `enter` would apply, and pops in un-animated once it does — the overwhelmingly common case (single-step `next()`/`prev()` within the default `preload: 1` window) always has the adjacent slide already decoded, so this only affects large jumps, which isn't worth extra machinery for (CLAUDE.md: don't build for the uncommon case ahead of a real need).

**Custom animation = a CSS class pair, no JS needed.** A `mode` string that doesn't match a built-in preset name is treated as custom: Shoji adds `shoji-transition-<mode>-leave` to the ghost and `shoji-transition-<mode>-enter` to the incoming slide (plus `data-shoji-direction="next"|"prev"` on both, for a host whose animation cares which way navigation went), and waits for either `transitionend` or `animationend` (whichever the host's own CSS declares) before cleaning up — "no JS needed" means Shoji can't assume which mechanism the host used, so both are handled.

**`transitionDuration` (`GalleryOptions`, ms, default `300` — matching `--shoji-duration`'s own CSS default).** Doesn't move timing into JS despite CLAUDE.md's "no hardcoded colors/sizes/timings in JS" rule — it's a convenience that sets `--shoji-duration` for you (`Gallery.ts`'s `ensureLightbox()`, only when explicitly provided, same pattern `backdropOpacity` already uses for `--shoji-backdrop-opacity`), not a second, JS-side timing mechanism running alongside the CSS one. Unset leaves `--shoji-duration` (and its own `prefers-reduced-motion` override, above) untouched, so a host already theming it directly in CSS is unaffected.

**The caption fades alongside the mode transition, requested directly after the transition system itself shipped** — a navigated-to caption used to swap its text instantly, mid-flight, while the photo around it was still visibly animating, reading as a jump-cut against the smooth slide. Two rounds of refinement, both from real feedback on the first attempt:

1. First version: fade the outgoing caption out over a full `--shoji-duration`, hooked to the mode animation's own completion event (`SlideTransition.animate()`/`animateCustom()` given an `onComplete` callback) to swap content and start a *second* full-duration fade-in. Feedback: the fade-in showed up late — by definition, a fade that only *starts* once something else finishes hasn't *finished* along with it; the caption was still visibly catching up a beat after the photo had already settled.
2. Reworked to fit the caption's whole disappear-then-reappear cycle inside the *same* `--shoji-duration` window the mode animation itself runs in, not a separate one after it: `transitionCaption()` (`Gallery.ts`) self-times off the resolved duration (read via `getComputedStyle(caption).transitionDuration`, same read `zoomTransition.ts`/`SlideTransition.ts` already use, not `getPropertyValue('--shoji-duration')` directly — the latter isn't covered by either existing test file's `getComputedStyle` mock and would throw) — fades out over the first half (a temporary inline `transitionDuration` override), swaps content invisibly at the exact midpoint, fades back in over the second half, then clears the override. No hook into the mode animation's own completion event at all: both are independently driven by the same `--shoji-duration` value, so they finish together without needing to be wired to each other.

The very first `open()` gets the same treatment, fading in (not the disappear half — nothing outgoing to hide) alongside `zoomIn()`, over the *full* duration since there's no fade-out sharing the window with it. Gated on the exact same `origin && naturalSize` condition `zoomIn()` itself already gates on (this section, above/§2.3) — the same "no second, disconnected transition" reasoning: nothing grows in from the thumbnail without known dimensions, so nothing should fade in disconnected from that either.

A real race, caught before shipping: `SlideManager.render()`'s loaded callback (an async `img.decode()`, resolving on a microtask) also calls the same caption-update function, and for an already-preloaded slide can win the race against the fade's own self-timed midpoint — updating the caption's text *before* it's actually hidden would show the *new* slide's caption fading, not the outgoing one's. `captionFadePending` (a `Gallery` field, not a local closure variable — the async callback needs to read state set by a different, earlier call) gates both call sites, not just the synchronous one.

Both a completed swipe (§2.4) and `{ animate: false }` are unaffected — same scoping the mode transition itself already has, `animate && this.transition` gates the whole thing. `prefers-reduced-motion` skips it entirely (checked directly, not inferred from a resolved `0ms` duration, so `captionFadePending` never gets set needlessly).

**`mobileSettings`, removed.** A small `{ mode?, controls? }` override, keyed off `(pointer: coarse)`, once lived here: `mode` swapped the transition on a touch device, `controls: false` started controls hidden there (reusing §2.8's own auto-hide mechanism rather than a separate permanent-hide state, specifically so a touch viewer could never be stranded unable to reach Close). Removed on review — neither field's own motivation held up: `mode` only ever affects *programmatic* navigation (buttons, autoplay, `goTo()`), since a gesture-completed swipe always plays its own live-drag animation regardless of `mode` either way, making it a real override for an already-narrow case with no evidence any host needed it; `controls` only ever affected the very first moment of `open()` (not persisted per-slide), reading more as an odd "start collapsed" quirk than a considered feature once examined directly. Neither had a validated use case behind it — see CLAUDE.md's don't-build-speculatively principle. A width-driven toolbar-overflow mechanism (not device-type-gated, since a busy toolbar wrapping is a viewport-width problem, not a touch-vs-mouse one) was discussed as a possible, better-motivated replacement for the `controls` half specifically — since built, as the toolbar overflow popover, §3.1a.

**A real bug, reported from real usage: rotating or flipping a photo, then navigating to the next slide, visibly snapped back to unrotated *before* the slide transition played, instead of the un-rotate/un-flip happening as part of the transition itself.** RotateFlip (§4.5) and Zoom (§4.6) each reset their own transform unanimated on `beforeSlide` — necessarily, since `SlideManager.render()` reparents the outgoing node synchronously right after, and there's no code path afterward that can still find that specific node to reset. But `SlideTransition`'s own ghost is cloned from the outgoing `.shoji-slide-media` *after* that reset already ran, so the clone it plays the `leave` keyframe on was already back at neutral — the actual un-rotate/un-flip had already happened, invisibly, a tick earlier, with no animation attached to it at all. The photo would sit rotated for the whole time leading up to the click and then, the instant navigation started, jump to unrotated before the leave transition even had anything rotated left to animate away.

**`Gallery.registerSlideLeaveDecorator(decorator: (clonedMedia: HTMLElement) => (() => void) | void): () => void`** — a new public core method, multi-slot (`Set`, unlike `registerZoomGate`/`registerZoomStartProvider`'s single mutable slot above: more than one plugin can have a per-slide visual override active on the same slide at once, and each targets a different part of the clone — RotateFlip the wrapper itself, Zoom a descendant `<img>` — so they don't conflict). `SlideTransition.run()` calls every registered decorator once per navigation, immediately after cloning the outgoing media into the leave-ghost but *before* `swapContent()` runs — each decorator can freeze whatever value it's about to reset (read live off the real element, which is still intact at that point) onto the clone instead, and optionally return a `() => void` "settle" callback. Every returned settle callback runs together, right after the transition's own `kickOff` — so the ghost starts frozen at the pre-reset (rotated/flipped) state and eases back to neutral concurrently with the incoming slide's own leave/enter animation, instead of the two states ever being visible as a hard cut. Both RotateFlip and Zoom register a decorator: `beforeSlide` now captures the live `transform`/`transformOrigin` into a small `pending*` field *before* calling `reset()` (reset itself is unchanged, still synchronous and unanimated — only the leave-ghost's own copy is different), and the registered decorator applies that captured value to the clone, returning a settle callback that eases the clone's own transform back to `none`/neutral over `--shoji-duration`.

**Doesn't cover a gesture-completed swipe** — `GestureController`'s drag-to-navigate calls `navigate(..., animate: false)` on release, bypassing `SlideTransition` (and therefore this mechanism) entirely, same as `mode` (this section, above) already doesn't affect a swipe's own live-drag animation. A rotated/flipped photo dismissed via swipe still resets un-animated, just without a leave-ghost to animate on top of in the first place — not fixed here; revisit if a real report asks for it specifically.

### 2.6 Accessibility (core, non-optional)

- Dialog semantics: `role="dialog"`, `aria-modal`, labelled by caption/counter.
- Focus trap on open; focus restore on close; `Escape` closes; arrows (or `a`/`d`, either letter case) navigate; `Home/End` jump; `Tab` cycles toolbar. Focus restore (`FocusTrap.deactivate()`) passes `{ preventScroll: true }` to that `focus()` call — a real bug: a bare `focus()` auto-scrolls the target into view within any scrollable ancestor by default, and the restored element (`previouslyFocused`) is captured once at `activate()` time and never updated afterward, so restoring it on close could drag a host's own scrollable thumbnail strip (e.g. `ActiveThumbnail`, §4.2) all the way back to wherever the gallery was originally opened from — undoing whatever it had legitimately scrolled to since, via a focus restoration that has nothing to do with it. Reported as "ActiveThumbnail loses track of the active slide," but only actually observable once real navigation had scrolled the strip away from its starting position (small photo counts never trigger it — nothing to scroll back from).
- Live region announces "Image 12 of 480: {alt}".
- All toolbar buttons real `<button>`s with labels; visible focus rings via `--shoji-focus-ring`.
- Reduced-motion: honors `prefers-reduced-motion` (fades instead of slides).

### 2.6a Baseline controls (core, non-opt-in)

Everything in §2.6 is keyboard-usable from the moment the dialog opens, but keyboard alone isn't mouse/touch-usable — these three exist so it is, without requiring any plugin:

- **Close button** — top-right, real `<button aria-label>` (not an icon-only div), always present. Hidden entirely (not just inert — a real `hidden` attribute, with a matching `.shoji-close[hidden] { display: none; }` CSS rule, since the button's own base `display: flex` would otherwise outrank the native `[hidden]` UA style, same as `.shoji-nav`/`.shoji-counter`/`.shoji-caption` already needed) when `closable: false`.
- **Prev/Next buttons** — fixed to the screen edges (not the image edges — a narrow portrait image still gets full-width-positioned arrows), vertically centered. Hidden entirely when there's only one item total. With the default `loop: true` (below), never disabled at the ends — Next past the last item wraps to the first and vice versa. With `loop: false`, disabled (not hidden, so the layout doesn't shift) at the first/last item instead.
- **`closable: boolean`** (default `true`) — `false` disables every viewer-facing way to close the lightbox at once: the close button (hidden), click-outside-to-close, `Escape`, and vertical swipe-to-close (suspended entirely — no live drag feedback either, not just a release that fails to close). For a gallery meant to stay open permanently once shown (a non-closable embed). `gallery.close()` itself is never gated — only these four built-in viewer-triggered paths — so host code can still close it programmatically at any time. Implemented as one `this.closable` check inline at each of the four call sites (`onOuterClick`, the `Escape` case in `onKeydown`, and a `canClose()` host method `GestureController` consults both before showing vertical-drag feedback and before completing a swipe-close) rather than a single shared gate, since the close button's own gating (hiding it) is structurally different from the other three (they stay wired, just conditionally no-op) — no single chokepoint all four could share cheaply. `gallery.reinit()` with a different `closable` value updates the button's `hidden` state and all four paths' behavior correctly, same as any other option.
- **`backdropOpacity: number`** (default unset) — a 0-1 value, clamped, requested directly: a host wanting a JS option for backdrop transparency rather than having to know/override the full `--shoji-color-backdrop` value in CSS. Sets `--shoji-backdrop-opacity` (`shoji.css`) as an inline style on that instance's own `.shoji-outer`, only when the option is given — `.shoji-backdrop { opacity: var(--shoji-backdrop-opacity) }`. Left unset, nothing is touched, so a host already theming `--shoji-backdrop-opacity` directly in CSS is unaffected either way.
  - **A real bug, caught by the person who requested this feature, immediately after it shipped: `backdropOpacity: 1` didn't look fully opaque — the backdrop stayed at its pre-existing ~92% look.** The first implementation set `--shoji-backdrop-opacity` as a second, *multiplicative* `opacity` layered on top of `--shoji-color-backdrop`'s own baked-in alpha (`rgba(0, 0, 0, 0.92)`) — so `1` meant "unchanged from whatever the color's alpha already was," never true 100% opaque; `0.92 × 1 = 0.92`, not `1`. Fixed by splitting the two concerns apart at the default-theme level: `--shoji-color-backdrop` is now a fully opaque hue (`#000000` dark / `#ffffff` light), and the *real* alpha moved entirely into `--shoji-backdrop-opacity`'s own default. `backdropOpacity: 1` now composites to genuinely, fully opaque; `0` to fully transparent; every value between is a real, honest alpha. A custom theme supplying its own `rgba()`/gradient `--shoji-color-backdrop` still composites multiplicatively with `--shoji-backdrop-opacity` exactly as before (plain CSS `opacity` semantics) — this fix only changed the two *shipped default* theme's own color values, not the mechanism. Covered by `tests/e2e/core-backdrop-opacity.spec.ts` (real `getComputedStyle`, since jsdom unit tests can only assert the custom property string is set, not what it actually composites to on screen) confirming `1` reaches true `opacity: 1` with an `rgb(0, 0, 0)` background.
  - **`--shoji-backdrop-opacity`'s own default, requested directly, changed from `0.92` dark / `0.96` light to `1` for both** — the backdrop is now genuinely opaque out of the box, same as `backdropOpacity: 1` would produce; a host that wants the old translucent look sets `backdropOpacity` (or the custom property directly) itself.
- **Click-outside-to-close** — clicking anywhere that isn't the image, a button, a `<video>`, a provider-video container, or an overlay (counter/caption) closes the gallery (subject to `closable`, above). Implemented as target-exclusion on the whole dialog, not a literal listener on `.shoji-backdrop`: the backdrop element is directly behind the (transparently-boxed) dialog content and would essentially never itself receive a click, since the dialog's own transparent descendants cover the same area first in hit-testing order.
  - **Uses `event.composedPath()`, not `event.target.closest(...)`.** A real bug shipped once from the latter: clicking an icon-only button's inner `<svg>`/`<path>` makes *that descendant* the click's target, not the `<button>`; if the button's own click handler synchronously replaces its `innerHTML` (autoplay's play/pause icon swap, §4.1, is the case that surfaced this) before the event finishes bubbling, the original target is detached from the document by the time this outer-click listener runs — `.closest()` on a detached node finds no ancestors and misreads it as "clicked outside," closing the gallery mid-interaction. `composedPath()` is captured at dispatch time and is unaffected by DOM mutations that happen while the event is still bubbling. Only reproducible by clicking a *descendant* of a button whose handler swaps that descendant away — clicking the button itself doesn't trigger it, since the button element stays attached even after its children are replaced, which is why this went unnoticed until a real plugin (not just core's own close/prev/next, none of which mutate their own subtree on click) exercised the path. Regression test: `tests/unit/gallery-controls.test.ts`'s "a toolbar button that replaces its own icon... does not trigger a false backdrop-close."
  - **A real bug, reported from real usage, mobile-specific: tapping a YouTube slide to bring auto-hidden controls back closed the gallery instead.** A provider embed (§4.3) is a `<div class="shoji-slide-provider-video">` wrapping a cross-origin `<iframe>`, not a `<video>` element — it never matched the exclusion list the way a native HTML5 video slide already did. `.shoji-toolbar`'s own empty space is `pointer-events: none` (so it doesn't block the embed underneath it, §3.1), so a tap there — the one real "safe," non-iframe-swallowed spot to reveal auto-hidden controls (§2.8) on a provider-video slide — fell through to the provider-video container and read as a backdrop click, closing the gallery on the very tap meant to bring controls back. Desktop rarely surfaced this: hovering reveals controls without ever generating a `click`. On mobile every reveal attempt is a tap, and a tap is a click, so it was unavoidable there. Fixed by adding `.shoji-slide-provider-video` to the exclusion list, alongside `.shoji-slide-img`.
- **Page scroll lock** — `document.documentElement.style.overflow` is set to `'hidden'` for the duration the dialog is open, restoring the page's *actual prior* inline value (not just clearing it) on close, so a host that already had its own inline `overflow` set gets it back unchanged. Reference-counted at module scope (`src/core/bodyScrollLock.ts`), not per-`Gallery`, so if two `Gallery` instances are ever open at once, closing one doesn't prematurely unlock the page while the other is still open. `document.body`'s own `overflow` is deliberately left untouched — see the fourth real bug below for why.
  - **A real bug, reported from real usage, mobile only: rotating/flipping a photo on a narrow viewport grew the page itself wider, pushing the toolbar off-screen until the whole page was scrolled right to reach it.** `.shoji-outer` is `position: fixed; inset: 0`, exactly viewport-sized; `.shoji-slide-media` inside it (rotated/flipped by the RotateFlip plugin, §4.5) is `100%` of that box, so a 90° turn paints well outside it — worse mid-turn than at either endpoint, since a non-square rectangle's rotated axis-aligned bounding box is *widest* partway through the sweep, not at 0° or 90°. `.shoji-slides`' own `overflow: hidden` clips that paint correctly (confirmed directly — giving `.shoji-outer` itself an `overflow: hidden` too, still clipping paint fine, did **not** fix it either), but a mobile browser's decision to widen its own *layout* viewport past `width=device-width` doesn't consult what's clipped further down the tree — only `<html>`'s own `overflow-x`. Reproduced directly on an emulated narrow (390px) viewport: `window.innerWidth` itself grew to 543px after a rotate, confirmed via the same real page a fresh clone of this repo builds (`docs/examples/view-controls.html`) — and confirmed fixed only once `document.documentElement`'s (not just `document.body`'s) `overflow` is locked for the same duration, restored the same reference-counted way on close.

  **A second real bug, found immediately after shipping the first fix: locking `overflow-x` alone revealed a real scrollbar around the lightbox that hadn't been there before.** Per the CSS Overflow spec, mixing `overflow-x`/`overflow-y` values of `hidden` and `visible` on the same element isn't allowed — setting only `overflow-x` to `'hidden'` while `overflow-y` was still its default `'visible'` silently promotes `overflow-y` to `'auto'` instead. Confirmed directly: `getComputedStyle(document.documentElement).overflowY` read `'auto'` (not `'visible'`) immediately after the first fix's `lockBodyScroll()` ran, and `<html>`'s `scrollHeight` still genuinely exceeded its `clientHeight` even with `document.body`'s own `overflow: hidden` already set — so that newly-`'auto'` axis rendered a real, scrollable scrollbar around the fullscreen lightbox. Fixed by locking the full `overflow` shorthand (both axes) on `document.documentElement` instead of `overflow-x` alone, which avoids the mixed-value promotion entirely — confirmed via the same real-browser reproduction, before/after screenshots.

  **Not reliably reproducible against this repo's own internal e2e fixture page** (`demo/pages/e2e-plugins.html`) even at the exact same rotation angle on the exact same emulated viewport — the underlying mobile-browser heuristic for *when* to widen the layout viewport didn't trigger there for reasons that didn't resolve under investigation (page content/height was the only variable found to correlate, not confirmed as causal). No dedicated e2e regression test for the visible symptom as a result — same class of gap as the Zoom plugin's GPU tile-seam bugs (§4.6), verified by direct, real-browser reproduction with concrete before/after numbers rather than an automated assertion. `tests/unit/gallery.test.ts` covers the actual code change (the lock/restore mechanism itself) deterministically.

  **A third real bug, reported from real usage: on a host page with a real (classic, reserved-space — not macOS's default overlay) scrollbar, opening or closing the lightbox visibly shifted the page.** Locking `overflow` hides the scrollbar, which reclaims its own gutter and widens `<html>`'s content box by however many px it was; restoring it on close gives that width back. On a host page whose content genuinely spans the full viewport width, that width change reflows the page at the exact instant of open and of close. Not reproducible on this repo's own docs site (`docs/examples/*.html`) — its `body` is capped at `max-width: 1280px` and centered, already narrower than the viewport in both scrollbar states, so it never touched the reclaimed gutter either way; confirmed via direct pixel-diffing two frames straddling the transition (identical, cursor position aside) once the diagnosis correctly separated "no repro on this page" from "not a real bug."

  **A first attempted fix, briefly shipped and then reverted, made things worse:** measure the scrollbar's width (`window.innerWidth - document.documentElement.clientWidth`) and add it as `padding-right` on `document.body` while locked, removing it on unlock — the standard "compensate for the vanished scrollbar" technique. Wrong element: the width was measured on `<html>`, but the compensation landed on `<body>`, which on a page like this docs site (or any centered, `max-width`-capped layout) has its own content box already narrower than `<html>`'s — the scrollbar's reclaimed gutter never reached it in the first place, so the added padding wasn't compensating for anything; it just shrank body's own content width by an *extra* scrollbar-width's worth for the lock's duration, which is a new, self-inflicted reflow (confirmed directly: instrumenting both functions with real-browser console logging showed `document.body.getBoundingClientRect().top` never moved at all through the whole lock/unlock cycle, while `document.documentElement.scrollHeight` changed by exactly the added-padding's worth — the paragraph text was rewrapping by one line, shifting the thumbnail grid below it, not the page's actual top). Reverted in full once real-usage testing confirmed the shift hadn't gone away.

  **A second attempted fix, also briefly shipped and then reverted: `scrollbar-gutter: stable` on `document.documentElement`, toggled for the same duration as `overflow: hidden`.** Correctly targets the same element the width is measured on this time, and does genuinely stop the reflow — but real-usage testing immediately surfaced a different problem: Chrome renders `scrollbar-gutter: stable`'s reserved space with its own visible (if non-interactive, nothing to scroll under `overflow: hidden`) scrollbar-track styling, for as long as the lock is active. Trading a brief shift for a permanent scrollbar-shaped strip sitting over the page the entire time the lightbox is open reads as more visibly wrong, not less — confirmed directly from a real screenshot showing the track present with the lightbox open, absent with it closed. Reverted for the same reason as the first attempt: the fix didn't actually make things look right.

  **The actual fix: measure the scrollbar's width the same way, but compensate with `padding-right` on `document.documentElement` (not `document.body` — that was the first attempt's own bug) instead of `scrollbar-gutter`.** Padding is genuinely invisible blank space — no scrollbar-track styling, nothing for a browser to paint differently whether the lock is active or not — and applying it to the same element (`<html>`) the width was measured on means it compensates the box that actually owns the reclaimed gutter, unlike the first attempt's `document.body` mismatch. Only applied when a real scrollbar was actually measured (`scrollbarWidth > 0`); a page that never had one gets no padding at all, so there's nothing to accidentally reflow on a page that was never at risk in the first place. Scoped to the lock's own duration (set in `lockBodyScroll()`, restored to its prior value in `unlockBodyScroll()`) rather than added to the stylesheet permanently, so a host page's layout is completely unaffected while the lightbox is closed.

  **A fourth real bug, reported from real usage after the third bug's fix shipped: the page was still visibly shifting on close — this time provably vertically, and on this repo's own docs site too, which the third bug's fix couldn't touch (its `body` never reflows regardless of scrollbar state).** Root-caused via real-browser instrumentation (`getBoundingClientRect()`/`getComputedStyle()` logged at each step of a real close, not guessed): `document.body`'s own `getBoundingClientRect().top` never moved at all, but the page's first child (an `<h1>`) sat exactly `body`'s own `margin-top` *plus* the `<h1>`'s own default top margin below the viewport top while the lock was active, then snapped back up by exactly the `<h1>`'s margin the instant `unlockBodyScroll()` ran — reading as the page shifting upward right as the lightbox closes. The cause: `document.body.style.overflow = 'hidden'` (present since this lock's very first version, §2.6a above, entirely unrelated to the third bug's own scrollbar-width fix) makes `body` establish a new block-formatting context, and any value of `overflow` other than `visible` blocks top-margin collapsing between an element and its first child — normally `body`'s own top margin and its first child's top margin collapse into one shared gap; locked, they stack instead, pushing that first child down for exactly as long as the lock is active. Not a corner case: any page where body has no padding/border of its own (letting that collapse happen in the first place — true by default, and true of this docs site) shows it, regardless of scrollbar-width or `max-width` layout at all, which is why the third bug's fix never touched it. Fixed by no longer setting `document.body`'s own `overflow` at all — confirmed directly (both a real-browser wheel-scroll test and a `window.scrollTo()` test) that `document.documentElement`'s own `overflow: hidden` (already set, §2.6a above) is sufficient on its own to block user-driven scrolling, since `<html>` is the real scrolling element in standards mode; `body`'s lock was never adding independent protection, only this side effect. Covered by `tests/unit/gallery.test.ts`'s "page scroll lock" suite, including a regression test asserting `document.body.style.overflow` is never touched at all.

  **Four further gaps, identified in the course of reviewing this lock's own known limitations rather than reported from a specific real-usage bug, all fixed together and all covered by `tests/unit/bodyScrollLock.test.ts`:**

  1. **iOS Safari's touch-driven rubber-band/bounce scroll isn't reliably blocked by `overflow: hidden` alone** — a well-known limitation of this technique across the ecosystem, not specific to this implementation. The common workaround (flipping `body` to `position: fixed` while locked, capturing/restoring `scrollTop` manually) has its own well-documented tradeoffs — a full reflow, and manual scroll-position math that's a frequent source of bugs in other libraries using it, the same class of bug this lock has already had twice above. Fixed with a lighter mechanism instead: a non-passive `touchmove` listener on `document`, added only while locked, that calls `preventDefault()` for any touch whose target isn't inside a `.shoji-outer` — Shoji's own in-dialog gesture handling (`GestureEngine.ts`, which already manages its own `preventDefault`) is completely unaffected, since its targets are always inside one. No layout change, no scroll-position capture/restore, so none of the reflow-timing bug class above applies to it.
  2. **A plain `window.scrollTo()` (or setting `scrollTop` directly) isn't blocked by `overflow: hidden` at all** — confirmed directly. If the host's own code scrolls the window while the lightbox is open (a router restoring scroll position on navigation, an unrelated "scroll to top" button), the page ends up somewhere different than where the viewer left it once the lock releases — `overflow: hidden` only ever blocked user-driven scrolling, never programmatic. Fixed by capturing `window.scrollX`/`scrollY` at the moment the *first* `lockBodyScroll()` call locks (reference-counted the same way as everything else here — a still-nested lock doesn't re-capture), and unconditionally restoring them via `window.scrollTo({ left, top, behavior: 'instant' })` once the *last* `unlockBodyScroll()` call actually unlocks — regardless of what scrolled the page in between. `behavior: 'instant'` explicit, not left to default, so a host page with its own `scroll-behavior: smooth` CSS can't turn this restoration into a visible animated scroll.

     **A real regression this fix itself caused, found via a real integration (Layout + `groupBy` + ActiveThumbnail, same page as §4.2's own real bug): "regardless of what scrolled the page in between" above is exactly what it says — it made no exception for Shoji's *own* code. `ActiveThumbnail`'s `scrollIntoView` (§4.2) runs while this exact lock is active (the lightbox it's tracking is the same one holding the lock), so every navigation's scroll got unconditionally undone the instant the lightbox closed — the entire feature reduced to a no-op behind an opaque backdrop, on every host, not just this one, since the lock is core and always active whenever ActiveThumbnail's scroll would fire.** Fixed with `markIntentionalScroll()` (`bodyScrollLock.ts`), an escape hatch `ActiveThumbnail` calls right when it actually invokes `scrollIntoView`: once called during a lock session, `unlockBodyScroll()` skips the restore entirely for that session rather than try to track a smooth-scroll animation's eventual resting position (no reliable cross-browser completion signal to key that off of — `scrollend` isn't universal yet). Deliberately all-or-nothing per session, not per-pixel: unrelated code scrolling during the *same* session as a legitimate `markIntentionalScroll()` call won't get undone either, an accepted gap rather than a solvable one without knowing which of two scrolls in the same window was which. Covered by `tests/unit/bodyScrollLock.test.ts`.
  3. **The lock only defends against other `Gallery` instances (reference-counted), not unrelated code on the host page** — another modal/dropdown library that also sets `document.documentElement.style.overflow`, then clears it back to `''` on its own close, would silently undo this lock mid-lightbox, with neither library aware of the other; this lock has no way to distinguish "the last `Gallery` really did close" from "something else touched the same property." Mitigated (not fully solvable without knowing every other library's own behavior) with a `MutationObserver` on `document.documentElement`'s `style` attribute, active only while locked, that re-asserts `overflow: hidden` if it's ever found to be anything else. `MutationObserver.takeRecords()` immediately after its own corrective write discards the mutation record that write itself just queued — without it, the observer would react to its own correction and loop forever (mutation records are queued synchronously on the DOM change, but callback delivery is a microtask, so a simple "ignore my own writes" boolean flag reset synchronously right after writing doesn't actually cover the async callback that fires later for that same write — `takeRecords()` sidesteps the whole timing question by discarding the record outright rather than trying to time a flag around it).
  4. **The scrollbar-width compensation (`padding-right` on `<html>`, the third real bug's own fix above) assumes a right-side scrollbar — untested on a `direction: rtl` page, where a classic scrollbar renders on the left instead.** Compensating the wrong side would reintroduce the exact reflow that fix exists to prevent, just mirrored. Fixed by checking `getComputedStyle(document.documentElement).direction` at lock time and compensating `padding-left` instead of `padding-right` when it's `'rtl'` — restored symmetrically on unlock either way.
- **Counter/caption are overlays, not layout rows.** The caption is `position: absolute` over the image (opaque box, bottom-left, sized to its content rather than a full-width bar); the counter (pill badge) instead flows as a normal flex item inside `.shoji-toolbar-left` (§3.1) — sharing that slot's flex layout with any plugin button placed there (e.g. autoplay's play/pause) rather than independently overlapping it, which is what it did before a plugin ever actually used that slot. Either way `.shoji-slides` still gets the dialog's full height, no reserved gutter at top or bottom, since the toolbar itself is the thing overlaid on the slides, not pushing them down. `counter: boolean` (default `true`) toggles the counter badge's visibility; the live-region announcement (§2.6) is unaffected either way, since that's the non-optional a11y channel and this option is purely about the visible badge. The caption box hides itself automatically when the active item has no caption — no separate option, since there's nothing to toggle when it's already empty. It's also hidden for the entire window the active slide is still loading (the same `isActiveReady()` signal §2.3's loading-state feature already gates the toolbar buttons on) — the *new* caption text is written into the DOM immediately either way (so it's already correct the instant loading finishes, no separate text flash), only `hidden` waits; otherwise a caption describing a photo that hasn't actually appeared yet — still a spinner — would sit there readable underneath it.
- **`caption: string | HTMLElement | DangerousHtmlCaption` (§2.1).** A plain string renders as text (`textContent` — auto-escaped, safe by default). An `HTMLElement` is appended as real DOM, letting a host build rich (bold/links/etc.) captions without any string-parsing involved. `{ dangerouslySetInnerHTML: string }` is the explicit, deliberately-named opt-in for raw HTML via `innerHTML` — named identically to React's escape hatch of the same name on purpose, so it reads as dangerous on sight and can't be triggered by passing an ordinary string. Shoji does not sanitize that string; the host must, exactly as with React's version. This three-way split exists because a plain string alone wasn't enough in practice — hosts do want inline markup in captions — but silently treating *every* string as HTML would make every caption an XSS vector for data that plausibly comes from user-supplied photo metadata.
- **`locale`** (§ options) resolves these buttons' `aria-label`s (`close`/`previous`/`next`), falling back to English — the first real consumer of the previously-unused `locale` option, per CLAUDE.md's "no hardcoded English in UI."
- **Closing fades controls out and runs the zoom-out concurrently, both starting the instant close begins.** `Gallery.beginClose()`'s zoom-out branch (shared by `close()` and `closeFromSwipe()`, see the second real bug below) calls `forceHideControls()` — forces the same `.shoji-controls-hidden` fade §2.8's idle auto-hide already uses (bypassing `hideControls()`'s own `isControlActive()` hover guard — the single most common close path, clicking the close button, *is* hovering a control at that exact instant, and a deliberate close should hide regardless) — then calls `zoomOut()` immediately after, with no gating between them. Covered by unit tests (`tests/unit/gallery-zoom.test.ts`) confirming controls hide immediately and bypass the hover guard; and an e2e test (`tests/e2e/core-close-controls-fade.spec.ts`) confirming the real CSS actually produces it — the toolbar reaches `opacity: 0` while the dialog is still open, before the whole thing closes.

  **An intermediate design, kept only briefly: waiting for the fade's own `transitionend` before starting the zoom-out.** Requested directly at the time: previously `close()` ran the zoom-out-to-thumbnail animation (§2.3b) with the toolbar/nav/counter/caption still at full opacity for its whole duration, then vanished the entire dialog — chrome included — in one abrupt cut once it finished, reading as stationary UI hovering over a shrinking photo rather than one clean motion. The fix at the time made `close()` wait for the fade's own `transitionend` (`waitForTransitionEnd`, `zoomTransition.ts`, generalized to accept a `property` argument — `'opacity'` here, `'transform'` everywhere else it's used) before calling `zoomOut()`, sequencing "fade, then shrink." **Reversed on later, explicit feedback**, once that sequencing itself read as two distinct steps rather than one continuous motion (the same complaint the very first version drew, just with the two steps swapped) — replaced with the concurrent version above. `waitForTransitionEnd`'s `property` parameter remains — still used elsewhere with its `'transform'` default — but `LightboxDom`'s standalone `toolbar` reference (kept only to key that wait off of) was dead once the wait was removed, and has been deleted along with it.

  **A real bug, reported from real usage immediately after shipping: moving the mouse during the close sequence re-showed the just-hidden controls.** `onActivity()` (§2.8, wired to `pointermove`/`pointerdown`/`touchstart`/`wheel`/`focusin` on `.shoji-outer`) stays fully attached for the entire close sequence — it's only ever torn down in `teardown()` (`destroy()`/`reinit()`), not by a plain `close()` — so any of those events firing during the controls-fade wait called its own `showControls()`, undoing the fade mid-animation. Not mouse-specific: `onActivity` is the one shared handler for every input type it's wired to, `touchstart` included, so a touch tap/drag during close hit the exact same bug. Fixed by making `onActivity()` a no-op once `this.isClosing` — there's nothing left to reveal controls *for* once a close is actually underway. Covered by unit tests (mouse via a synthetic `pointermove`, touch via a synthetic `touchstart`, both dispatched mid-close, asserting `.shoji-controls-hidden` survives) and an e2e test (a real `page.mouse.move` sequence during a real close, asserting the toolbar's real computed opacity stays at `0`).

  **A second real bug, reported from real usage: a completed vertical swipe-to-close visibly popped the photo back to fully visible for a beat before the zoom-out-to-thumbnail animation took over, instead of one continuous fade/shrink.** `GestureController`'s vertical-drag feedback (live `translateY`/`scale`/`opacity` on `.shoji-dialog` while dragging, §2.4) used to reset itself *instantly* — no transition — the moment a completed drag released, before `close()` (or, at the time this was written, before either controls-fade step above existed at all) ever ran. That instant reset was the pop: the dialog snapped back to full opacity/scale/position for a frame, then the *separate* zoom-out animation started from scratch. Originally fixed by easing the drag feedback back to neutral (`clearVerticalDragFeedback(true)`) *concurrently* with the zoom-out instead of resetting it instantly — see the third real bug directly below for why that turned out to have its own, subtler cost, and the actual current fix. `Gallery.beginClose(waitForControlsFade)` is the shared logic behind both `close()` (`true` — sequences the controls fade *before* the zoom-out, per the entry above) and `closeFromSwipe()` (`false` — still force-hides controls via `forceHideControls()`, but doesn't block the zoom-out on that fade's `transitionend`, since a swipe already has its own closing motion in progress).

  **A third real bug, reported from real usage: a completed drag-close landed off the thumbnail — sometimes badly — unlike a button-close, which always lands exactly on it.** Two compounding causes, both in how the second bug's fix interacted with `zoomOut()`'s own landing math (`computeTransform`, `zoomTransition.ts`):
  1. **Two transforms animating at once.** `.shoji-slides`' drag transform easing back to neutral *concurrently* with `zoomOut()`'s own transition on `target` (a descendant) — `computeTransform()` measures `target`'s rect once, assuming a static starting box, but the parent kept moving underneath it as its own easing progressed, so the computed landing transform was chasing a target that had already moved by the time it finished. Fixed by leaving `.shoji-slides`' transform exactly where the drag left it for the *entire* close animation instead — `finishVerticalDrag()`'s completed branch no longer calls `clearVerticalDragFeedback()` at all — so `zoomOut()` is the only thing animating and its math holds against a static box. Reset only happens once the dialog is already hidden (`GestureController.resetDragFeedback()`, called from `Gallery.finishClose()`) — nothing left on screen to visibly snap.
  2. **A smaller, subtler residual error, found while verifying fix 1 above**: even fully static, the drag feedback's own *scale* term (`scale(1 − progress×0.15)`, capped at a 15% shrink) still distorted the landing *position* specifically — the final landed *size* matched a button-close exactly, but the position was off by tens of pixels. `computeTransform()` computes a screen-space translate delta for `target`'s own transform, but with a non-1-scale ancestor still in place, that same local translate value covers *less* on-screen distance once composited through the ancestor's shrunk coordinate system than the screen-space math assumed — a multiplicative distortion translation alone doesn't have (an ancestor's own *translate* composes additively with a descendant's, regardless of its value; only a non-1 *scale* distorts a descendant's translate this way). Originally fixed by dropping the scale term (keeping only `translateY`) the instant a drag completes and closes — see the fourth real bug directly below for why that itself had a visible cost, and the actual current fix.

  Covered by a unit test (`tests/unit/gallery-gestures.test.ts`) confirming `.shoji-slides`' transform/transition are left untouched (not eased, not cleared) through the whole zoomOut animation and only reset once it completes; and an e2e test (`tests/e2e/core-drag-gesture.spec.ts`) comparing a drag-close's real landed rect against a button-close's for the same item — not against the thumbnail's own rect directly, since `.shoji-slide-media` is usually larger than the photo actually rendered inside it (letterboxed), so the two aren't a fair one-to-one comparison; comparing two landings measured the same way sidesteps that entirely, and caught both bugs above in isolation while verifying the fix.

  **A fourth real bug, reported from real usage: the close animation looked different depending on where on the screen the drag started** — starting near a screen edge left a lot of room to drag before releasing, reading as unusually slow (a long way back to the thumbnail) or, dragged far enough, visibly cutting the photo off against the edge of the screen; starting midway produced a visible pop. Two distinct causes, both in the third bug's own fix above:
  1. **The frozen translate was completely unbounded** — exactly the raw distance the pointer physically traveled, which is bounded only by how much open screen space existed between the drag's start point and the edge of the window. Originally fixed by clamping it to the same 160px (`VERTICAL_FEEDBACK_DISTANCE`) the live dim/scale feedback already ramps over — see the seventh bug below for why that clamp was itself a real bug, and the actual current fix (no clamp at all).
  2. **Dropping the scale term instantly (fix 2's own fix, above) itself popped the photo back toward full size for a frame** before the real close animation took over — small (capped at 15%) but compounding with cause 1 above into a visible, described-as-a-jump correction. First fixed by keeping the scale term and having `zoomOut()` compensate for it mathematically — see the fifth bug directly below for why that turned out to have its own, subtler cost, and the actual current fix.

  **A fifth real bug, found immediately after shipping the fourth: the close animation now paused briefly at a partial size before visibly shrinking toward the thumbnail** — worse the smaller the drag, since a smaller drag left less of the frozen shrink already "spent." Root cause: fix 4.2 above split the close motion across *two* elements — the drag's shrink stayed frozen on `.shoji-slides` (the parent) for the whole close, while `zoomOut()`'s own transition ran independently on `target` (the child), easing in from a standing start. Right at release almost all the visible size came from the static parent alone, since the child's own eased transition hadn't picked up any speed yet — reading as "hold, then shrink" instead of one motion. Fixed by collapsing the two elements back into one: `GestureController.takeFrozenDragTransform()` reads the drag's last live translateY/scale/opacity (clamped per fix 4.1), instantly resets `.shoji-slides` to neutral, and returns those values instead of freezing them on it. `Gallery.closeFromSwipe()`/`beginClose()` thread them through as `zoomOut()`'s own `dragStart` parameter (`ZoomTransitionTarget.dragStart`, `zoomTransition.ts`) — `zoomOut()` measures `target`'s natural (untransformed) box for its landing math *first*, exactly as a button-close already does, then jumps `target` there instantly (the same FLIP technique `zoomIn()` already uses to jump onto origin's box before transitioning away from it, just jumping to wherever the drag left off instead of a fixed point) before starting its one real transition. Only one element ever animates, continuous from exactly where the drag left off — structurally, not just visually, since there's no longer a second transform anywhere to hand off from.

    **A sixth real bug, found while building the fifth's own fix**: measuring `target`'s box *before* baking `dragStart` onto it (order matters, and getting it backwards was the first attempt) put the ~403px landing error right back. `effectiveTargetBox()` prefers the real rendered child `<img>`'s own rect — a *descendant* of `target` — which, if `dragStart`'s scale is already applied to `target` when that measurement runs, is already shrunk by it. `zoomOut()` then wholesale *replaces* `target`'s transform (not composes with it), so that shrinkage doesn't carry through to the final result, but it still corrupted the *measurement* the landing math was based on — double-counting a scale that was about to be discarded. Fixed by measuring strictly before any `dragStart` jump happens, inside `zoomOut()` itself, which is also why the jump moved from `Gallery.beginClose()` into `zoomOut()` rather than staying a separate step run beforehand.

  **A seventh real bug, reported from real usage and confirmed on a screen recording: dragging far enough past the 160px clamp (the fourth bug's fix 4.1, above) made the photo visibly jump to a small, centered-looking position right at release, before the real shrink-to-thumbnail motion continued from there** — described as "it should zoom out from where the drag left off, not center itself first." Frame-by-frame video review pinned it down exactly: the photo was still at its fully-dragged, off-screen position one sampled frame, then at a position barely below neutral (matching the 160px clamp, not the actual ~800px+ the pointer had traveled) the very next. The clamp itself was the bug — it's an *instant* correction, not a smoothed one, so any drag past 160px caused a hard snap from the real dragged position back to the clamped one at the exact moment of release, before `zoomOut()`'s own transition ever started. Fixed by removing the clamp entirely: `takeFrozenDragTransform()`'s `translateY` is now the raw, unclamped `lastDragDelta` — the close animation continues from exactly where the drag left off, however far that is, full stop, accepting the fourth bug's original "reads as slow / can start near an edge" tradeoff as the cost of no recentering step, per explicit, repeated user direction. (Scale/opacity are unaffected — they were never clamped by this same mechanism, only ramped 0→1 over the same 160px, which is a different, unrelated cap that still applies.)

  **An eighth real bug, reported from real usage immediately after: crossing the close threshold hid the mouse cursor along with the toolbar/nav/counter/caption**, since the live controls-hide cue (§2.4 above) reuses `.shoji-controls-hidden` — the same class idle auto-hide uses, whose own CSS rule (§2.8) also sets `cursor: none`. That's correct for an idle/inactive hide, but backwards for an active drag: the pointer is moving, and losing the cursor mid-drag is disorienting, not clean. Fixed with a new, dedicated marker class, `.shoji-controls-hidden-for-drag`, toggled in `Gallery.setControlsHiddenForDrag()` alongside `.shoji-controls-hidden` itself and cleaned up in `finishClose()` (a completed drag-close never explicitly un-hides, so nothing else would clear it) — `shoji.css` overrides the cursor back to `auto` specifically when both classes are present, at the same specificity level as the existing `.shoji-cursor-visible` override (§2.8) for `autoHideDelay: 0`. Deliberately a *new* class rather than reusing `.shoji-cursor-visible` itself: that one is a permanent marker for `autoHideDelay: 0`, and toggling it on/off with the drag would incorrectly clear it once the drag ended even when that permanent mode was also active.

  Covered by unit tests (`tests/unit/gallery-gestures.test.ts`) confirming `.shoji-slides` resets to neutral instantly on a completed drag-close (nothing left on it to animate) while `target` is what's transitioning; that `dragStart.translateY` passes through as the raw, unclamped delta regardless of how far the drag went; that the scale term survives release unchanged as part of `dragStart` rather than being dropped; and that `.shoji-controls-hidden-for-drag` toggles with the threshold crossing/retreat and is cleaned up after a completed close. A unit test (`tests/unit/zoomTransition.test.ts`) confirms a baked-in `dragStart` opacity is cleaned up the same way transform/transition/transformOrigin already are. E2e tests (`tests/e2e/core-drag-gesture.spec.ts`) confirm a very large real drag still lands exactly where a button-close does (the sixth bug's own regression test — this is what actually caught the wrong measurement order) and that the position right after release matches the live-dragged position exactly, not a snapped/bounded one (the seventh bug's own regression test); an e2e test (`tests/e2e/core-autohide-cursor.spec.ts`) confirms the real computed `cursor` CSS value stays visible through a threshold crossing (the eighth bug's own regression test).

Deliberately **not** baseline: autoplay/slideshow, despite being closely related UX, stays a plugin per §4/§11 — it needs real state (timer, video-sync) that belongs behind the plugin loader (§3), not bolted into core ahead of that existing for real.

### 2.7 Instance registry, refresh & reinit

Every constructed gallery registers itself against its container element, so code that never held a closure reference — a `scroll` plugin data-source callback resolving long after the call site that opened the gallery is gone (§7), a separate `<script>`, devtools — can still reach the live instance:

```ts
Shoji.getInstance(el: HTMLElement): Gallery | undefined
Shoji.instances(): IterableIterator<Gallery>          // all live instances, e.g. page-wide teardown

gallery.refresh(): void                                // selector mode: rescan the DOM
gallery.reinit(options?: GalleryOptions): void          // full reset, same instance identity
```

- `getInstance`/`instances()`, `refresh()`, and `reinit()` are all implemented. Registration lives in two module-level structures kept in lockstep: a `WeakMap<HTMLElement, Gallery>` for O(1) `getInstance` lookup (never leaks, since the entry is only ever reachable through an element the host still holds), and a `Set<Gallery>` for `instances()` enumeration (WeakMaps aren't iterable). The constructor adds to both; `destroy()` removes from both, guarded (`if (registry.get(el) === this)`) rather than a plain delete — if a second `Gallery` was constructed on the same element without the first ever being destroyed, the registry entry already points at that newer instance, and a stale first instance being destroyed later must not evict it. `reinit()` touches neither — same instance, same registry entry, by design. The two registries stay paired and neither is optional to call directly, which is also what the destroy/leak tests (CLAUDE.md) assert.
- **`refresh()`** — selector-mode only (no-op with a dev warning in dynamic mode, where `updateSlides` is the direct equivalent). Rescans the DOM at `options.selector` and feeds the result through the exact same item-diffing `updateSlides()` already does internally — it's sugar over that path, not a second implementation. Use it when something *outside* Shoji added, removed, or reordered items in the DOM. Nothing is torn down: active slide, plugin state, gesture/transition state all survive, same as a normal `updateSlides()` call.
- **`reinit(options?)`** — **implemented** (`Gallery.ts`). Full teardown and reconstruction — internally, everything `destroy()` does, immediately followed by everything the constructor does (including re-running every plugin's `init()`), but on `this` rather than a new object, so the same `Gallery` reference callers already hold, and the same registry entry, stay valid across the call. Pass a full options object to reconfigure structurally (different `plugins`, different core settings, a new `selector`/`items`); omit it to rebuild with the current options unchanged, which is a hard reset (clears any live edit-mode state, GL contexts, drag/zoom state, etc. and re-establishes everything from scratch). Prefer `reinit()` over "`destroy()` then `new Shoji(...)`" whenever other code might be holding the instance — a closure, `Shoji.getInstance()`, a plugin's own reference — since that code keeps working across a `reinit()` instead of needing to be told about a new object. `destroy()` alone (no reinit) remains for when the gallery should go away for good: the container is being removed from the DOM, the page is navigating away from the gallery entirely, etc.
  - **Implementation**: the constructor and `reinit()` both funnel through a shared private `applyOptions(options)` (everything after `this.element` is resolved/registered — options-derived fields, item scanning/dynamic-mode setup, `ensureLightbox()`, `openOnInit`); `destroy()` and `reinit()` both funnel through a shared private `teardown()` (force-close if open, run plugin cleanups, tear down gesture/transition/slides/dialog) — `destroy()` additionally removes the registry entry and clears the event bus permanently, `reinit()` clears the bus (see below) but keeps the registry entry, then immediately calls `applyOptions()` again.
  - **Host-registered `gallery.on(...)` listeners do not survive `reinit()`** — the event bus is fully cleared, same as `destroy()`. A plugin's own subscriptions come back for free (its `init()` re-runs), but there's no way to distinguish a plugin's internal `ctx.on()` call from a host's own `gallery.on()` call after the fact, so both get cleared together; a host that needs listeners after `reinit()` must re-attach them.
  - Several previously-`readonly` fields (`options`, `selector`, `isDynamicMode`, `preload`, `locale`, `showCounter`, `loop`, `autoHideDelay`) became plain, reassignable fields to support this — `this.element` itself stays `readonly`, since neither `reinit()` nor anything else ever moves a `Gallery` to a different element.
- Primary motivating case for all of the above: `scroll` plugin host callbacks (`loadAfter`/`loadBefore`, §7) are async and may resolve well after the call site that constructed the gallery has gone out of scope. Rather than requiring the host to keep its own reference alive across every pending fetch, code anywhere — including that callback — can do `Shoji.getInstance(container)` to get back the live instance and call `updateSlides` (or its `addSlides`/`removeSlides` sugar, §2.1), `refresh`, `reinit`, or `destroy` on it, without the host threading a reference through.

### 2.8 Auto-hide (buttons + overlays)

Core option, not a plugin — it applies uniformly to every baseline control (§2.6a: close, prev/next, counter, caption) and, once the plugin loader exists, every `ctx.ui.toolbar()`-registered button too, regardless of which plugin registered it:

```ts
new Shoji(el, { autoHideDelay: 5000 })   // ms of inactivity before controls hide; default 5000
```

- **On by default, 5000ms.** This revises an earlier draft of this section that defaulted to off — reasoning at the time was "nothing hidden by accident" per CLAUDE.md's a11y stance, but on reflection that's satisfied by *how* it hides (opacity-only, never removed from the tab order, cancels immediately on any interaction, keyboard shortcuts unaffected regardless of visibility) rather than by *whether* it hides at all. Auto-hide-on-idle is a well-established pattern for media viewers precisely because it doesn't cost accessibility when implemented that way.
- **Three real states, `type: number | false`.** Any `N > 0` — normal auto-hide, hides after `N` ms idle, activity reveals again. `N === 0` — the *opposite* of what "0" suggests in most APIs: it does not disable auto-hide, it means controls are hidden immediately on open and stay hidden permanently, activity included. `false` — the actual "always visible" value, requested directly after the confusion around `0` came up in practice: the idle timer never arms at all (`scheduleAutoHide()`'s own early return), so nothing ever calls `hideControls()` from this mechanism, and controls simply stay however they already are (visible, by default). `autoHideDelay: Infinity` does *not* get you this — `setTimeout`'s delay is stored as a 32-bit signed int, so any value above ~2147483647ms (~24.8 days), `Infinity` included, gets clamped and fires almost immediately instead of never; `false` is a real, explicit sentinel checked before ever touching `setTimeout`, not a large delay value passed through to it.
- **`0` doesn't block other, unrelated hides; `false` does — for the public `hideControls()` specifically.** `0` only governs the idle timer (whether it ever arms, whether activity re-arms it) — a plugin calling `hideControls()` directly, and drag-to-close's own live threshold cue (§2.4), still work under `autoHideDelay: 0`, unaffected. `false` is stronger: `hideControls()` *itself* checks `this.autoHideDelay === false` and no-ops, so *every* caller of that public method respects "always visible," not just the timer — this includes any plugin, official or third-party, that calls it. `forceHideControls()`/`setControlsHiddenForDrag()` (private — close, drag-to-close) deliberately check neither value, under either `0` or `false`: those are direct, deliberate user actions with their own visual feedback, not an auto-hide convenience a host's "always visible" request should be able to suppress.
  - **A real bug, reported from real usage immediately after `autoHideDelay: false` shipped: `hideControls()` didn't actually check it, so any plugin calling it directly could still hide controls out from under an "always visible" host.** Concretely: the Autoplay plugin's own tap-to-toggle-chrome feature (§4.1 point 15 — since removed entirely, but real and shipped at the time) called `gallery.hideControls()` directly on a tap, with no `autoHideDelay` check of its own — since only `scheduleAutoHide()` (the idle timer) checked `false` at the time, this call went straight through regardless, defeating the host's explicit request the moment autoplay was enabled and the viewer tapped the image. Fixed by moving the check into `hideControls()` itself (above) rather than patching Autoplay specifically — the bug wasn't really "Autoplay doesn't know about `autoHideDelay`," it was "the public method any plugin calls doesn't enforce the contract its own name implies." Covered by unit tests in `tests/unit/gallery-autohide.test.ts` (confirming `hideControls()` itself is a no-op — the Autoplay-specific regression test was removed along with that feature, and the once-similar `mobileSettings.controls: false` coverage was removed along with `mobileSettings` itself, §2.5). The exact same class of bug recurred once more, later: the truncated-caption modal (§2.3a) could open while an idle timer from before it opened was still ticking down, and `hideControls()`'s guard list didn't know about `captionModalOpen` either — fixed the same way, adding that check to `hideControls()` directly rather than to whatever called it.
- `autoHideDelay: 0` is for hosts building fully custom chrome around Shoji. Core keyboard nav (Escape/arrows/Home/End) keeps working either way, since it's independent of visibility; a keyboard user can still Tab to an invisible control and activate it, they just can't see it — an accepted tradeoff for what is an explicit host opt-in, not the default.
- **`autoHideDelay: 0` also keeps the mouse cursor itself visible, unlike ordinary idle-hide.** Requested directly: `.shoji-controls-hidden`'s own `cursor: none !important` rule (below) applies unconditionally to whatever hid controls — idle timeout, `0`, a vertical drag past its own threshold, closing — but `0` specifically means "this host is building their own chrome around Shoji," not "the whole gallery should act like nothing is there." `ensureLightbox()` (`Gallery.ts`) adds `.shoji-cursor-visible` to `.shoji-dialog` once, at construction, only when `autoHideDelay === 0`; a second CSS rule, `.shoji-cursor-visible.shoji-controls-hidden` (two classes on one element — higher specificity than the one-class rule it's overriding, so it wins despite both using `!important`, no source-order dependence needed), sets `cursor: auto !important` back. Every other hidden-controls path (idle timeout, a completed drag, closing) is untouched — the cursor genuinely still hides there, exactly as before.
- **Idle detection** — `pointermove`, `pointerdown`, `touchstart`, `wheel`, `keydown`, `focusin` inside the gallery, one passive listener set on `.shoji-outer` rather than a per-control timer (the gesture engine, §2.4, attaches its own separate listener set to `.shoji-dialog` for drag/pinch/tap recognition — a distinct concern, not literally shared, though `onDragStart` also calls the same activity hook so a drag counts as activity too). Any of them resets the idle clock and re-shows immediately (except in the `autoHideDelay: 0` mode above). `focusout` on a control restarts the idle clock too, so tabbing away from a focused button resumes the countdown rather than leaving controls visible forever.
- **Never hides while the pointer is hovering any part of the overlay** — close/prev/next/caption-toggle, the counter, the caption itself, the toolbar bar (including its own padding/gaps, not just the buttons nested in it), any plugin `ButtonSpec`/raw-element toolbar addition, and any plugin `ctx.ui.overlay()` element. `wireControlHover()` (`Gallery.ts`) tracks this via `hoveringElements`, a `Set<HTMLElement>` (paired `pointerenter`/`pointerleave`, safe to double-wire nested elements — entering a nested element's bounds also crosses its ancestor's, so both fire, both balance on leave — and safe against the exact same element entering twice with no leave between, `Set.add()` on an already-present member is a no-op), only counting down again once the pointer actually leaves every hovered element. (A stationary hover alone wouldn't be caught by the `pointermove`-based idle reset above, since `pointermove` only fires on movement — this is the reason `pointerenter`/`pointerleave` exist as a separate mechanism.) Only the slide media itself (the photo/video being viewed) is deliberately excluded — auto-hide exists specifically so a motionless viewer sees an unobstructed photo, and pausing on that too would defeat the point.
  - **Reported from real usage: the counter and caption used to be excluded too** ("informational, not interactive"), and a plugin's own `ctx.ui.overlay()` content was never wired at all — meaning a plugin like an EXIF panel had its own overlay vanish out from under a viewer actively hovering it, since Shoji had no way to know. Fixed by extending `wireControlHover()` to the caption, counter, toolbar zones, and — via `pluginOverlay()`/`pluginToolbar()`'s raw-element path — every plugin-added overlay/toolbar element too, with no plugin-side changes needed to opt in.
  - **A real correctness gap introduced by extending this to plugin content**: unlike the static, gallery-lifetime toolbar buttons, a plugin can legitimately add and remove its own overlay element while the gallery stays open (a toggleable panel, not just on `destroy()`). Removing an element mid-hover means its `pointerleave` never fires, which would leave the old hover count stuck positive — auto-hide paused forever. `wireControlHover()` now returns an unsubscribe that corrects the set if the element was still hovered at removal time, and `pluginOverlay()`/`pluginToolbar()` call it as part of their own cleanup.
  - **Three further real bugs, all reported from real usage, all the same underlying lesson: a plain incrementing/decrementing counter trusts every `pointerenter`/`pointerleave` to fire, in order, exactly once each — and browsers don't actually guarantee that.** `hoveredControlCount` (a number) was replaced with `hoveringElements` (a `Set`) plus `hoverableElements` (every control ever wired, the reconciliation candidate list) and `reconcileHover()`, which re-derives set membership from the browser's own live `:hover` truth rather than trusting bookkeeping alone:
    1. **A control that synchronously replaces its own children on click while the pointer sits stationary over it (Autoplay's own play/pause icon swap, `button.innerHTML = ...`) can make the browser refire `pointerenter` a second time** — the target's identity changed under the cursor, so hit testing re-runs, even though the pointer itself never moved and never left. A plain counter double-increments here with no way to detect it; the single real `pointerleave` that eventually follows can only ever undo one of the two increments, leaving the count permanently stuck above zero and auto-hide silently, permanently paused. A `Set` sidesteps this entirely — adding an already-present element twice is a no-op by construction, nothing to "double count" in the first place.
    2. **The mirror image: a control that *appears* under an already-stationary cursor never gets a `pointerenter` at all** — the same "browsers only recompute hover state on actual pointer movement" rule already leveraged for the hide-under-a-stationary-cursor case elsewhere in this file, just running in the opposite direction. The common trigger is `open()` itself: whatever the viewer clicked to get here is often right where a toolbar/caption/nav control ends up once the dialog renders, so the cursor can be genuinely, visibly resting on a control the very instant it appears — with the old counter, that control's hover was simply never counted, so idle auto-hide could fire and hide something the cursor was plainly still sitting on top of. `reconcileHover()`, run at the top of `onActivity()` (so any real activity re-syncs it, not just pointer-specific events — a `focusin` from `FocusTrap.activate()` moving focus into the dialog on open is what actually triggers the first reconciliation pass in practice, letting this self-heal before the viewer even moves the mouse) fixes this directly: it doesn't wait for an enter event that may never come, it just asks each registered control "is the pointer over you right now" and syncs the set to match, in both directions.
    3. **A third real bug, found testing the above cross-browser, not reproducible in the browser this was first built and verified against:** reconciliation is only as fresh as the last real activity event that triggered it — if a browser's own pointer-movement simulation fires its last bubbling event *before* `:hover` has caught up to the pointer's actual final resting position (confirmed reproducing consistently under Firefox automation specifically; nothing rules out a genuine, if much rarer, real-hardware equivalent), reconciliation records a stale answer and nothing else ever arrives to correct it before the idle timer fires. Fixed by also calling `reconcileHover()` a second time, directly inside `hideControls()` itself, immediately before the decision that actually depends on the answer — the one moment staleness would actually matter is the one moment worth a fresh, authoritative re-check, rather than trusting whatever the last activity event happened to leave behind.
- **Focus counts as activity, not as a standing block.** Focusing a control (`focusin`) resets the idle clock and re-shows controls, same as any other interaction — it does *not* prevent them from hiding once the delay elapses with nothing further happening. A real bug, found and fixed: this used to work like hover — checking `document.activeElement` directly inside `hideControls()`'s gate, so a focused control stayed visible indefinitely. But a click leaves a `<button>` focused as an ordinary side effect, not only through deliberate keyboard navigation, and nothing un-focuses it if the viewer simply stops interacting afterward (mouse moves away, window loses attention, whatever) without clicking something else in the dialog first — that permanently blocked auto-hide, not just delayed it, since a no-op'd hide timer never reschedules itself. Fixed by dropping the `activeElement` check entirely; the existing `focusin`/`focusout` → `onActivity()`/`scheduleAutoHide()` wiring already resets the clock correctly on every real focus change, with no separate standing-block needed.
- **Purely presentational**: a single class (`.shoji-controls-hidden` on the dialog) toggles `opacity`/`pointer-events` on the controls, never `display:none`, never removed from the tab order. Transition duration is `--shoji-duration`, which is already `0ms` under `prefers-reduced-motion` (§9) — reduced-motion users get an instant toggle instead of a fade, the idle timing itself is unchanged.
- **The mouse cursor hides too**, not just the controls — `.shoji-controls-hidden, .shoji-controls-hidden * { cursor: none !important; }` (`shoji.css`), so a motionless viewer sees nothing but the photo, not a lingering pointer sitting over it. `!important` is deliberate: it wins over a plugin's own cursor styling (e.g. Zoom's `zoom-in`/`grab` affordance, `zoom.css`) without core needing to know that plugin's selectors — the hidden state overrides any interactivity hint regardless of which plugin set it. Real CSS cascade behavior, verified in `tests/e2e/core-autohide-cursor.spec.ts`, not a jsdom unit test. Except under `autoHideDelay: 0` (see above) or a vertical drag past the close threshold (§2.4/§2.6a's eighth real bug — `.shoji-controls-hidden-for-drag`) — both reuse `.shoji-controls-hidden` for the fade but override the cursor back to visible, for opposite reasons: `0` because the host owns its own chrome, the drag because the pointer is actively moving and hiding it mid-drag is disorienting, not clean.
- Emits `controls:hide` / `controls:show` so a plugin can opt its own overlay out of the sync later (e.g. the editor keeping its toolbar visible regardless, since idle detection is suspended while it's the busy/blocking modal per §8.3).

## 3. Plugin system

Design goal: **an "elegant and simple" plugin is a function.** No base classes required.

```ts
export interface ShojiPlugin {
  name: string;
  version?: string;
  requires?: string[];                    // plugin dependency names
  defaults?: Record<string, unknown>;     // merged into options.<name>
  init(ctx: PluginContext): void | (() => void);  // return = cleanup
}

interface PluginContext {
  gallery: Gallery;                 // full public API
  options: Readonly<Record<string, unknown>>; // merged options for this plugin
  on: Gallery['on'];                // auto-unsubscribed on destroy() (bus.clear())
  emit<K extends keyof GalleryEvents>(event: K, detail: GalleryEvents[K]): void; // same bus gallery.on() reads from
  ui: {
    toolbar(slot: 'left'|'center'|'right', el: HTMLElement | ButtonSpec): Unsubscribe;
    overlay(el: HTMLElement, layer?: number): Unsubscribe;   // appended into .shoji-dialog; position:absolute is on the caller
    outer(): HTMLElement;                                     // .shoji-outer
    registerShortcut(key: KeySpec, fn: (e: KeyboardEvent) => void): Unsubscribe; // key = event.key, e.g. ' ' for Space
    registerVideoProvider(name: string, render: VideoProviderRenderer): Unsubscribe; // §4.3 — name matches VideoDescriptor['provider']
  };
  storage: { get(k: string): unknown; set(k: string, v: unknown): void }; // per-gallery scratch, cleared on destroy()
}
```

Rules:

- Plugins register UI only through `ctx.ui` slots → consistent styling/theming, automatic cleanup, no z-index wars.
- Plugins communicate via events, never direct imports of other plugins. `requires` enforces hard deps — resolved against the whole declared `plugins` list, not registration order; see §3.1's own note.
- Everything a plugin creates through `ctx` is disposed automatically on `destroy()`; the optional returned cleanup handles anything else.
- Options: `new Shoji(el, { plugins: [Zoom, Autoplay], zoom: {...}, autoplay: {...} })`.
- Every official plugin's `defaults` are chosen so `new Shoji(el, { plugins: [Zoom] })` — no `zoom: {...}` object at all — is a complete, working config. The per-plugin options objects throughout §4–§8 exist for hosts who want to override something, not because anything is required.

A "hello world" plugin is ~10 lines. That's the bar for "simple".

### 3.1 Loader implementation notes

- **Plugins init eagerly, at `new Shoji()` construction time** — not lazily on first `open()`. `Gallery`'s constructor calls `ensureLightbox()` directly (building the dialog DOM, hidden via `display:none` until an actual `open()`) and `ensureLightbox()` calls `initPlugins()` right after, so every plugin's `init()` has already run by the time the constructor returns. This is a deliberate, scoped tradeoff: it means `ctx.ui.toolbar()`/`ctx.ui.overlay()`/`ctx.ui.outer()` always have real DOM to act on synchronously inside `init()`, with zero queueing machinery, *and* it lets a plugin act on the gallery before the viewer has clicked anything — the layout plugin (§5) depends on exactly this, rendering the *inline* container (`ctx.gallery.element`) immediately, since that's what the viewer clicks to open in the first place. (This corrects an earlier draft of this section, which described the opposite — lazy, on-`open()` init — a stale holdover from before the layout plugin's requirements settled this the other way; the code has been eager since, the prose just hadn't caught up.) `reinit()` (§2.7) re-runs every plugin's `init()` the same way, on the same eager schedule.
- **`requires` violations are skipped, not thrown — resolved against the whole declared list, not registration order.** `resolveValidPluginNames()` (`Gallery.ts`) decides which plugins will actually load as a fixed point over the *entire* `plugins` array before any `init()` runs: start from every structurally-valid entry (a real object with an `init` function), then repeatedly drop any whose `requires` points at a name no longer in that set, until a full pass drops nothing. That repetition is what makes a chain cascade correctly — if B gets dropped because its own `requires` went unmet, anything requiring B drops on the very next pass, the same as if the original problem were its own. A genuine mutual requirement (A needs B, B needs A, both otherwise fine) never gets caught by this — each still finds the other present whenever it's checked — which is correct, not a missed case: this only ever decides *whether* something loads, never *when*, so two plugins depending on each other creates no actual ordering conflict to detect in the first place. `initPlugins()`'s own loop still runs in exactly the declared array's order regardless, and every `ctx.ui.toolbar()` registration lands in that same order too — an earlier version of this check was itself order-dependent (checked against whichever plugins had already been processed so far in the same pass), so declaring `requires: ['x']` before `x` itself appeared anywhere in the array silently failed. Flagged directly as real integration friction — a host had to hand-order a `plugins` array purely to satisfy `requires`, with no actual reason *execution* order needed to match *declaration* order for what's fundamentally a presence check. Toolbar/collapse-priority order (§3.1a) is entirely unaffected either way: it was, and remains, driven purely by the array's own declared order, never by this resolution. One misconfigured plugin still shouldn't take down the whole gallery — the rest of the plugin list still loads regardless.
- **`ctx.ui.toolbar`'s `ButtonSpec` path** builds a real `<button class="shoji-toolbar-button">` — `icon` set means `innerHTML = icon` + `aria-label = label` (icon-only, matching the core close/prev/next buttons' pattern); no `icon` means `textContent = label` instead. `.shoji-toolbar-button` shares its round-icon-button CSS with `.shoji-close`/`.shoji-nav` (one rule block, not duplicated per plugin) and is automatically wired into the §2.8 auto-hide system's "don't hide while a control is hovered/focused" behavior — that check now matches by class (`.shoji-close, .shoji-nav, .shoji-toolbar-button`), not an enumerated element list, specifically so plugin buttons participate without each plugin having to know auto-hide exists.
- **Slot `'right'` is where plugin controls belong** — every real official plugin (autoplay included) uses it. Unlike `'left'`/`'center'` (independent zones elsewhere in the toolbar, appended in call order, for a plugin that deliberately doesn't want to sit next to close), `'right'` inserts each new button *immediately before* the toolbar overflow caret (§3.1a; before close directly if the caret didn't exist yet) rather than appending after it — so close stays the fixed absolute-rightmost element, the caret sits just to its left, and plugin controls cluster directly to the caret's left, in registration order: `plugins: [A, B, C]` reads left-to-right as A, B, C, caret, close, since each later plugin's `init()` runs after the earlier ones and inserts at that same "right before the caret" point, pushing earlier buttons further left as each new one lands.
- **Single-file build (CLAUDE.md's "self-registering, zero setup")**: `src/index.ts` attaches each official plugin as a static property on the default export — `const Shoji = Object.assign(Gallery, { Autoplay });` — so the UMD global stays a single callable/constructable `Shoji` (not a namespace object) while `Shoji.Autoplay` is still reachable, no separate `<script>` tag needed. `new Shoji(el, { plugins: [Shoji.Autoplay] })` is how a host opts in. Bundler users who want to tree-shake away plugins they don't use should import from the `shoji/plugins/<name>` subpath instead of the default export.
- **`gallery.getActiveMedia()`** (public API, not `ctx`-scoped since any plugin can just use `ctx.gallery`) returns the active slide's `.shoji-slide-media` container — the same element the zoom transition (§2.3b) already targets internally via `SlideManager.getActiveMedia()`. This is how the autoplay plugin locates the active `<video>` (`getActiveMedia()?.querySelector('video')`) without querying `.shoji-slide-video` globally, which would be ambiguous whenever `preload > 0` pools multiple off-screen slide-media containers.
- **`gallery.getOriginElement(index)`** (public, same rationale as `getActiveMedia()` above) — the thumbnail for `index`: `data-shoji-id="<item.id>"` marker if present, else `scannedElements[index]` in selector mode, else `null`. The zoom transition (§2.3b) has always used this internally; made public so the `activeThumbnail` plugin (§4.2) can reuse the exact same lookup rather than re-deriving it.
- **Instance introspection**: `gallery.isOpen`/`isDestroyed`/`controlsHidden` are getters over private fields (`opened`/`destroyed`/`autoHidden` — renamed from the private field names they used to share, since a getter and a same-named field collide) that were already tracked internally but had no public read path before; `getActivePlugins()` returns the plugin names that actually initialized (deduplicated, excluding invalid entries and ones skipped for an unmet `requires`) by reusing `initPlugins()`'s own tracking set (`activePluginNames`, promoted from a function-local `Set` to a field so it survives past that call) rather than re-deriving anything — reset at the top of every `initPlugins()` call (so `reinit()` with a different plugin list doesn't inherit stale names) and cleared again in `teardown()` (so a destroyed instance correctly reports `[]`). `Shoji.version` (static, on the library itself, not per-instance) is a named import from `package.json` (`resolveJsonModule`), not a hand-duplicated string, so it can't drift from the real release version — tree-shaken down to just the string, not the whole file, since only that one named export is used.

### 3.1a Toolbar overflow popover

**Problem**: a host with several plugins registered to the `'right'` slot (§3.1) — say Zoom, RotateFlip, Fullscreen, Autoplay, plus a couple of app-specific ones — plus close, can pack more buttons onto the toolbar's own row than a narrow viewport (mobile-portrait especially) has width for. The `.shoji-toolbar-slot`s (`left`/`center`/`right`) already `flex-wrap: wrap` independently rather than as one unified row, but letting a busy toolbar grow to two or three rows eats into the caption's own reserved space (§2.3a's `--shoji-toolbar-height`) and looks cluttered. `mobileSettings.controls` (§2.5, removed) was an earlier, device-type-gated attempt at a related problem — "start hidden on touch" — but a wrapping toolbar is a viewport-*width* problem, not a touch-vs-mouse one, and doesn't need a whole separate `mobileSettings` surface to solve.

**Mechanism — measured, not assumed.** `Gallery.pluginToolbarButtons: Array<{ el, slot }>` tracks every `ctx.ui.toolbar()`-registered button in registration order, alongside the slot it was registered into. `measureToolbarOverflow()` (triggered by `scheduleToolbarOverflowMeasure()`, rAF-coalesced — CLAUDE.md's batch-DOM-writes-via-rAF principle, reusing the pre-existing `toolbarHeightFrame` field/pattern §2.3a already established) always restores every tracked button to its original slot first — a full clean-slate recompute each time, not an incremental delta, since both the button set and the viewport width can have changed since the last pass. "Fits in one row" is then measured directly: each slot's own rendered height is compared against `closeButton`'s (always exactly one row tall, always present) — a slot has wrapped if it's taller than that. If everything fits, the popover caret (`toolbarOverflowButton`, hidden by default) stays hidden and nothing else happens.

**Collapse policy — `maxPinnedToolbarButtons` (`GalleryOptions`, default 2) — a ceiling, not a guarantee.** If it doesn't fit, buttons collapse into the popover latest-registered first (§3.1's own registration-order-is-priority convention: `plugins: [A, B, C]` keeps A pinned longest), collapsing down to at most `maxPinnedToolbarButtons` pinned — but requested directly, corrected from an earlier design: **the counter (`toolbarLeft`) and `closeButton` must never wrap onto their own line, full stop**, no configuration able to force it. Collapsing therefore keeps going *below* the ceiling — down to zero pinned if it must — whenever even that many still leaves a slot wrapped; `fitsOneRow()` already measures every slot's height, not just `toolbarRight`'s, so a wide counter or other left-slot content competing for the same row pushes the pinned count down too, not just `toolbarRight`'s own button count. (An earlier version of this policy went the other way — `minPinnedToolbarButtons`, a *floor* that was never violated even if it left a slot wrapped, went through hardcoded 1, then 3, before landing on a configurable default of 2. Flagged directly as the wrong tradeoff once a real narrow-viewport report showed `closeButton` itself wrapping to a second line: losing access to a button was judged less bad than that at the time, but a *guaranteed* single row turned out to matter more. Renamed and inverted to the ceiling described here — same default of 2, opposite meaning.) `closeButton` stays the fixed absolute-rightmost control; the caret sits just to its left, revealed only once needed — reordered from an initial close-then-caret layout, flagged directly as reading backwards. "Latest-registered first" only describes *which* button drops off the row first — the panel itself reads in the same left-to-right registration order the toolbar row would have shown (each newly-collapsed button is inserted at the *front* of the panel, not appended to the end, since it was evaluated for collapse before the ones already ahead of it in registration order): flagged directly as reading backwards in an early build, when a plain `appendChild` in the collapse loop put the panel in the reverse of that order.

**`.shoji-toolbar-slot`'s own `max-width` — removed entirely.** A real bug, reported from real usage (a Galaxy Note II-class 360×640 viewport, reproduced directly): `.shoji-toolbar-slot` predated this feature and already capped each slot at a flat percentage of the toolbar's width (§3's own pre-existing wrap-to-a-second-row fallback, from before the popover existed to replace it for the common case) — 45% initially, which a first report showed was narrower than even the *default, unconfigured* pinned count plus close plus the caret needed, so raised to 60%. That only patched the specific default-count case, though: the cap was a flat percentage regardless of how much room the *other* slot's content (the counter) actually needed at a given viewport, so `toolbarRight` could still get capped well below the real available space — confirmed directly by a follow-up report at a higher configured `maxPinnedToolbarButtons` (4 pinned buttons configured, only 2 actually shown, plenty of real width still free). Removed the cap entirely rather than raising the percentage again: `measureToolbarOverflow()`'s own real, measured fit-check (`fitsOneRow()`, already reading every slot's actual rendered height) is what decides how many buttons stay pinned now, so a static percentage assumption was never the right mechanism for a problem the JS was already solving properly — it could only ever fight that measurement, never help it.

**Popover, not in-place expansion** — requested directly, so a revealed set of buttons never pushes/reflows whatever else shares the toolbar row. `toolbarOverflowPanel` is appended directly to `dialog` (a sibling of `.shoji-toolbar`, not nested inside it — sidesteps the toolbar's own `pointer-events: none` base rule, which is re-enabled per-slot, not per-descendant, and would otherwise need remembering to re-enable here too; same placement pattern `.shoji-caption-modal`, §2.3a, already uses). Positioned `absolute`, anchored under the toolbar via `top: var(--shoji-toolbar-height)`. Laid out as a CSS grid (`grid-template-columns`, wrapping to as many rows as needed) whose column count `Gallery.positionToolbarOverflowPanel()` sets on every open — not a fixed value — to match the toolbar row's own column count right now: however many plugin buttons are actually still pinned, *plus one for the caret itself* (`closeButton` excluded — it's never one of the popover's own columns). Requested directly, corrected from an initial fixed-3-column version and, after that, from a version scoped to the pinned buttons alone (undercounting by one — the caret is visually part of that same row too): at the default `maxPinnedToolbarButtons` (2), that's 2 pinned + the caret = 3 columns. Buttons keep their normal round 44px toolbar-button appearance, not stretched to fill a column; the pitch (44px + `--shoji-spacing-sm` gaps) matches a toolbar button's own size and `.shoji-toolbar-slot`'s own gap, so the popover's icon columns line up with the toolbar row's icons above them — the whole panel reads as that same row continuing downward, not an independently-sized box that happens to sit nearby.

**Anchored to the caret, not the toolbar's edge** — a real bug, flagged directly: the panel's `right` offset was originally a fixed CSS value (`var(--shoji-spacing-md)` from `dialog`'s own right edge), which happened to land near/under `closeButton` — the actual absolute-rightmost toolbar control — rather than under the caret that opens it, since the caret sits one button-width-plus-gap to `closeButton`'s left. That fixed offset also couldn't track the caret's own position shifting with `maxPinnedToolbarButtons` or viewport width. `positionToolbarOverflowPanel()` (the same method that sets the column count above) runs on every `openToolbarOverflow()`, reading `toolbarOverflowButton`'s live `getBoundingClientRect()` against `dialog`'s, and sets `toolbarOverflowPanel.style.right` inline — subtracting the panel's own `padding-right` so the *grid content's* right edge (not just the panel's border box) lines up with the caret's right edge, keeping the icon-to-icon alignment above genuinely flush rather than merely close. Not re-measured while open: `measureToolbarOverflow()` (triggered by any resize/toolbar-height change) already unconditionally closes the popover first, before it re-collapses buttons from a clean slate — so a fresh `openToolbarOverflow()` call, which always repositions, is guaranteed before the panel is shown again.

**Pinned count derived from `pluginToolbarButtons`, not from `toolbarRight`'s own DOM children — a real bug, reported from real usage.** `positionToolbarOverflowPanel()`'s column-count math (above) originally counted `toolbarRight.children`, filtering out `closeButton`/`toolbarOverflowButton` by identity and anything `hidden`. That's correct only as long as `toolbarRight` contains exactly what Shoji itself put there — but `.shoji-toolbar-right` isn't a documented extension point, and nothing enforces that a host stays out of it. Confirmed directly from a real report: a host plugin appended its own loading spinner straight into `toolbarRight` (alongside its properly-registered button, via raw DOM access rather than `ctx.ui.toolbar()`) and toggled the spinner's visibility with `style.display` rather than the `hidden` *attribute* — so it passed the old filter's `!el.hidden` check (never actually `hidden`, just visually `display: none`) and got counted as a third pinned button, turning what should have been a 3-column popover into 4. Counting from `this.pluginToolbarButtons` (buttons genuinely registered through the plugin API) instead of re-querying the DOM makes this immune to any such element a host or plugin places directly in that slot, regardless of how it manages its own visibility — `.shoji-toolbar-right` is still not a supported place to put arbitrary content, this only stops that misuse from corrupting *this specific calculation*. Covered by an e2e regression test (`tests/e2e/core-toolbar-overflow.spec.ts`) using a fixture plugin (`demo/pages/e2e-plugins.ts`, `?foreignToolbarElement=1`) that reproduces the exact pattern — a `style.display`-toggled element appended directly to `toolbarRight` — and asserts the popover still renders a 3-column grid.

**A second, distinct pinned-count bug, reported from real usage, this time on a video slide — the fix above wasn't wrong, just incomplete.** Counting from `pluginToolbarButtons` correctly stops a *foreign* element from corrupting the count, but two more sources of drift live entirely inside Shoji's own, otherwise-correct bookkeeping:

- **Undercounts**: `captionToggleButton` (`dom.ts`, only ever visible on a video slide with a caption — §2.3a) is a real, space-consuming, never-collapsible toolbar button, but it isn't registered through `ctx.ui.toolbar()` — it's appended directly in `dom.ts`, so it was never in `pluginToolbarButtons` to begin with and stayed invisible to this calculation entirely.
- **Overcounts**, in the opposite direction: a genuinely-registered plugin button that hides *itself* for its own content reasons — Zoom's `zoomIn`/`zoomOut`/`actualSize` buttons on a video slide (§4.6) — still passes the `parentElement === toolbarRight` check. Hidden means zero layout size, so `measureToolbarOverflow()`'s collapse loop (above) never needed to move it into the panel to make the row fit; it stays sitting in `toolbarRight`, invisible, but still counted as if it occupied a column.

Reported exactly as the two compounding on a real video slide: only 2 icons visibly pinned (the caption toggle and the caret) but a 4-column popover grid — neither number matching what was actually on screen. Fixed by checking `!b.el.hidden` in the same filter (removing the overcounting half) and adding one more to `pinnedCount` whenever `captionToggleButton` is currently shown (removing the undercounting half) — both still counted from the registry/known core elements, never by re-querying `toolbarRight.children` wholesale, so the first bug's own fix isn't undone by this one. Covered by an e2e regression test (`tests/e2e/core-toolbar-overflow.spec.ts`, `demo/pages/e2e-plugins.ts`'s `?videoSlide=1`) that turns item 0 into a captioned video slide — triggering both the caption-toggle undercount and Zoom's self-hidden-button overcount at once, same as the real report — and asserts the popover's actual `gridTemplateColumns` count against an independently-computed expectation (every button genuinely visible on `toolbarRight` ahead of the caret, counted fresh from the DOM in the test itself, not by calling Gallery.ts's own formula). Confirmed failing against the pre-fix code first (3 columns, not the correct 2), by hand-reverting the fix locally before restoring it.

**Interaction**: click (or the caret's own click) toggles it; `FocusTrap.retarget(toolbarOverflowPanel)` narrows Tab-cycling into it while open, same mechanism the caption modal (§2.3a) established for a nested mini-dialog without disturbing the outer trap's own focus-capture/restore state; Escape closes it (a `document`-level keydown listener, added on open and removed on close — matching the caption modal's own leak-safety precedent); an outside click closes it (listener registered on `dom.outer`, before `onOuterClick`'s own, same ordering-matters pattern the caption modal's backdrop-click listener uses); a click on one of the popover's own buttons does neither, via `INTERACTIVE_CONTROL_SELECTOR` (`GestureController.ts`) gaining `.shoji-toolbar-overflow-panel` alongside its pre-existing `.shoji-caption-modal` entry, so `GestureEngine`'s own tap recognition and `isBackdropClick` don't misread it as a gesture or a backdrop click.

**Guards, mirroring §2.3a's `captionModalOpen` precedent exactly** (the same bug class, proactively guarded against from the start this time rather than found and fixed after): `hideControls()` won't hide controls while `toolbarOverflowOpen` (an idle timer armed before the popover opened isn't auto-cancelled by opening it, and the popover is visually anchored to the toolbar it would otherwise disappear out from under); `GestureController`'s `isZoomed` callback also checks it (suspends drag-to-navigate/close while the popover is open); `navigate()` closes it before moving to a new slide (its position depends on the current toolbar height, which can change slide-to-slide — e.g. a video slide's caption-toggle button appearing/disappearing — simpler to close than reposition mid-navigation); `beginClose()` closes it; and `teardown()` closes it too, with its own explicit check — `teardown()` bypasses `beginClose()` entirely by calling `finishClose()` directly, so a `destroy()`/`reinit()` while the popover happened to be open would otherwise leak its document-level keydown listener the same way the caption modal's own `teardown()` gap once did.

## 4. Feature specs (lightGallery parity)

- **Thumbnails** (an in-lightbox filmstrip strip, distinct from active thumbnail tracking below): attempted and then **removed**. Built once (a real `<button>`-per-item strip below the slides, `ctx.ui.overlay()`-mounted); ran into a structural performance problem that turned out to be unfixable at the plugin level — hosts without a real, small `item.thumb` fall back to full-resolution originals for every thumbnail, and no amount of fetch-scheduling (deferred `src`, `fetchPriority` hints, gating on `slideItemLoad`) changes the fact that decoding N multi-MB images is expensive; a controlled A/B test showed the plugin itself was no longer the bottleneck once those fixes landed, but the underlying "no real thumbnail source" cost remained and the feature was scrapped rather than kept as a footgun. Revisit only with a real thumbnail-generation story (server-side resizing, or a documented hard requirement that hosts supply `item.thumb`) — not as a bare fallback-to-full-res strip again.
- **Active thumbnail tracking** — **implemented**, see §4.2. This syncs the *host's own* thumbnail grid to whatever's open in the lightbox, rather than rendering a dedicated strip of its own.
- **Pagers** — **not implementing.** (Was scoped as minimal dot/bar pagers, alternative to thumbnails; hover shows the corresponding thumbnail in a popover — the thumbnail-popover dependency is why it's cut, same reasoning as Thumbnails above.)
- **Zoom** — **implemented**, see §4.6 for the full spec, the new `Gallery.registerZoomGate()` core hook pan needed, and what's deliberately deferred (a further reactive `sizes` rewrite beyond the base `srcset`/`sizes` wiring this plugin's work also fixed).
- **Video** — **implemented, YouTube + Vimeo**, see §4.3 for the full spec, the new `ctx.ui.registerVideoProvider()` core hook it needed, and what's deliberately deferred (poster/thumbnail handling; Wistia — not implementing at all, not just deferred, see §4.3).
- **Autoplay / slideshow** — **implemented**, see §4.1 for the full spec (video-aware timing, the manual-pause-interrupt state machine, and what's deliberately deferred).
- **Fullscreen** — **implemented**, see §4.4.
- **Hash / browser history** — **not implementing.** (Was scoped as `#shoji-<galleryId>-<slideId|index>` deep links; open-on-load if hash matches; back/forward navigates slides.) The user's own gallery (shashin) already has its own share-link feature at the app level with its own URL scheme — a second, Shoji-internal deep-link mechanism would just compete with it, not serve a need.
- **Share** — **not implementing**, for the same reason as Hash above: shashin already owns this at the app level.
- **Comments** — **not implementing.** (Was scoped as a mount-point overlay panel with adapters for Facebook Comments and Disqus, plus a `custom` adapter receiving the current item — the widget itself user-supplied.)
- **Rotate/flip (view)** — **implemented**, see §4.5. Non-destructive, resets per slide — persistent, pixel-level editing was scoped to the Editor plugin (§8), which is not implementing; there is no persisted-edit path.
- **Responsive images**: `srcset`/`sizes`/`<picture>` passthrough, DPR-aware selection, any format (webp/avif/jxl) — core never re-encodes.
- **Dynamic mode & updateSlides**: covered in §2.1.
- **Mobile**: CSS-only media sizing; 44px touch targets. (`mobileSettings` — removed, §2.5.)

### 4.1 Autoplay / slideshow (`src/plugins/autoplay`)

`new Shoji(el, { plugins: [Shoji.Autoplay] })` — no `autoplay: {...}` object needed for the default 5000ms interval, per §3's "every official plugin's defaults make a bare `plugins: [X]` complete" rule. A toolbar play/pause button (left slot) and a `Space` shortcut both call the same internal `toggle()`; a thin progress bar (`--shoji-progress`) tracks time-to-next-advance along the dialog's bottom edge for timed slides, hidden during video slides. `showProgress: false` (default `true`) turns it off entirely — purely presentational, doesn't touch timing — for a host who'd rather the slideshow ran silently; when off, the bar is never even mounted into the DOM, not just visually hidden.

- **`autoStart: boolean`** (default `false`) — starts the slideshow automatically the moment the gallery opens, every `open()` not just the first, same as clicking the button. Requested from real usage: no exposed programmatic `start()`/`stop()` existed, and the only way to trigger this from outside was clicking the DOM button — a host wanting "plays immediately on open" had no clean way to get there. The button itself also now carries a stable `shoji-autoplay-toggle` class — a real bug pattern, reported from real usage: `title`/`aria-label` swap with `locale` (play/pause), so host code that needs to find this button from outside (e.g. to pause the slideshow before opening its own modal on top) and was matching on that translatable text broke silently the moment the locale changed. The class never changes regardless of `locale`.

**Ordinary (non-video) slides**: fixed `interval` ms (default 5000, `options.autoplay.interval` to override), then `gallery.next()`. `next()`'s own `loop` behavior (§2.2a) — wrap at the ends, or stop there — applies unchanged; autoplay does **not** have its own separate loop setting. If `loop: false` and autoplay's `next()` lands back on the same index (already at the last item), autoplay stops itself (button reverts to Play) instead of ticking forever with nothing to advance to.

**Video slides — this is the part that matters, spelled out precisely:**

1. Arriving at a video slide (via `next()`, or the viewer manually navigating mid-slideshow, or pressing Play while already sitting on one) calls `video.play()` instead of starting the fixed-interval timer. The interval never applies to a video slide — its own runtime is the timing source.
2. The video's native `ended` event is what advances to the next slide — not a timer, and not `next()`'s own scheduling.
3. **A manual pause on that video pauses the whole slideshow**, not just the video: the `pause` event (checked against `video.ended` to not misfire on the pause some browsers fire alongside the natural end) stops autoplay entirely — timer/video listeners torn down, button reverts to Play, `autoplayStop` emitted.
4. **Manually resuming the video afterward does not resume the slideshow.** Because step 3 already detached autoplay's listeners from that video, a subsequent `play` (or even a later `ended`, if the viewer watches it through to the end on their own) is invisible to the plugin — nothing auto-advances. The viewer must press the slideshow's own Play control (button or Space) again to re-engage; doing so calls `video.play()` fresh on whatever is the current slide.
5. Explicitly pausing the slideshow *while* a video is actively playing (not a pause that originated from the video itself) also pauses the video, so the visible "paused" state and the video's actual playback state don't drift apart.
6. **Browser autoplay policy**: an unmuted `video.play()` that isn't a direct synchronous continuation of a user gesture can be blocked (rejected promise) — this is a real risk here specifically because auto-advancing into a video slide happens from a `setTimeout`/`'ended'`-event callback, not a click handler. The one case guaranteed to work regardless is pressing the slideshow's own Play button while *already sitting on* a video slide — that call chain (`click` → `toggle()` → `enterSlide()` → `video.play()`) is fully synchronous, so it counts as a direct user gesture under every major browser's autoplay policy; confirmed directly that reaching a video slide via `autoStart` (below) on `afterOpen` also counts, since that chain is equally synchronous, start to finish.
   - **A rejected `play()` isn't necessarily a broken video, and the two cases need different responses — reported from real usage, asked directly: "a broken video should skip to the next slide," not stop the slideshow.** A blocked-by-autoplay-policy rejection (`NotAllowedError`) and a genuinely unplayable video (`NotSupportedError` — a broken/missing source, an unsupported format) are indistinguishable by symptom alone (`play()` rejected, nothing plays) but need opposite responses: the first is a perfectly fine video that just needs the viewer's own click, so stopping the slideshow and waiting for them is correct; the second has nothing worth waiting for, so stopping just leaves the viewer stuck looking at a dead video until they notice and intervene by hand. Confirmed directly in a real browser, through the actual code path (not a synthetic `.play()` call): a genuinely missing/broken source rejects with `NotSupportedError`; the same call chain against a real, working video source rejects with nothing at all (no false-positive block on this synchronous chain — consistent with the point above). Fixed by branching on `error.name`: `NotAllowedError` still stops the slideshow exactly as before; anything else calls `advance()` instead, same as an `error` event does for a provider video (§4.3's `onError`/`error` event, which was already correctly distinguishing "this specific video is broken" from "playback merely blocked" by construction, never conflating the two the way the native-video path used to). Guarded against a stale rejection the same way `ensureProviderPlaying` already does (`currentVideo !== video || !playing`) — the viewer may have already navigated elsewhere, or stopped the slideshow entirely, by the time a slow-resolving rejection actually arrives.
7. **A provider video (§4.3, e.g. YouTube) still isn't necessarily playable the instant its slide becomes active** — a real bug, reported from real usage: `enterSlide()`'s `findPlayable()` check runs synchronously off `afterSlide`, but a provider's container is attached to the DOM immediately while its `.play` method only gets wired up once its own async setup (loading an SDK, constructing a player) finishes — arriving on a cold YouTube slide (nothing preloaded it, or the API simply hadn't finished loading in time) meant `findPlayable()` found nothing playable, so autoplay silently fell through to the ordinary fixed-interval branch: the video was never played at all, `--shoji-progress` ran and counted down like the slide was a photo. Reproduced deterministically in a real browser by delaying the IFrame API's own load past the interval — confirmed the video sat at `paused: true` indefinitely. Fixed with `isPendingProviderVideo()`: if a provider container exists but isn't playable yet, `enterSlide()` still starts the ordinary timer (a bounded fallback, so a provider that never becomes ready — network failure, blocked, ...— can't stall the slideshow forever) but also sets `awaitingProviderVideo`, and a new `slideItemLoad` listener re-enters `enterSlide()` once that same still-active index actually becomes playable, this time finding it via `findPlayable()` and playing it properly.
8. **A provider video (e.g. YouTube) still needs muting for an *automatic* play to actually take** — a real bug, reported from real usage after point 7 above was fixed: even once `findPlayable()` correctly waits for the provider to report playable, YouTube's own IFrame API has a stricter, silent cross-origin autoplay policy of its own — an unmuted `playVideo()` call that isn't a direct synchronous continuation of a gesture *on the embed itself* is simply ignored (no rejected promise the way native `<video>.play()` gives point 6 above something to catch; nothing to observe at all). Confirmed in a real browser: a slideshow left running unattended showed the video sitting at `paused: true` for 15+ seconds despite `enterSlide()` correctly calling `.play()` on it. Fixed by setting `video.muted = true` immediately before the automatic `.play()` call, scoped to a non-`HTMLVideoElement` playable only (`§4.3`'s `wirePlayableContract` gives `.muted` a real accessor backed by the player's own `mute()`/`unMute()`/`isMuted()`, not inert state) — native `<video>` needs none of this and stays unmuted (point 6 is unaffected). A manual click on the slideshow's own toggle button while already sitting on the video slide never touches this path at all — clicking YouTube's own native play button inside the iframe is a direct gesture on the embed itself and was never blocked to begin with.
9. **A provider embed's `mute()`/`playVideo()` postMessage commands can need more real time after "ready" before they reliably take** — a real bug, found via CI: `tests/e2e/plugins/video.spec.ts`'s Autoplay test failed consistently (all 5 browser projects, every retry) in GitHub Actions while passing reliably locally — the embed loaded fine, but the automatic play from point 8 above never visibly took effect within the test's timeout. GitHub Actions runners are far more CPU-constrained than a local dev machine; reproduced locally under 6x CPU throttling (`Emulation.setCPUThrottlingRate`), where a single play attempt was measurably less reliable. `ensureProviderPlaying()` retries `.muted = true` + `.play()` — the initial attempt plus up to `MAX_PROVIDER_PLAY_ATTEMPTS` (8) more, `PROVIDER_PLAY_RETRY_MS` (400ms) apart (9 total, ~3.6s before giving up) — checking `.paused` after each. Cancels itself if the slide changes or autoplay stops mid-retry (`currentVideo !== video`), and calls `stop()` if every attempt is exhausted, same "don't leave the slideshow silently stuck" principle as a rejected native `play()`. Verified under 6x throttling: video reliably starts within ~2s of the automatic play attempt. Legitimate hardening, kept — but **not** what turned out to fix CI (see point 10).
10. **GitHub Actions cannot reliably confirm YouTube actually reaches its own `PLAYING` state at all — infrastructure outside Shoji's control, not a timing race.** After point 9's retry landed, the same CI test still failed identically: all 5 browser projects, every retry, `paused` never once flipping to `false` in the full 10s window despite ~9 automatic play attempts within it. That rules out a timing race (which should have won at least a few of 15 total attempts across those runs) and points instead to the CI runner's environment itself — most likely YouTube declining real video delivery to a cloud/datacenter IP range, or the headless Linux runner lacking a working video decoder; the embed itself loads fine (a separate test), so this is specific to actually starting playback. `tests/e2e/plugins/video.spec.ts` now skips only the "reaches `paused: false`" assertion under `process.env.CI`, keeping it for local runs; the "the fixed interval never applies to a video slide" assertion right after it holds regardless of whether YouTube truly played, since `findPlayable()` locating a playable container is what stops `enterSlide()` from ever arming that timer in the first place, independent of what YouTube itself does next.
11. **A provider video that errors out (e.g. removed, private, or embedding disabled) is skipped, not stalled on.** Nothing in points 1–10 above covers this: a video that never reaches `PLAYING` because YouTube rejected it outright (not a timing/readiness problem) previously just sat there — no `ended` event ever comes, so the slideshow had nothing to advance on and no fallback timer either, since `findPlayable()` finding it playable is exactly what skips arming that timer. Fixed by having `renderYouTube` (§4.3) dispatch a bubbling `error` CustomEvent from the provider container whenever YouTube's own `onError` fires, and having Autoplay listen for it once, at `init()` time. `onVideoError` calls `advance()` if the slideshow is currently playing (a no-op otherwise, matching how an `ended` on a paused/inactive video wouldn't advance either). Deliberately listens on an ancestor rather than whatever `findPlayable()` currently returns: `onError` can fire *instead of* `onReady` entirely (a removed video never becomes "ready"), so a check gated on playability would miss exactly the case this exists to handle.
   - **A real bug, reported from real usage ("it used to work" — a regression): the ancestor listened on was `gallery.getActiveMedia()`, captured once at plugin `init()`.** Safe when a pool slot's own offset never changed after construction, no longer safe once `SlideManager.render()` was reworked (§2.3) to relabel a slot's offset in place instead of moving content between fixed-offset slots — the node that was offset 0 (the "active" one) at plugin-init time can become a neighbor after even one navigation, while a different node becomes the one actually active, going unheard by a listener still attached to the old node. Fixed by listening on `ctx.ui.outer()` instead — the whole lightbox, never relabeled — and checking, fresh on every `error` event, whether `gallery.getActiveMedia()` (re-resolved live, not cached) actually contains the event's target.
12. **Retry-exhaustion (point 9) and a slow-to-arrive `onError` (point 11) can both be racing to resolve the same stuck video — exhaustion used to call `stop()`, which could win that race and strand the slideshow.** Reported from real usage: a YouTube error (e.g. code 153) sometimes never advanced the slide even with points 9 and 11 both already in place. Root cause was two-fold, not one bug: first, `ensureProviderPlaying()`'s own exhaustion path called `stop()` instead of `advance()` — inconsistent with point 11's own `onVideoError`, which already treats "this video is broken" as "skip it," not "wait here." Changed to `advance()`, same reasoning as point 6's `NotSupportedError` branch: muted autoplay is essentially never blocked by policy, so exhausting every retry after already muting first means something is genuinely wrong with the embed, not that it's waiting on a gesture. Second, and the harder-to-find half: fixing that alone still failed a test reproducing the same scenario, because of an unrelated ordering bug in `Gallery.navigate()` that this exposed — see the `beforeSlide`/`pauseMedia()` ordering fix in §2.3's `pauseMedia()` entry, without which `advance()`'s own `gallery.next()` call could get silently reverted to `stop()` from inside the same synchronous call, by a completely different code path (Autoplay's own manual-pause detection, point 3 above) misfiring on a side effect of the navigation itself.
13. **Point 9's "retry by reissuing the command" strategy — correct for YouTube's fire-and-forget `playVideo()` — actively breaks a provider whose `play()` genuinely returns a promise (Vimeo).** Reported from real usage, three symptoms together: the video visibly never played and the slideshow just skipped past it every time; and — the tell — pausing the slideshow at exactly the right moment sometimes made the video start playing right afterward. That last symptom is what made this a distinguishable bug rather than "Vimeo is just unreliable": `stop()` doesn't call `play()`, so something already in flight had to be what finally completed once nothing else was interrupting it. Isolated from Shoji entirely to confirm: a single, uninterrupted `play()` call on a real Vimeo player reliably started playback in ~1.6s, while reissuing `play()`/`muted = true` every `PROVIDER_PLAY_RETRY_MS` (this loop's original, unconditional behavior, needed for point 9's YouTube case) kept it stuck indefinitely — each new call resets the progress the previous one had already made toward actually starting, so it never gets an uninterrupted run long enough to finish. (This also retroactively explains an earlier-recorded finding in §4.3 attributing this same symptom to Vimeo's Cloudflare bot protection — that was a misdiagnosis; the embed's own network access was never the problem.) Fixed by branching `ensureProviderPlaying()` on whether `video.play()`'s return value is genuinely thenable at runtime (`PlayableMedia`'s own type only *claims* every provider returns a promise, per its doc comment — this checks reality, not the type): a fire-and-forget result keeps point 9's exact reissue-every-retry behavior; a real promise is issued exactly once, with every subsequent retry only re-checking `.paused` over the same total budget, never calling `play()` again.

14. **A Vimeo video reaching its natural end stopped the slideshow instead of advancing it — a real bug, reported from real usage, with the same kind of tell as point 13: manually pressing play again restarted the same video from 0 instead of resuming or advancing anywhere.** Confirmed directly: Vimeo's own `'pause'` arrives as a genuinely separate postMessage event shortly *before* `'ended'` (~20ms apart in testing) when a video reaches its natural end — unlike native `<video>`, whose `.ended` property the browser sets synchronously before firing either event, so point 3's `onVideoPause` check (`currentVideo?.ended`) reliably lost the race here, reading `false` and treating a natural end as a manual pause; `stop()` fired and detached the video's listeners before the following `'ended'` event even arrived, so `onVideoEnded`'s `advance()` never got a chance to run at all. Fixed in `renderVimeo` (§4.3), not in Autoplay itself: `'pause'` is no longer dispatched immediately — it's held for a short delay (comfortably above the observed gap) and dropped entirely if `'ended'` arrives first, which then becomes the *only* event a natural end ever produces. A genuine standalone pause (no `'ended'` following) still dispatches, just delayed by that same short window — imperceptible for a real pause, and the cost of a correct one. Provider-specific by design: this is a Vimeo SDK event-ordering quirk, not something Autoplay's own provider-agnostic state machine should need to know about.

15. **Tap-to-pause-on-images, removed.** A single tap/click on a photo slide briefly toggled play/pause (holding off for `TAP_TO_PAUSE_DELAY_MS` to not also fire on the first half of a double-tap-to-zoom gesture) and toggled the auto-hide controls overlay on the same tap — both requested directly, both shipped, both later explicitly removed at the same requester's direction ("too disruptive"). The `tap`/`doubleTap` bus events themselves (§2.4) are unrelated core infrastructure and remain — this was one specific consumer of them, not the mechanism. `controlsWereHidden` on the `tap` event (added for this feature's own controls-toggle half) is left in place: general-purpose, not specific to what this plugin did with it, and removing it would be a breaking API change for no benefit.

16. **Pauses on a vertical drag crossing the close threshold, resumes if it retreats back under it without closing — requested directly.** Listens for the `dragCloseThreshold` event (§2.4, emitted from `Gallery.setControlsHiddenForDrag()` on every threshold crossing), independent of the now-removed tap-to-pause mechanism above (point 15): `hidden: true` calls `stop()` (recording whether it was actually playing first, `wasPlayingBeforeDrag`); `hidden: false` calls `start()` again, but *only* if this same crossing was what paused it — dragging back under the threshold after an unrelated manual pause (the toolbar button, a mid-drag tap) must not resurrect a slideshow the viewer had already stopped on purpose. A completed drag-close needs no explicit handling here: the existing `close` listener (point 3's sibling, `offClose`) already stops it, same as any other close path.

    **A related real bug, reported alongside the request above: the progress bar stayed fully visible through the entire close animation**, unlike the toolbar/nav/counter/caption, which all fade out first (§2.6a). It lived outside `.shoji-controls-hidden`'s CSS selector list — that list is core's `shoji.css`, a separate stylesheet from `autoplay.css`, easy to miss when it grows since nothing wires a plugin's own overlay elements into it automatically. Fixed by adding `.shoji-controls-hidden .shoji-autoplay-progress { opacity: 0; transition: opacity var(--shoji-duration) var(--shoji-easing); }` to `autoplay.css` itself — the same class core's own close/idle-hide sequencing already applies to the dialog either way, so no JS change was needed, just wiring the existing mechanism to one more element. Covered by unit tests (`tests/unit/plugins/autoplay.test.ts`) confirming both directions of the pause/resume behavior and that an already-stopped slideshow isn't spuriously resumed; and an e2e test (`tests/e2e/plugins/autoplay.spec.ts`) confirming the real CSS fade, checked deterministically via the `.shoji-controls-hidden` class landing synchronously right after the close click (not by polling the interpolating opacity value itself down to a final `0` — same race `core-close-controls-fade.spec.ts` already documented: the whole close sequence can finish and reset faster than a poll reliably samples, passing straight through the fade and landing back on "fully closed" between two polls).

    **A second real bug, reported from real usage some time after the fix above shipped: the same fade also applied on *ordinary idle auto-hide*** (§2.8), not just closing — plain `.shoji-controls-hidden` is the class *both* paths set, and the fix above keyed off that shared class rather than a close-specific one. A slideshow left running unattended would visibly lose the one piece of UI actively telling the viewer "still counting down to the next slide," and not get it back until an unrelated interaction, for every idle period, not just when actually closing. This had been shipped and unnoticed for a while — until Autoplay's own tap-to-toggle-chrome feature (point 15, since removed) was still in place, tapping the image revealed controls (progress bar included) on essentially every interaction with the running slideshow, papering over how often it was actually gone; removing that feature (an unrelated, direct request) is what made this pre-existing bug suddenly visible in practice, without any code touching the progress bar itself having changed. Fixed by giving `forceHideControls()` (the close-specific hide path) a second marker class, `.shoji-controls-hidden-for-close`, alongside the shared one — `autoplay.css`'s own rule now keys off that instead, so it only ever fades for closing, exactly the scope the original bug report was actually about. `showControls()`/`finishClose()` clear both classes together, so neither can linger stale into a later state.

17. **`pauseOnZoom: boolean`** (default `false`) **and `pauseOnRotateFlip: boolean`** (default `false`) — pause the slideshow while the viewer is actively engaged with the Zoom/RotateFlip plugins, a real UX gap: nothing stopped it from auto-advancing out from under someone mid-zoom examining a detail. Only reacts to `zoomChange`/`rotateFlipChange`'s event *shapes* (`core/types.ts`) — never imports either plugin directly, so both are a complete no-op with the corresponding plugin not loaded (events over inheritance, CLAUDE.md). Both **opt-in, off by default** — `pauseOnZoom` shipped defaulting `true` initially, then was changed to match `pauseOnRotateFlip`'s own off-by-default, requested directly: a host embedding Autoplay shouldn't have its slideshow's pause behavior silently change the moment Zoom happens to also be loaded, unless it explicitly asked for that interaction between the two plugins.

    **Deliberately stays paused rather than auto-resuming once back at neutral — a real bug, reported from real usage against the first design, which tried the opposite.** That first attempt edge-tracked a combined "engaged" state and auto-resumed on disengage, mirroring point 16's own drag-to-close pause/resume. Two real problems, found testing it directly: (1) play → rotate (pauses) → manually press Play again while still rotated → rotate further — the second rotate didn't re-pause, and the slideshow kept advancing. The edge-tracker was already reading "engaged" from the first rotate and never cleared (the viewer hadn't un-rotated), so an early-return guard on "no change since last time" skipped ever re-checking whether the slideshow was actually still playing — which *had* changed, via the manual restart in between. (2) Once fixed, reported again: rotating back to the *original* orientation didn't pause either — confirmed the fix wasn't the auto-resume behavior itself so much as the whole premise: landing back on neutral isn't the same as "the viewer is done." They might rotate back and forth several times before deciding. Redesigned to never auto-resume at all — pausing is a one-way action here, same as a manual pause, requiring an explicit Play press to continue — which also let the whole edge-tracking mechanism (and its own bug class) be deleted outright. `scale > 1` still gates *which* `zoomChange` events pause: an ordinary scale-1 event can also fire from an unrelated slide-change reset (`zoom/index.ts`'s `reset()`, itself fixed to emit at all — see §4.6), not a real interaction, so it can't unconditionally pause on every event the way `rotateFlipChange` safely can (every one of those only ever fires from a real button/shortcut click; `rotateFlip/index.ts`'s own per-slide `reset()` never emits it).

    **A third real bug, found immediately after: zooming in *first*, then pressing Play, ran the slideshow unpaused instead of catching it at all.** Clicking Play doesn't itself fire `zoomChange`/`rotateFlipChange` — nothing was listening for "is the view already engaged at the moment playback starts." Worse, a single-step "toggle straight back to neutral" action taken afterward (Actual size, double-tap-to-reset) only ever emits the *already-neutral* event — never one crossing the engaged threshold — so nothing downstream would have caught it that way either. Fixed by tracking the *current* zoom/rotate-flip state purely for this one check (`zoomedIn`/`rotatedOrFlipped`, deliberately not reused by the reactive pause-on-event logic above, which still reacts to each event directly): `toggle()`'s manual-start path re-checks both immediately after calling `start()`, re-pausing on the spot if either is already true. Scoped to the manual toggle only, not `autoStart`/the drag-close resume's own `start()` calls — both of those are only ever reached with the view already guaranteed neutral (RotateFlip/Zoom both reset on `afterOpen`), so the check would be a structurally-guaranteed no-op there, and depending on it would be fragile against plugin registration order. Both tracking booleans are resynced to `false` on `afterSlide`/`afterOpen`, the same staleness class as the `scale > 1` gate above — an outgoing slide's engagement must not leak into a fresh one's "was it already engaged" reading.

    **The asymmetry between the two options — zoom excludes the "back to scale 1" event, RotateFlip pauses on every event unconditionally — is a deliberate, discussed tradeoff, not an oversight.** RotateFlip has no equivalent gate to begin with (every `rotateFlipChange` is provably a real click), so there was nothing to reconcile there. For zoom, the `scale > 1` gate could very likely be dropped too — given the two fixes above, `playing` is provably already `false` by the time any reset-driven `scale: 1` event could fire while `pauseOnZoom: true`, since the zoom-in that produced it would already have paused things synchronously — but left in place on request rather than simplified, since it isn't costing anything either way.

    **A fourth real gap, asked about directly rather than reported as broken: pressing Play while resume is blocked gave no visible feedback that anything happened at all.** `toggle()`'s own re-check (above) re-pauses synchronously, in the same tick as the manual start — no `transitionend`, no paint in between the two button-state flips, so the button never actually shows "Pause" for even a frame before reverting; a click just silently did nothing. Fixed by disabling the Play button (`aria-disabled` + `tabIndex = -1` + `pointer-events: none`, the same pattern core's own slide-loading disable already uses — `Gallery.ts`'s `setSlideLoading()`) whenever pressing it wouldn't actually take, so "can't resume yet" is an honest, visible state rather than an apparently-broken button. Only while *not* playing — while playing, the button always means Pause and must stay clickable regardless of zoom/rotate state. Deliberately doesn't disable the `Space` shortcut, which bypasses the button's own interactive state entirely and still needs `toggle()`'s re-check to work correctly — the button being disabled makes a *mouse* click impossible, but the underlying re-check logic stays real, load-bearing code, not dead weight the disabled button alone would make unreachable.

**Deliberately deferred, not part of this pass**: `shuffle` and pause-on-hover. Add anything here if/when actually requested rather than speculatively; the core video-interrupt state machine above was the part worth getting exactly right first.

### 4.2 Active thumbnail tracking (`src/plugins/activeThumbnail`)

`new Shoji(el, { plugins: [Shoji.ActiveThumbnail] })` — no options object needed. Keeps the host's own thumbnail grid in sync with whichever slide is open in the lightbox: as `activeIndex` changes by *any* means (arrow keys, prev/next buttons, a completed swipe, autoplay ticking, a plugin calling `goTo()`), the corresponding origin thumbnail gets an active class (`activeClass`, default `'shoji-thumb-active'`) and — by default (`scrollIntoView`, default `true`) — is scrolled into view (`block: 'nearest'`, honoring `prefers-reduced-motion`).

Opt-in, not core: CLAUDE.md's "everything that can be a plugin is a plugin" — a host whose grid always fits on screen, or who doesn't want the page scrolling under them mid-slideshow, can leave it off, or enable it with `scrollIntoView: false` for the highlight alone.

Reuses `Gallery.getOriginElement(index)` — the same index→thumbnail lookup the zoom transition (§2.3b) already relies on — rather than re-deriving it, so this plugin's coverage exactly matches the zoom transition's: `scannedElements[index]` in selector mode, `data-shoji-id="<item.id>"` markers elsewhere, including the layout plugin's own tiles (which set that attribute automatically whenever `item.id` is present). `getOriginElement` was previously a private `Gallery` method (`findOriginElement`) used only internally by the zoom transition; made public for this plugin to reuse, same pattern as `getActiveMedia()` being public for autoplay's video-locating need (§3.1).

The `scrollIntoView` call is debounced 80ms (reset on every navigation, canceled on close), not fired synchronously on every `afterSlide`/`afterOpen`. Reported and reproduced from real usage: navigating faster than a single native smooth-scroll animation can finish (autoplay ticking, or just clicking quickly) issues one `scrollIntoView` call per step, each interrupting the last — overlapping, unsettled scroll animations that don't simply get superseded. Waiting a short beat before actually scrolling, and restarting that wait on every subsequent navigation, means a rapid burst issues exactly one real `scrollIntoView` call, for wherever the viewer actually lands, instead of one per step. The highlight (`classList.add`) is unaffected either way — only the scroll is debounced. Note this does not (and cannot) make the scroll itself instantaneous: `behavior: 'smooth'` is a genuine, browser-timed animation, so a click immediately followed by closing the gallery can still leave that animation completing its last ~100-300ms after the dialog is gone — confirmed via direct testing to always converge on the *correct* thumbnail position, never a snap back to the gallery's original open point (that was a distinct, separate bug in `FocusTrap.deactivate()`, fixed above, §2.6). A page continuing to smoothly scroll toward the right place for a moment after closing is expected, ordinary `scrollIntoView` behavior, not something to suppress.

The active class is cleared on `close()` (not left highlighting a thumbnail the viewer isn't looking at anymore) and re-applied from whatever index the next `open()` lands on. Shoji ships no default *styling* for `.shoji-thumb-active` — only the class toggling — since the thumbnail markup it's applied to is host-authored (or the layout plugin's, which doesn't have an opinion on "active" styling either); the host defines what "active" looks like.

**A real bug, found via a real integration (layout `groupBy` + most items missing `width`/`height`)**: the highlight would silently vanish mid-session, on a page that otherwise looked identical to Shoji's own docs example. Root cause: this plugin held a direct `HTMLElement` reference (`current`) to the tile it last marked active, but the layout plugin's own `groupBy` option always fully re-renders on any `autoMeasure` correction landing, not just on a real `updateSlides()` call (§5, "grouped changes always fully re-render") — `container.replaceChildren()` plus a fresh `createTile()` per item, discarding every existing tile element outright. `current` was left pointing at a now-detached node; the class was technically still "applied," just on an element no longer in the live DOM, so the highlight disappeared from the page with nothing else visibly wrong. Reproduced only with most items relying on `autoMeasure` (a single correction is enough to trigger the grouped full re-render) — small test galleries with explicit `width`/`height` on every item, like the docs example, never hit it, which is why it looked plugin-specific to "my custom page" until traced to the interaction. Fixed by tracking `currentIndex` (not just the resolved element) and listening for the layout plugin's own `layoutRender` event (already emitted at the end of both `fullRender()` and `appendRender()`, §5.3, originally added so a host can inject content into freshly-built tiles) to re-resolve and re-mark the rebuilt tile via `getOriginElement()` — the same `data-shoji-id` lookup still finds it, since `createTile()` sets that attribute on every rebuild regardless. Deliberately does *not* re-trigger the debounced `scrollIntoView` from that path (a `layoutRender` firing means the DOM changed, not that the viewer navigated) — split into a scroll-free `applyClass()` used by both the real navigation path and the re-mark path. Covered by `tests/unit/plugins/layout-activeThumbnail.test.ts`.

### 4.3 Video (`src/plugins/video`)

`new Shoji(el, { plugins: [Shoji.Video] })` — no options object needed. Renders `{ video: { provider: 'youtube' | 'vimeo', id } }` items as a real `<iframe>` embed; core's own `SlideManager` only knows how to build a native `<video>`, for `provider: 'html5'`. Wistia is not a supported provider at all — removed from `VideoDescriptor` (§2.1) rather than deferred; no use case has asked for it, and it would've been a whole third provider's worth of surface (host detection, a renderer, `id`-required validation in `scan.ts`) with nothing exercising it.

**The core hook this needed** (`ctx.ui.registerVideoProvider(name, renderFn)`, §3): a provider-renderer registry, keyed by provider name, that `SlideManager` consults whenever `item.video.provider !== 'html5'`. `renderFn(container, item, onReady, signal)` builds into `container` and calls `onReady()` once it should show; `SlideManager` shows the loading spinner until then, same as any other slide. No returned cleanup callback — `signal` fires `'abort'` once the slide is no longer wanted (evicted from the preload window, or `destroy()`) instead, since a provider's setup is often genuinely async (loading its SDK can take a while on first use) and a synchronous return value has no way to capture cleanup for work that hasn't finished yet; a returned-callback design would leak whatever eventually gets created — a player instance still running, invisible, forever — if eviction happened first. `'custom'` (already typed on `VideoDescriptor`) uses the identical signature via the item's own `render`, not the registry, since it's inherently one-off per item rather than shared across every item from a given provider.

**A real bug, found building this**: a provider's `container` was originally built off-document and only attached to the real DOM once `onReady` fired (mirroring `ensureImageDecoding`'s image-decode pattern, §2.3) — but an `<iframe>`, unlike an `<img>` mid-decode, only actually loads its content once attached to the *live* document; a detached one never fires anything, so `onReady` never came. Confirmed directly: constructing a `YT.Player` against a detached mount reliably builds the real `<iframe>` element but never calls its `onReady` callback, while the identical setup against an attached one resolves normally. Fixed by attaching `container` to the real DOM immediately — hidden (`[hidden]`, same pattern as `.shoji-caption`/`.shoji-close`), behind the still-visible spinner — instead of deferring attachment until ready; only *revealing* it (and marking the slot ready) waits for `onReady`.

**No poster/thumbnail handling at all** — deliberately: the slide shows the loading spinner until the embed itself is ready, never an auto-fetched or host-guessed preview image. A YouTube thumbnail *is* fetchable without an API call (a predictable `img.youtube.com/vi/<id>/hqdefault.jpg` URL), but that's scoped to whatever the host wants to show in their own *thumbnail grid* (page-level, unrelated to Shoji) — not something this plugin does on their behalf for the lightbox slide itself.

**Autoplay integration (§4.1) works without Autoplay knowing YouTube or Vimeo exists.** `renderYouTube`/`renderVimeo` each augment `container` with `.play()`/`.pause()`/`.paused`/`.ended`/`.muted` plus real `play`/`pause`/`ended` DOM events — the same shape `HTMLVideoElement` already has, driven by each provider's own player-state callbacks (YouTube's `onStateChange`; Vimeo's `player.on('play'|'pause'|'ended', ...)`). Autoplay's own `findPlayable()` looks for a native `<video>` first, then falls back to `.shoji-slide-provider-video` if it's been wired up this way; the rest of its video-aware state machine (§4.1) runs completely unmodified, treating either provider's slide exactly like a native video one.

**A real bug: `wirePlayableContract` must run from the real `onReady`, not synchronously after `new YT.Player()`.** The constructor returns before the player's own internal bootstrap (its postMessage handshake with youtube.com) finishes — calling `player.mute()`/`unMute()`/`isMuted()` (or even `playVideo()`/`pauseVideo()`) against that window can throw (`player.isMuted is not a function`) or silently no-op, even though the constructor already handed back an object. Confirmed directly: reaching for `.muted`/`.play()` right after construction, before YouTube's own `onReady` event fires, is unreliable; the identical calls made after `onReady` are not. This matters beyond just avoiding the throw — `wirePlayableContract` running early meant `.play` existed on `container` before the real player could reliably act on a call, which is exactly the gap Autoplay's `findPlayable()`/`isPendingProviderVideo()` (§4.1 point 7) are relying on `.play` wired = genuinely ready to rule out. Fixed by moving the `wirePlayableContract(container, player)` call into the `onReady` event callback itself, ahead of invoking the `onReady` param — so `.play` only appears once YouTube's own readiness signal has actually fired, restoring that invariant.

**`onError` is surfaced as a plain, provider-agnostic DOM event, not a Shoji-specific API.** YouTube's IFrame API reports playback failures (invalid video ID, HTML5 player error, video not found/private, embedding disabled by the owner, plus undocumented codes seen in the wild) via its own `onError` callback — entirely separate from `onStateChange`, and not guaranteed to be preceded by `onReady` at all (a removed or private video can error out before ever becoming ready). `renderYouTube` dispatches `new CustomEvent('error', { bubbles: true, detail: { code: event.data } })` on `container` whenever it fires. `bubbles: true` is what lets Autoplay (§4.1 point 11) catch it from `.shoji-slide-media` without needing `wirePlayableContract` to have run first; the numeric code is passed through as-is in `detail.code` rather than special-cased per value, since Shoji has no way to give a viewer-facing meaning to most of them beyond "this one didn't work, move on."

**Detection**: `scan.ts` (§2.1) recognizes `youtube.com`/`youtu.be`/`youtube-nocookie.com` and `vimeo.com`/`player.vimeo.com` hosts in a `data-shoji-video` URL and extracts the id automatically — cheap, dependency-free URL parsing, not either provider's SDK, so this stays in core rather than needing a plugin-owned scanning hook (which doesn't exist). Anything not matching a known host falls back to the existing html5 treatment (the URL as a direct source). Vimeo's id extraction takes the first numeric path segment (`vimeo.com/<id>`, `vimeo.com/<id>/<hash>` — an unlisted video's privacy hash, `player.vimeo.com/video/<id>`, or a numeric id buried deeper as in `vimeo.com/channels/<name>/<id>`) — the resolved item keeps the original `url` alongside `id`, not just the bare id, specifically so `renderVimeo` can pass the whole URL (hash included) to the player instead of losing it.

**Vimeo's Player SDK (`player.vimeo.com/api/player.js`, `window.Vimeo.Player`) is fully Promise-based, unlike YouTube's mostly-synchronous IFrame API** — `play()`/`pause()`/`setMuted()`/`ready()`/`destroy()` all return promises, and there's no synchronous `isMuted()`-style query at all. `renderVimeo`'s `wirePlayableContract` mirrors `.muted` as a locally-tracked value instead of reading the player live: the setter still genuinely forwards to `player.setMuted()` (not inert), but the getter reflects the last value *set*, not necessarily the player's true current state. Harmless in practice — nothing in Autoplay ever reads `.muted` back, only sets it (§4.1 point 8's `video.muted = true` before an automatic play). `player.ready()` is Vimeo's equivalent of YouTube's `onReady` event — `wirePlayableContract` runs from its resolution, same reasoning as the YouTube real-bug entry above (don't let `.play` exist before the player can reliably act on it).

**Vimeo playback getting stuck was initially misdiagnosed as an environment-level Cloudflare bot check — the real cause was Autoplay's own retry loop reissuing `play()`, fixed at §4.1 point 13.** Worth recording precisely because the wrong diagnosis was plausible and directly actionable-looking (a real Cloudflare Turnstile challenge was observed when probing `vimeo.com` directly outside the embed context) before the actual mechanism was isolated: a single, uninterrupted `play()` call reliably started real Vimeo playback in ~1.6s in the exact same environment, proving the embed's own network access was never the problem. `tests/e2e/plugins/video.spec.ts`'s Vimeo autoplay test reliably confirms `paused: false` outside CI now, same as the YouTube one.

**Sizing `.shoji-video-mount` (Vimeo's own wrapper div) took three iterations to get right — a real bug, reported from real usage, chased through in sequence:**
1. Left at its own defaults, Vimeo's SDK sizes `mount` to a small fixed box (its own embed default, ~640x360) via inline styles — `.shoji-slide-provider-video iframe`'s `width/height: 100%` CSS rule (§4-video) only ever resolved relative to that fixed-size `mount`, not the actual slide, so the embed rendered small, in a corner, instead of filling the dialog.
2. `responsive: true` (a genuine SDK option) looked like the fix, and does make `mount` fill its parent's *width* — but computes `mount`'s *height* from that width times the video's own native aspect ratio via a padding-percentage trick, entirely ignoring how much vertical space the slide actually has. Confirmed directly at a wide-but-short viewport (1920x1000, container height 1000): the resulting iframe came out 1080px tall — over 100px taller than its container, pushing the bottom of the video (and Vimeo's own scrubber/controls bar, always along that same edge) below the visible area. YouTube's iframe has no such wrapper or aspect-driven height at all, unaffected either way.
3. Dropping `responsive` and instead forcing `mount`'s `width`/`height` to a flat `100% !important` each (discarding whatever the SDK sets inline) fixed that, but traded it for a third bug, reported next: stretching regardless of the video's real 16:9 shape exposed the provider's own internal letterbox color instead of Shoji's theme.

Final fix: `.shoji-video-mount` (and `.shoji-slide-provider-video > iframe`, YouTube's equivalent direct-child case, no wrapper involved) use `width: min(100cqw, 100cqh × 16/9)` / `height: min(100cqh, 100cqw × 9/16)` — the same *contain* formula `object-fit: contain` gives an `<img>`/`<video>` natively, expressed with CSS container query units since `object-fit` doesn't apply to a non-replaced element like a div/iframe. Plain `aspect-ratio` alone can't do this either: it only ever derives *one* dimension from the other, so whichever of width/height stays a fixed `100%` never actually shrinks once the derived dimension gets capped by `max-width`/`max-height` — confirmed directly, this silently distorted the ratio in whichever direction wasn't the binding constraint. `.shoji-slide-provider-video` sets `container-type: size` to make `cqw`/`cqh` resolve against its own content box (the top gutter's padding already excluded) — safe to establish there since its own size already comes from its parent, never from whatever ends up inside it. Verified at both a wide-short and a narrow-tall viewport, matching real 16:9 exactly in both.

**The internal-letterbox-color problem the contain fix above solves is a hard constraint, not a preference: neither YouTube's nor Vimeo's own player page renders with a background matching Shoji's theme in a letterboxed gap — both showed white — and that content is cross-origin, so it can never be restyled from here.** Fitting the embed to its actual aspect ratio instead of stretching it means any *remaining* gap is outside the iframe, where `.shoji-slide-provider-video`'s own (deliberately unset, transparent) background lets Shoji's real dark backdrop show through instead.

**`.shoji-slide-provider-video` reserves a top gutter (`--shoji-provider-video-top-inset`, default matching the toolbar's own rendered height) so the embed's own hover-revealed title bar never sits under Shoji's toolbar — a real bug, reported from real usage, the same shape as §2.3a's bottom-controls one but at the opposite edge.** Shoji's toolbar (§3.1) is always on top, `position: absolute` over the slide; a provider video that fills most of the dialog leaves little to no letterboxing gap at the top either, so a provider's own title/channel bar (YouTube's, shown on hover, same corner) can end up directly under Shoji's own toolbar buttons. Unlike the caption case, there's no click-through or hide-by-default fix available here — every pixel of the toolbar is a real, always-needed control (close in particular can't be hidden), so the only fix that actually works is giving the two their own separate space: `box-sizing: border-box; padding-top: var(--shoji-provider-video-top-inset);` on the container, permanently — not tied to the toolbar's own auto-hide state, since moving the pointer toward the video's top edge to reach the provider's own UI is itself the gesture that resets Shoji's idle timer and re-shows its toolbar, so auto-hide can never reliably clear out of the way right when it's needed to. Applied at the shared `.shoji-slide-provider-video` container level, so it protects any provider automatically — confirmed for Vimeo too (`tests/e2e/plugins/video.spec.ts`), no Vimeo-specific gutter work needed. HTML5 video is untouched: native `<video controls>` never renders anything at the top of the element in any current browser, only a bottom bar, so there's nothing to protect there.

### 4.4 Fullscreen (`src/plugins/fullscreen`)

`new Shoji(el, { plugins: [Shoji.Fullscreen] })` — no options object needed. A toolbar toggle button (`'right'` slot) puts `ctx.ui.outer()` — `.shoji-outer`, the *whole* lightbox (backdrop, dialog, controls), not just the slide media — into the browser's native fullscreen mode. No toolbar button at all (not a disabled one) on a browser with no Fullscreen API support at all, checked once via `document.fullscreenEnabled`/the vendor-prefixed `webkitFullscreenEnabled` (historically Safari on iOS) — nothing to control there, so nothing is shown.

**Button state is driven by the native `fullscreenchange` event (plus its `webkitfullscreenchange` vendor variant), not the click handler directly.** A `requestFullscreen()`/`exitFullscreen()` call can be rejected (another element already fullscreen, a permission policy) and the browser's own Escape-key fullscreen exit never goes through this plugin's click handler at all — reacting to the event instead of the request keeps the button's icon/`aria-pressed`/`aria-label` correct regardless of *why* fullscreen state changed, including changes this plugin didn't initiate itself.

**Closing the gallery while fullscreen exits fullscreen explicitly**, rather than relying on the browser's own Escape-triggers-fullscreen-exit behavior — that behavior is inconsistent across browsers (some exit fullscreen *and* still deliver the page its own Escape keydown, some don't), and leaving the *page* stuck in fullscreen mode after the *lightbox* it was fullscreening is already gone would be a real, confusing UX bug.

Emits `fullscreenChange: { fullscreen: boolean }` on the gallery bus (same "reacts to the real event, not the request" sourcing) for a host that wants to know without polling `document.fullscreenElement` itself.

### 4.5 Rotate/flip — view only (`src/plugins/rotateFlip`)

`new Shoji(el, { plugins: [Shoji.RotateFlip] })` — no options object needed. Four toolbar buttons (`'right'` slot: rotate left, rotate right, flip horizontal, flip vertical) apply a CSS `transform` to the active `.shoji-slide-media` — non-destructive, resets to neutral on every `afterOpen`/`afterSlide` (per-slide, not per-gallery, matching the roster bullet's own wording exactly). Distinct from the (unbuilt) Editor plugin's own rotate/flip (§8), which is destructive and persisted server-side via `item.edits` — this one has no persistence of its own by design; a host that wants to keep a rotation stores the emitted `rotateFlipChange` event's payload themselves and re-applies it however they choose (this plugin has no "seed from a starting orientation" input, only output).

**Composition order matters and is non-obvious** (CLAUDE.md flags this by name: "Flip + rotate compose non-commutatively"): the applied transform is `scaleX(...) scaleY(...) rotate(...)deg)`, flip functions listed *before* rotate in the string. CSS transform functions apply right-to-left to the content, so `rotate()` (rightmost) acts on the image first, and the flip (leftmost) acts on that *already-rotated* result — this is what makes "flip horizontal" mean "mirror what you're currently looking at," not "mirror the original un-rotated image," which is the intuitive expectation for a viewer clicking the button.

**Shares `src/core/rotateFlipNormalize.ts`'s canonicalization with the future Editor plugin**, rather than each re-deriving the composition — the exact table from §8.1, verbatim: `flipH && flipV` always canonicalizes to no flips + rotation+180°, applied on every state change. This isn't just for internal tidiness: it means two different click sequences that are visually equivalent (rotate 90° then flip both axes, vs. rotate 270° directly) produce byte-identical emitted `rotateFlipChange` payloads and toggle-button `aria-pressed` states — a host storing/comparing these values sees the same result either way, and rotation never grows unbounded across repeated clicks (`((r % 360) + 360) % 360` on every update).

**Button clicks animate; the per-slide reset doesn't** — same "discrete jumps animate" pattern the Zoom plugin (§4.6) already established: each of the four buttons is a one-shot state change, not a continuous gesture, so `apply(animate: boolean)` wraps it in `transition: transform var(--shoji-duration) var(--shoji-easing)` before writing the new transform, clearing the inline `transition` once it ends (`waitForTransitionEnd`, reused from `zoomTransition.ts`) so it doesn't linger onto that module's own later use of this same element's `transform`. `reset()` (on `afterOpen`/`afterSlide`) stays unanimated — there's nothing to visibly animate *from* on a slide the viewer never rotated.

**A real bug, reported from real usage: a full rotation (four rotate-right clicks) visibly spun backward instead of continuing forward.** The animated transform used `state.rotation` directly — the *normalized* value, wrapped into `[0, 360)` by `normalizeRotateFlip` (so state stays bounded and two click sequences reaching the same orientation compare equal, per this section's own composition-sharing note above). A fourth rotate-right click computed `270 + 90 = 360`, normalized down to `0` — so the CSS transform animated straight from `rotate(270deg)` to `rotate(0deg)`. A browser has no notion that `0deg` and `360deg` look identical; it interpolates the literal numeric delta, so a 270°→0° transition is a 270° *decrease*, visibly spinning backward almost a full turn instead of continuing the same 90° forward step the viewer was clicking through. Fixed by decoupling *what's animated* from *what's normalized*: a second, unbounded `visualRotation` counter (90, 180, 270, 360, 450, ... — never wrapped) now drives only the CSS `rotate()` degrees; `state.rotation` keeps its existing wrapped/normalized role everywhere else (the emitted `rotateFlipChange` payload, the flip+rotate canonicalization math) completely unchanged.

**A second real bug, found immediately after, same class: flipping horizontal then vertical animated a visible "twist" instead of a plain flip — the end orientation was correct, only the path there looked wrong.** `normalizeRotateFlip` collapses `flipH && flipV` into `{flipH: false, flipV: false, rotation: rotation + 180}` (this section's own composition-sharing note, above) — correct for *state*, but animating straight to that collapsed form means the CSS transform changes *both* `scaleX` (back to 1) *and* `rotate` (up to 180°) in the same transition. Since both are in the same transform-function list, the browser interpolates each independently and simultaneously — `scaleX` un-squishing while `rotate` spins a half-turn at the same time, a compound motion that doesn't resemble either a flip or a rotation. Fixed the same way as the first bug: `visualFlipH`/`visualFlipV`, two more raw, independent booleans decoupled from `state`'s own canonicalized ones, toggled directly by their own button (never collapsed). This works cleanly because flipping both axes is algebraically identical to a 180° rotation *regardless of whatever rotation is already applied* — so the raw, uncollapsed representation and the canonical one always land at the same final visual result, only the animated path differs. A flip click that would trigger the canonicalization now animates as a plain, single-axis `scaleY` (or `scaleX`) change — the normal flip motion the button implies — while `state`, `aria-pressed`, and the emitted `rotateFlipChange` payload still canonicalize exactly as before, completely unaffected.

**A third real bug, reported from real usage: with exactly one flip axis active, "Rotate right" visibly spun the image counter-clockwise instead.** Both rotate buttons unconditionally applied a fixed `±90` raw delta to `visualRotation`, regardless of flip state — correct while unflipped, but wrong once mirrored: `scaleX(-1)`/`scaleY(-1)` is a reflection (determinant `-1`), and composing a reflection with a rotation reverses that rotation's *visual* handedness (a `+90` raw delta that reads as clockwise unflipped reads as counter-clockwise once mirrored on a single axis) — provable directly from the matrix product `ScaleX(-1) · Rotate(θ) = Rotate(-θ) · ScaleX(-1)`. Flipping *both* axes doesn't have this problem: two reflections compose back into a plain rotation (determinant `+1`, same as no flip at all) — exactly why `normalizeRotateFlip` already collapses that combination into a plain 180° rotation (this section's composition-sharing note, above). Fixed by inverting the raw delta (`rotateDelta()`) whenever `visualFlipH !== visualFlipV` (XOR — exactly one axis flipped): both `visualRotation` (the animated value) and `state.rotation` (the canonicalized, emitted one) get the same inverted delta, so the two stay in lockstep and `rotateFlipChange` remains an accurate description of what's actually on screen, not just the CSS transform. Covered by both a unit test (`tests/unit/plugins/rotateFlip.test.ts`) asserting the animated transform's sign directly, and an e2e regression test (`tests/e2e/plugins/rotateFlip.spec.ts`) against a real browser.

**A fourth real bug, reported from real usage: on a narrow (mobile) viewport, rotating a photo painted `.shoji-slide-media` well outside its own bounds, cropped by `.shoji-slides`' `overflow: hidden` rather than shrunk to fit.** `.shoji-slide-media` is always its full box (`width`/`height`: 100%) — rotating it by an odd multiple of 90° swaps its own footprint's width/height, and for a non-square container (the common case, especially on mobile) the swapped footprint no longer fits back within the original space, so the far edges were simply clipped away instead of the whole rotated photo shrinking to remain visible. Fixed by `fitScaleFor()`: multiplies a scale factor into `scaleX`/`scaleY` (folded directly in, not a separate `scale()` — a single uniform factor commutes with everything else already in the transform, so this is exactly equivalent without adding a fourth transform function) whenever `rotationDeg` is an odd multiple of 90. `1` (a no-op) for 0°/180°, where a rectangle's own bounding box is unchanged by a half-turn.

  **Two real wrong turns on the way to the right formula, both caught from real usage before settling.** *Attempt 1* scaled based on the photo's own contain-fit box (`containedBox()`, `zoomTransition.ts`, reasoning only the *visible* photo needed to stay contained, not the full container) — wrong, because rotate/flip is applied to `.shoji-slide-media` itself, not the `<img>` (unlike the Zoom plugin, §4.6, which deliberately targets the image so the two nest without conflicting): the *entire container*, invisible letterbox margins included, rotates as one rigid unit, and those margins — not the photo — were what was actually overflowing. Confirmed directly: `.shoji-slide-media`'s own rendered box still exceeded `.shoji-slides`' bounds after "fitting" to the image's smaller box alone. *Attempt 2* over-corrected: switched to `min(mediaWidth / mediaHeight, mediaHeight / mediaWidth)` — the container's own shape alone, ignoring the photo's aspect ratio entirely. This can never overflow (the image's contained box can never exceed the container's own in either dimension, so the container-only scale is always the more restrictive one) — but it was reported back as a real regression: an already near-full-bleed photo (container and photo sharing a similar aspect ratio, minimal letterboxing) shrank dramatically on rotation instead of staying roughly the same size, since the scale now came from the *container's* shape, margins included, rather than the photo's actual, usually much less extreme one. **The actual fix uses the photo's contain-fit box after all** (`containedBox()`, restored) — attempt 1's instinct was right, its diagnosis of what broke it wasn't: the container's own margins genuinely can still paint outside `.shoji-slides` with this formula, but that turns out to be harmless on both counts — `.shoji-slides`' `overflow: hidden` already clips them (invisible, nothing to see) and the page itself no longer grows from it either, handled independently by locking `<html>`'s own `overflow` while the lightbox is open (§2.6a) — so there was never a real conflict between "the photo stays a good size" and "nothing actually overflows visibly or breaks the page." Covered by a unit test suite (`tests/unit/plugins/rotateFlip.test.ts`, including `item.width`/`height` vs. the `<img>`'s own natural-dimension fallback) and an e2e regression test asserting the `<img>`'s own real rendered box — not `.shoji-slide-media`'s — against `.shoji-slides`' bounds in an actual browser (`tests/e2e/plugins/rotateFlip.spec.ts`), which emulates `prefers-reduced-motion: reduce` to collapse `--shoji-duration` to `0ms`, avoiding a real flake where `getBoundingClientRect()` briefly reflects a larger mid-transition bounding box than the settled end state under parallel-test CPU contention (a non-square rectangle's rotated bounding box peaks partway through a 0→90 sweep, not at either endpoint — same reasoning as the mobile viewport-widening bug, §2.6a).

  **A follow-up correction, reported from real usage once the formula above shipped: growing a small photo felt wrong, even though shrinking a large one looked right.** The formula above always recomputes the photo's *ideal* best-fit size for its new orientation — the same "biggest size that doesn't crop" rule applied fresh after every turn — which can grow a small, heavily letterboxed photo just as readily as it shrinks a large one. Technically consistent, but not what was wanted: a small photo visibly ballooning on rotation reads as a glitch, precisely because nothing that dramatic happens to a large photo in the same rotation. **First attempt at a fix: cap the result at `1` outright — shrink to avoid clipping, never grow.** This *did* fix small photos, but was too blunt, and was itself reported back as a regression: a genuinely large, high-resolution photo (6144×8160, letterboxed on a 1080p monitor because its portrait shape doesn't match a landscape screen) also got capped from growing to fill the newly-available width after rotating — even though a photo with that much native resolution has far more pixels than a 1080p screen could ever need, so growing it costs nothing in quality. The flat `1` cap couldn't tell these two cases apart, because it was answering the wrong question: "was the photo already filling the screen" instead of "does the photo have the resolution to grow without becoming blurry." Those are different questions — a small, low-res photo and a small-*looking*-but-actually-huge photo can be letterboxed identically, yet only one of them should be allowed to grow.

  **The attempted fix above (`resCeiling`, computed from `idealFit`'s already-wrong `containedBox()` baseline) caps growth against the photo's own native pixel resolution — the right idea, but still built on the same flawed foundation `containedBox()` supplied, and it too was reported back as a bug from real usage on the docs site itself.** `containedBox()` (and `idealFit`, built from it) assumes `.shoji-slide-img` always scales to *touch* the container on at least one axis — standard `object-fit: contain` behavior. That's not what the actual CSS does: `.shoji-slide-img` is `max-width: 100%; max-height: 100%` — a *cap*, not a forced fill (`shoji.css`'s own comment explains why: real photos are assumed bigger than the slide area, so never growing past natural size is the correct default). A photo smaller than the dialog in both dimensions — a small placeholder, or any photo on a big-enough screen — just renders at its own native size, touching *no* edge at all. Confirmed directly on the real deployed docs page: an 800×600 test photo in a 1920×950 window rendered at exactly 800×600, not the ~1267×950 `containedBox()`/`idealFit` assumed. Since `idealFit` started from that wrong, imagined size, the resulting scale shrank the photo relative to a size it was never actually rendered at — a real, visible shrink of a photo that should not have changed size at all.

  **The actual fix drops `containedBox()`/`idealFit`/`resCeiling` entirely and replaces the whole two-step calculation with one formula that mirrors the real CSS directly, at both orientations, and compares the two.** `scaleAt0 = Math.min(1, mediaWidth / naturalWidth, mediaHeight / naturalHeight)` is exactly `.shoji-slide-img`'s own `max-width/max-height: 100%` rule — the real render scale (relative to native pixels) for the *current* orientation, capped at `1` so it can shrink to fit but never grow past native size, precisely matching what the browser itself would render unrotated. `scaleAt90` is the identical calculation with `naturalWidth`/`naturalHeight` swapped — the same "what would the browser render this at" question, asked for the *rotated* orientation. The fit-scale is simply their ratio, `scaleAt90 / scaleAt0`: how much more (or less) of its own native resolution the rotated orientation can use compared to what's already on screen. This single ratio subsumes everything the two-step formula was trying to do, correctly and for free — neither term can ever exceed `1` (native resolution is never exceeded, in *either* orientation, not relative to a possibly-wrong assumed starting point), and whichever term is constrained by the *container* rather than by native resolution still shrinks or grows the ratio exactly as far as that constraint requires, with no separate floor/cap step needed. `containedBox()` is no longer imported from `zoomTransition.ts` by this file at all. Covered by regression tests (unit and e2e) for: a low-resolution photo that renders untouched and stays untouched when rotated (the real bug, reproduced with no `item.width`/`height` at all — the exact path the bug went through, relying purely on the `<img>`'s own `naturalWidth`/`naturalHeight`, on a wide desktop-shaped viewport matching the real report); a high-resolution photo growing fully; a photo with partial resolution headroom growing only part of the way; a photo that fits fine unrotated but still needs to shrink once rotated (orientation mismatch, not a resolution limit); and the pre-existing large-photo shrink case, unaffected. The wrong-turn/right-turn narrative across all of these matters for future maintainers: "large vs. small," "was it letterboxed," and even "cap the ideal-fit result against native resolution" all turned out to be the wrong shape for this problem — computing the *real* CSS render scale at each orientation and comparing them directly was the one formula that didn't need a second correction on top of it.

**A fifth real bug, reported from real usage: rotating a particular photo never resized to fit the window at all — fit-scale silently computed to exactly `1` (a no-op) every time, no matter the photo's actual resolution.** Only affected items sharing one specific shape: a dynamic-mode `thumb` genuinely different from `src`, and no explicit `item.width`/`height`. First theory (wrong, disproven below): rotating while only `SlideManager`'s open placeholder (§2.3 — a low-res `item.thumb` stand-in, sharing the real `<img>`'s own `.shoji-slide-img` class) had loaded would read the *placeholder's* `naturalWidth`/`naturalHeight` via `resolveNaturalSize()`'s `media.querySelector('img')` fallback, computing a scale against the wrong image. Investigating this turned up a contradiction that disproved it outright: `Gallery.ts`'s `setSlideLoading()` keeps every toolbar button (rotate included) `aria-disabled`/`pointer-events: none` until `slideItemLoad` first fires for the active index — the exact same event that marks the real image ready — so a genuine click can never land while only the placeholder is showing. Two independent real-browser reproduction attempts using a large photo with a genuinely separate thumbnail both computed the fit-scale correctly, failing to reproduce the bug and confirming the toolbar-disabled path made the theory unreachable. The real cause, found afterward from the user's own live diagnostics, was in a different plugin entirely: Layout's `autoMeasureTiles()` (§5) was writing its own tile-thumbnail measurement straight onto the shared `item.width`/`item.height` fields — convenient since `resolveNaturalSize()` (this plugin) and `SlideManager`'s aspect-ratio placeholder both already read those fields first, but wrong, since that measurement came from the *tile's* thumbnail image, not the full photo. A thumbnail genuinely smaller than the lightbox in both orientations always satisfies `fitScaleFor`'s `Math.min(1, ...)` cap on its own, in both the 0° and 90° terms alike, so the ratio between them — the whole fit-scale — collapsed to exactly `1` for every such item; an item whose `thumb` happened to equal its `src` was unaffected only because the "wrong" measurement and the real one were then simply the same numbers. Fixed in Layout itself (§5) by keeping its auto-measurement Layout-private (a `WeakMap`) instead of mutating the shared item; `item.width`/`item.height` now only ever reflect what the host explicitly supplied. Covered by a cross-plugin regression test (`tests/unit/plugins/layout-automeasure.test.ts`, Layout + RotateFlip together) proving RotateFlip's fit-scale reads the real slide image's own dimensions, never the layout tile's.

  A short-lived, ultimately-unused side effect of chasing the first (wrong) theory: `slideItemLoad` re-applying `apply(false)` for the still-active index, to survive a same-index re-render. Investigating further found no reachable path that actually re-renders the current index's media without either going through `afterOpen`/`afterSlide` (which already `reset()` the rotation state, by design) or leaving `SlideManager`'s per-index cache untouched entirely (`updateSlides()` swapping in new item data for the same, currently-open index does not currently trigger a re-decode at all — a separate, real gap, but not one this bug touched) — so the listener never had an effect on any actual user-observable behavior and was removed rather than kept as untested dead code.

**A sixth real bug, reported from real usage: rotate, then navigate to the next slide via the right nav arrow — the rotated photo visibly bled into the new slide instead of the new slide replacing it cleanly.** The exact same bug class the Zoom plugin already had (§4.6's own real-usage bug, same root cause, same fix): `reset()` only ran on `afterOpen`/`afterSlide`, never `beforeSlide` — with `preload > 0` (the default), `SlideManager.render()` reuses a still-cached slide's node via a plain reparent (`moveIn()`, no state-clearing of its own) into whichever new pool slot its offset needs, and there is no code path *after* that reparent that can still find *that specific node* to reset it. A rotated slide that outlives its own visit (still cached, later reused for a different item) carried its stale rotation into wherever it got repositioned, bleeding unclipped into the neighboring slot. Fixed the same way Zoom already was: an added `beforeSlide` handler, also calling `reset()`, run while `getActiveMedia()` still resolves to the about-to-move slide — before `SlideManager.render()` (called synchronously, between `beforeSlide` and `afterSlide`) ever reparents it. `afterSlide`'s own `reset()` is unaffected — it still separately covers whichever slide *becomes* active, which may carry its own stale rotation from an earlier, unrelated visit. Covered by a unit test (`tests/unit/plugins/rotateFlip.test.ts`, mirroring the Zoom plugin's own equivalent regression test) proving a rotated node's transform clears synchronously inside `next()`, before any `SlideManager` reparenting has a chance to run.

  **A "seventh real bug" that, after an extended investigation, turned out not to be a RotateFlip bug — or even a Shoji bug — at all: recorded here anyway, at length, because every wrong turn along the way is a real trap for the next person chasing a similar-looking mobile viewport-widening report.** Reported from real usage: rotating/flipping a photo on `docs/examples/view-controls.html`, viewed on a narrow mobile viewport, grew the page's own layout viewport wider than the physical screen, pushing right-anchored UI (the next-slide arrow, toolbar buttons) off-screen — reproduced directly, `window.innerWidth` measurably growing after the click. The eventual, real cause: that page's own debug status line (`docs/docs.css`'s `.status-line`, shared with `.event-log` on several other demo pages) prints `JSON.stringify()` of whatever event payload it's showing — including RotateFlip's own `rotateFlipChange` event — as plain text, with no `overflow-wrap`. `JSON.stringify`'s default output has no internal whitespace, so the whole payload is one unbreakable "word"; on a narrow viewport it overflows `.status-line`'s box, widening the *page's* own scrollable content, and a mobile browser correctly widens its layout viewport to match content that's genuinely wider than the device — not a heuristic or a bug in the browser at all. Confirmed directly: `document.documentElement.scrollWidth` grew to exactly match `window.innerWidth`'s reported widening, and the bug reproduced identically with RotateFlip's own click handler completely disabled (a no-op), which should have been impossible if the cause were anywhere in this plugin's own transform/DOM logic. Fixed with one CSS rule, `overflow-wrap: break-word`, on both `.status-line` and `.event-log` in `docs/docs.css` — no `src/` change at all, since there was nothing wrong in the library to fix.

  **Every wrong turn taken before that, in the order tried, since each looked like strong evidence at the time:**
  1. **`contain`/`overflow` on three different elements in the chain** (`.shoji-outer`, `.shoji-slides`, and `.shoji-slide-media` itself) — no effect, for the unsurprising reason that nothing was actually overflowing `.shoji-slide-media`'s own ancestors in the first place.
  2. **Capping `fitScaleFor`'s growth at `1` below a narrow-viewport breakpoint** — did stop the *reported symptom* (by coincidence: it happened to also suppress the specific rotation angle exercised while testing), but broke genuine grow-to-fit-new-orientation behavior and was reverted as its own regression, without ever being the real fix.
  3. **A full rewrite of `apply()`/`transformFor()` to grow via real `width`/`height` instead of `transform: scale()`**, on the theory that paint-only overflow (not genuine layout overflow) was tripping some mobile heuristic — built, and looked promising in an isolated test, but a real-browser repro against the actual plugin showed the same widening regardless. Reverted.
  4. **A `pluginToolbar()` change in `Gallery.ts` adding `event.stopPropagation()`, in various forms, to every toolbar button's click** — the closest wrong turn, and the most dangerous: a *capture-phase* version of this reliably stopped the widening in testing, but the fix and the test were both broken the same way — capture-phase `stopPropagation()` on a target also prevents that same target's own bubble-phase listeners from firing (confirmed with an isolated, Shoji-free repro), silently disabling every plugin's own click handling. The "fix" only appeared to work because nothing was happening anymore. A bubble-phase version preserved functionality but, once actually verified against real transform output rather than just `window.innerWidth`, did not stop the widening either. Fully reverted; `pluginToolbar()` has no changes from this investigation.
  The pattern that finally cracked it: bisecting `RotateFlip.update()` piece by piece (state normalization, `apply()`, the two `aria-pressed` writes, `ctx.emit(...)`) found that skipping *only* `ctx.emit('rotateFlipChange', ...)` — otherwise leaving the real transform and DOM writes untouched — made it safe. Since `EventBus.emit()` itself does nothing but call registered listeners, that pointed straight at whatever *was* listening — the demo page's own `gallery.on('rotateFlipChange', ...)` handler, and from there, straight to `.status-line`'s missing `overflow-wrap`.

**An eighth bug, reported from real usage: rotating/flipping, then navigating, visibly snapped back to unrotated before the slide transition played, instead of the un-rotate/un-flip happening as part of it.** `beforeSlide`'s own reset (sixth bug, above) runs before `SlideTransition` ever clones the outgoing slide into its leave-ghost, so the clone was already back at neutral — nothing left to animate away. Fixed at the core level via `Gallery.registerSlideLeaveDecorator()`, shared with Zoom's own identical bug — see §2.5 for the full mechanism and reasoning.

### 4.6 Zoom (`src/plugins/zoom`)

`new Shoji(el, { plugins: [Shoji.Zoom] })` — no options object needed (`maxScale` default 4, `doubleTapScale` default 2, `buttonStep` default 1.5, all overridable via `zoom: {...}`). Pinch, double-tap/double-click, ctrl+wheel, and three toolbar buttons (`'right'` slot: zoom in, zoom out, actual size) all drive a single `scale`/pan state on the active slide, with pan (drag while zoomed) to move around once zoomed in. All three toolbar buttons are hidden (not just disabled) whenever the active slide is a video (`item.video`) — see the eleventh bug below.

**Consumes core's own gesture relay (§2.4), doesn't reimplement it.** Pinch/double-tap/wheel+ctrl were scaffolded in core specifically for this plugin — `pinchStart`/`pinchMove`/`pinchEnd`/`doubleTap`/`wheelZoom` bus events with no built-in effect until now. Pan (a single-pointer drag once already zoomed) is the one gesture core's relay *doesn't* cover, and needed a real, new coordination mechanism to add cleanly:

- **`Gallery.registerZoomGate(isZoomed: () => boolean): () => void`** — a new public core method, single mutable slot (not an `on()`-style multi-subscriber event, since only one zoom controller is ever meaningful per gallery). While the registered predicate returns `true`, `GestureController`'s `onDragMove`/`onDragEnd` become a no-op entirely — core's drag-to-navigate and drag-to-close are *fully suspended* for the gesture's duration, not just redirected, so a pan drag can never also change slides or close the lightbox. This plugin registers `() => scale > 1.001` (a small epsilon, avoiding float residue pinning the gate open forever) on `init()` and unregisters it on cleanup.
- **Pan itself uses its own minimal raw `PointerEvent` listeners** (attached to `ctx.ui.outer()`), not a second `GestureEngine` instance — `GestureEngine`'s axis-locked model (pick horizontal *or* vertical per gesture, the right shape for "navigate vs. close") is the *wrong* shape for a 2D pan that needs both axes at once. The listener self-gates on `scale > 1.001` too, so it's a true no-op (no `preventDefault`, no state) while unzoomed, leaving core's own drag handling completely undisturbed in the common case.

**Applies its transform to the active slide's `<img>` itself, never `.shoji-slide-media`** — the rotateFlip plugin (§4.5) already owns that container's `transform`, and both writing to the same property would clobber each other. Nesting instead of sharing means a rotated *and* zoomed photo behaves correctly for free: the outer rotate (on the container) carries the inner pan/scale (on the image) along with it as a rigid unit, which is also the visually correct behavior — if you're zoomed into a detail and then rotate, that same framing should rotate with the photo, not reset.

**Zoom-toward-a-point and pan-boundary math is pure and unit-tested in isolation** (`src/plugins/zoom/zoomMath.ts`, `tests/unit/plugins/zoomMath.test.ts`), same "extract the fiddly geometry, test it against hand-verified numbers" approach the zoom *transition*'s `computeTransform` (§2.3b) already uses. `transform-origin: 0 0` on the image (never the CSS default `center`) is what makes the pan-offset math tractable — scaling never moves the image's own natural top-left on screen, only the tracked `tx`/`ty` pan offset does, so "keep this viewport point visually fixed while scale changes" reduces to one closed-form formula (`zoomTowardPoint`) instead of needing to re-derive `transform-origin`'s own effect on top of it. Panning is clamped (`clampPan`) so the scaled image's edges never retreat inside the container, revealing empty space beyond the photo — except when the scaled image is still smaller than the container on an axis, where no pan range can avoid a gap on *both* sides at once, so it's centered instead of clamped to an inverted range.

**"Actual size"** computes `img.naturalWidth / <the image's own unscaled rendered width>` and zooms to exactly that scale, deliberately bypassing `maxScale` (an explicit, deliberate action, not continuous gesture zoom that the cap exists to keep sane) — a second click (or any click while already zoomed) resets to neutral, matching double-tap's toggle behavior.

**`w`/`s` keyboard shortcuts zoom in/out by the same fixed `buttonStep`** as the toolbar buttons — `zoomInStep()`/`zoomOutStep()` are shared functions, called by both the button click handlers and `ctx.ui.registerShortcut()` (§3), so there's exactly one implementation of "one step," not two that could drift apart. Both letter cases are registered explicitly (`'w'` and `'W'`, `'s'` and `'S'`) since `registerShortcut` matches `event.key` verbatim with no case-insensitive matching of its own — core's own `a`/`d` navigation aliases (§2.6) do the same for the same reason. Exists only when this plugin is loaded: core has no concept of "zoom" at all, so a host without this plugin simply never has these keys registered, and `w`/`s` fall through untouched, same as any other unregistered key.

**Discrete jumps animate; continuous gestures don't.** Toolbar buttons, double-click/double-tap, and "Actual size" (including its reset back to neutral) each jump `scale`/pan straight from one value to another — `withTransition()` wraps just those calls in `transition: transform var(--shoji-duration) var(--shoji-easing)` (the same custom properties every other transition in the codebase already uses, so `prefers-reduced-motion` zeroing `--shoji-duration` covers this for free) before writing the new transform, then clears the inline `transition` once it ends (`waitForTransitionEnd`, reused from `zoomTransition.ts`) so it doesn't linger onto a later, possibly-continuous action. Pinch, pan-drag, and ctrl+wheel deliberately do **not** get this — they already track the pointer/fingers/wheel-ticks 1:1, frame by frame; a transition there would make the image visibly lag behind the input instead of following it, and a fast wheel/trackpad-pinch stream would stack up a transition per tick rather than reading as smooth. `afterOpen`/`afterSlide`/`beforeClose`'s resets stay unanimated too — `beforeClose`'s in particular must stay synchronous, since `close()` measures the image's rect immediately afterward for the zoom-out-to-thumbnail transition (the sixth bug, below); an animated reset there would reintroduce it, since the transform only interpolates visually, it doesn't delay when `getBoundingClientRect()` sees the final value.

**Testing pan for real surfaced two pre-existing, general core bugs, not introduced by this plugin** — see §2.4's third and fourth bugs: `GestureEngine` capturing the pointer on every `pointerdown` (not just once a real drag locked in) silently retargeted every click inside the dialog to `.shoji-dialog`, breaking click-outside-to-close's ability to tell "clicked the photo" from "clicked the background" (a single click on the image closed the lightbox); and the active slide's `<img>` being natively draggable let a real drag gesture lose the race to the browser's own "drag this image out" recognition, which cancels the pointer sequence outright (a drag appeared to move once, then stop dead). Both affected ordinary navigate/close drags too, with or without this plugin enabled — confirmed via a fresh, zoom-free page.

**Deferring capture to lock-time wasn't sufficient on its own for pan specifically** — a fifth core bug, found immediately after: a pan drag *while zoomed* still locks direction inside `GestureEngine` (it has no concept of zoom; only `GestureController`'s *effect* is gated via `registerZoomGate`), so it still captured the pointer, and the release still retargeted its `click` to the dialog exactly as before — releasing the mouse after panning closed the lightbox. `GestureEngineCallbacks` gained a `shouldCapture?(): boolean` hook, consulted right before capture (not just before applying the drag effect); `GestureController` wires it to `() => !host.isZoomed()`. The drag still locks and reports normally either way — only the capture (and its click-retargeting side effect) is skipped.

**A sixth bug, same investigation**: closing while zoomed animated the zoom-out-to-thumbnail transition (§2.3b) from the image's *current* zoomed/panned rect, not its natural one — `close()` measures `getActiveMedia()`'s rect synchronously, and this plugin only reset on `afterOpen`/`afterSlide`, neither of which fires before that measurement. The photo would visibly "close" into a seemingly random spot instead of shrinking into the thumbnail. Fixed by also resetting on `beforeClose` (fires synchronously, first thing inside `close()`, before the measurement) — the image is back at its natural scale/position by the time `zoomOut()` ever looks at it.

**A seventh bug, found via e2e flakiness, not the pan investigation**: `ensureNatural()`'s first measurement of a slide (caching `natural`/`container` boxes, reused for every later zoom action on that slide) is only trustworthy once the lightbox's own open transition (`zoomIn`, §2.3b) has actually settled — `zoomIn` applies its FLIP transform directly to `.shoji-slide-media`, the exact element measured as `container`. A zoom action firing within `--shoji-duration` of opening (a fast click, or simply any interaction the moment the dialog becomes visible — `zoomIn` is fire-and-forget by design, exposing no completion signal) captured a wildly wrong, mid-animation rect that then permanently poisoned that slide's zoom math; "Actual size" was hit hardest since it's the one entry point computing an *absolute* target scale from that box rather than a relative multiplier, so a bogus `container.width` reliably produced a target ≤ 1, silently clamped to a no-op. Fixed with a `whenSettled()` guard (`src/plugins/zoom/index.ts`) wrapping every entry point that measures: if the active media's inline `style.transition` is still set (the one signal available — only `zoomIn`/`zoomOut` ever set it on that element, clearing it once their own transition ends), the action is deferred via `zoomTransition.ts`'s already-exported `waitForTransitionEnd` instead of running immediately against a moving target. Runs synchronously in the overwhelming common case (any interaction more than ~300ms after open, which is nearly all real usage).

**An eighth bug, found immediately after adding the transition above**: the animated `reset()` (toolbar zoom-out reaching neutral, double-tap-to-reset, "Actual size" toggling off) cleared `transformOrigin` from `'0 0'` back to the browser default (`center`) in the same synchronous tick it started the transition. `transform-origin` isn't itself an animated property — changing it mid-flight instantly moves the anchor the *current* (still-scaled) transform renders around, which visibly snapped the image to a new position before it ever started easing down, reading as a jump-then-settle instead of one smooth ease. `zoomTo()`'s `apply()` never had this problem — it re-sets `transformOrigin` to the same `'0 0'` value on every call, so it's constant for the whole animation. Fixed by giving `withTransition()` an optional `afterEnd` callback that only runs once `waitForTransitionEnd` reports the transition genuinely finished; `reset()`'s animated path defers clearing `transformOrigin` to that callback instead of doing it upfront alongside the transform.

**A ninth bug, reported from real usage**: zooming in via "Actual size," then clicking next, could show the new slide with a strip of the *old* photo visibly bled in along one edge. `reset()` only ran on `afterSlide`, which fires *after* `SlideManager.render()` (§2.3) has already reassigned pool slots for the new `activeIndex` — a still-cached slide (within the `preload` window) is reused via `moveIn()`, a plain reparent with no state-clearing of its own, into whichever slot its new offset now needs. By the time `afterSlide`'s `reset()` ran, `getActiveMedia()` resolved to the *new* slide's fresh, never-zoomed image — the actual zoomed image, now sitting in a different, unclipped pool slot (only `.shoji-slides` itself clips overflow; individual slots don't), was never found, so its `transform` was never cleared, and it visibly extended past its slot's own bounds into the new slide's space. Only reproduces with `preload > 0` — at `preload: 0` there's a single pool slot, so every navigation fully re-decodes rather than reusing a cached node, which is why the plugin's own existing `afterSlide` regression test never caught it. Fixed by also resetting on `beforeSlide` (un-animated, same reasoning as the sixth bug's `beforeClose` fix — synchronous, before the reassignment happens, while `getActiveMedia()` still resolves to the about-to-move image), leaving `afterSlide`'s existing reset (now effectively a no-op immediately after) in place for `markEnabled()`.

**A tenth bug, reported from real usage: evenly-spaced horizontal lines visible across a zoomed photo, at certain zoom levels, on real GPU hardware** (not reproducible in headless/software rendering, so unverifiable directly in this codebase's own test suite — also independently reported as present in lightGalleryJS, i.e. a genuine browser/GPU rendering quirk, not specific to this implementation). The regular spacing matches Chromium's own GPU raster-tile boundaries — a known issue where scaling large content via a 2D `scale()` CSS transform can show seams between tiles. `apply()` now uses `translate3d`/`scale3d` instead of the 2D `translate`/`scale` (functionally identical on-screen result — `scale3d(s, s, 1)` and `scale(s)` produce the same transform, just via a different GPU compositing path), the commonly effective mitigation for this exact class of bug. A related, milder version of the same symptom showed as seam lines through the *toolbar's* own semi-transparent, `border-radius` buttons — a sibling of the zoomed image, not a descendant — from the same frequent-repaint activity; `.shoji-toolbar` (`shoji.css`) now sets `will-change: transform` to keep it on its own stable compositing layer, decoupled from the image's repaints. Neither fix is a guaranteed 100% elimination — this class of bug is GPU/driver-dependent — but both are the standard, low-risk mitigations for it.

**A real, separate gap found and fixed while building this**: `GalleryItem.srcset`/`sizes` were declared on the type from the start but never actually applied to the rendered `<img>` anywhere — `SlideManager`'s `renderImage` only ever set `src`. Now wired through (`img.srcset`/`img.sizes` set when present), plus `data-shoji-srcset`/`data-shoji-sizes` added to selector-mode scanning (on the wrapping element, not the inner thumbnail `<img>`, since `src` there is the full-resolution image, a different scope than the thumb). This plugin's own "respects srcset" spec point would otherwise have been meaningless — nothing to respect if the base image never used it. Beyond that base wiring, this plugin does not implement a further "force an even-larger candidate once zoomed past what `sizes` already selected" step (e.g. rewriting `sizes` reactively as scale changes) — deferred, not proven necessary yet; a host wanting guaranteed-sharp high-zoom images should supply `maxScale`-appropriate resolution in `srcset` from the start.

**Emits `zoomChange`** (`{index, scale}`) on every scale change, gesture or button-driven — same "no persistence of its own, resets per slide, a host wanting to keep it stores the payload themselves" pattern as `rotateFlipChange` (§4.5).

**An eleventh bug, found auditing the toolbar for other mouse/UX drift, not reported directly**: all three zoom buttons were always visible, including on a video slide — but every one of them is a silent no-op there. `getImg()` returns `img.parentElement`'s (i.e. the active slide media's) first child cast to `HTMLImageElement`, `null` if it isn't one — a video slide's first child is a `<video>` or a provider embed `<div>`, never an `<img>`, so `apply()`/`ensureNatural()` bail out immediately on every entry point (buttons, `w`/`s`, double-tap, pinch, wheel) without any visible feedback that anything was even attempted. Clicking "zoom in" on a video did precisely nothing, with no indication why. Fixed by hiding (`button.hidden`, real CSS removal — not just visually disabled) all three toolbar buttons whenever `gallery.items[gallery.currentIndex]?.video` is set, updated on `afterOpen`/`afterSlide` (the same two lifecycle points `markEnabled()` already runs at, immediately above). Deliberately scoped to the toolbar buttons only — the `w`/`s` shortcuts and pinch/double-tap/wheel gesture relays are left as harmless no-ops on video, same as before, since they have no persistent on-screen affordance to mislead anyone; only a visible-but-dead button is the actual problem this fixes. Covered by unit tests (`tests/unit/plugins/zoom.test.ts`) confirming all three buttons are hidden opening directly on a video slide, hidden navigating onto one, shown again navigating off of one, and never hidden in a photo-only gallery.

**A twelfth bug, found auditing the codebase for the same latent-bug shape as drag-to-close's own long fix history**: pan's raw pointer listeners (above) never called `setPointerCapture`, unlike `GestureEngine`'s own drag handling. A fast pan whose pointer exits `outer`'s bounds mid-drag stopped receiving `pointermove`/`pointerup` entirely (no capture means only elements actually under the cursor get events) — `panPointerId` stayed non-null, and the gesture just went dead until the next `pointerdown`. Naively capturing on `outer` itself (mirroring `GestureEngine` exactly) would have reintroduced the third bug above under a different name — `outer` doesn't match `isBackdropClick`'s exclusion selector, so a captured pan's release-click, retargeted to `outer`, would misread as a backdrop click and close the lightbox on every real pan. Fixed by capturing on the active slide's `<img>` itself instead: `img` already matches `isBackdropClick`'s exclusion selector (Gallery.ts), so the retargeted click lands somewhere already excluded — no separate `suppressRetargetedClick`-style mechanism needed, unlike `GestureEngine`'s own fix for the same underlying class of problem.

**A thirteenth bug, reported from real usage: while zoomed in, clicking the plain black backdrop between the image and a nav arrow no longer closed the lightbox, unlike the same click when unzoomed.** The twelfth bug's own fix captures pan's pointer on `<img>` specifically — correct once a pan is actually happening, but `onPointerDown` (the pan listener, attached to `outer` so a fast pan is still tracked once the pointer leaves its bounds) engaged and captured on every qualifying pointerdown *anywhere in the lightbox* while zoomed, with no check that the pointerdown itself actually started on the image — `isRealControl`'s exclusion list (buttons/inputs/links/caption/etc.) has no "or the backdrop" term, since the backdrop was never meant to be excluded from *panning*, only from being *captured onto the wrong element*. A click on the plain backdrop while zoomed still matched none of those exclusions, so it still captured the pointer onto `img` regardless — retargeting that click's own `composedPath()` to include the image, which is exactly what `isBackdropClick` (Gallery.ts) then reads as "not a backdrop click," silently defeating close-on-backdrop-click specifically while zoomed. Fixed by also checking that the pointerdown's `composedPath()` actually includes the image before engaging pan at all (`event.composedPath().includes(img)`) — a real pan gesture always starts there anyway, since there's nothing else zoomed-in to grab onto; a backdrop click now falls through untouched, exactly as it already does unzoomed. Covered by unit tests (`tests/unit/plugins/zoom.test.ts`) confirming pan still engages/captures correctly for a pointerdown that starts on the image, and does not for one that doesn't.

**A fourteenth bug, reported from real usage: rotate once, zoom in, then drag — the drag direction was wrong, and rotated with the photo (dragging up moved the image sideways instead of up, and which way flipped with each additional rotation).** `onPointerMove`'s raw `event.clientX/Y` delta (screen space) was applied directly as `pan.tx`/`ty` — the `<img>`'s own *local* space, nested inside `.shoji-slide-media`, which RotateFlip may have rotated. A parent rotation doesn't rotate the coordinate space a screen-space delta is expressed in; applying it unconverted meant "drag down" only ever meant "increase local ty," which only reads as "moves down on screen" when the parent has no rotation. Fixed with `screenDeltaToLocal(dx, dy, m)` (`zoomMath.ts`) — the standard 2x2 matrix inverse (`det = ad-bc`; `M⁻¹ = 1/det · [[d, -c], [-b, a]]`), applied to the raw screen delta using the parent's *live* transform matrix (`getComputedStyle(media).transform`, parsed by `parseLinearTransform` — a small hand-rolled `matrix(a, b, c, d, ...)` regex parser, not the `DOMMatrix` constructor, since jsdom doesn't implement it and every unit test in `tests/unit/` runs there) — converting the delta into the local space the parent transform maps *from*, so the image tracks the pointer 1:1 on screen regardless of whatever rotation (or flip — a flip is just another linear transform this same matrix-inverse handles for free, no special-casing needed) is currently applied. `clampPan` needed the same correction for its own boundary check, for the same reason (see the fifteenth bug, next, for why that fix wasn't actually complete on its own). Covered by a unit test (`tests/unit/plugins/zoomMath.test.ts`) and an e2e regression test (`tests/e2e/plugins/zoom.spec.ts`) asserting a real rotated-then-dragged photo moves along the correct real screen axis in an actual browser.

**A fifteenth bug, found immediately after, same investigation: double-clicking to zoom toward the pointer, once rotated, zoomed toward the wrong point — sometimes badly (occasionally toward an edge of the image rather than anywhere near the actual click).** The fourteenth bug's own fix (a matrix parameter threaded into `zoomTowardPoint`/`clampPan`) turned out to be necessary but not sufficient: both functions still used `natural.left`/`top` (from `getBoundingClientRect()` on the rotated element) as if it were the screen position of the image's own local origin `(0, 0)` — true only with no rotation. Under rotation, a *different* corner of the image lands at the bounding box's own top-left; verified by hand against real browser numbers (a 90°-rotated image's bounding-box top-left corresponds to the image's original *bottom*-left, not its top-left), and confirmed live: the function was computing exactly what its formula specified, faithfully — the formula itself, not the wiring, was wrong.

The one point immune to this ambiguity is the bounding box's own *center* — rotating a rectangle around its own center (the default `transform-origin`, and where flexbox already centers the image within its wrapper) never moves that center, on screen or off. Fixed by re-deriving both functions around that pivot: `localOriginScreen()` (`zoomMath.ts`) computes the image's true local-origin screen position as `pivot + (parent-transform applied to (originOffset + pan))`, where `originOffset` is the image's own true, *unrotated* local size (`img.offsetWidth`/`offsetHeight` — CSS `transform` is paint-only and never affects layout size, unlike `getBoundingClientRect()`, which reports the rotated bounding box) as an offset from local origin to center. `zoomTowardPoint` now anchors against this corrected origin instead of `natural.left/top` directly; `clampPan` similarly now computes the content's actual screen-space bounding box via all four (scaled, panned, rotated) corners rather than assuming a single edge scales along a fixed axis — necessary because a 90°-multiple rotation swaps which local axis (width vs. height) lands on which screen axis, so the scaled content's screen-space width/height aren't simply `natural.width/height × scale` once rotated. Both parameters default to identity/`natural`-derived values, so an unrotated caller (or `offsetWidth`/`offsetHeight` reading `0`, as jsdom always does — it never computes real layout) gets byte-identical output to the pre-fix formula. Verified against real e2e-captured numbers (a 90°-rotated, 600×800-reporting image, double-clicked at a specific off-center point) by hand before implementing, then confirmed via a real-browser e2e regression test (`tests/e2e/plugins/zoom.spec.ts`) asserting the same fraction of the image lands under the same screen point after zooming, rotated.

**A sixteenth bug, found auditing `reset()` against this section's own documented contract ("emits `zoomChange` on every scale change, gesture or button-driven") while building Autoplay's `pauseOnZoom` (§4.1): resetting from an engaged scale back to `1` silently skipped emitting it, at every call site — `beforeSlide`, `afterSlide`, `beforeClose`, `afterOpen`, and `zoomOutStep`/`toggleZoom` reaching neutral all route through `reset()`, not `zoomTo()`.** A host listening for `zoomChange` to reflect "is this slide currently zoomed" would never learn it stopped being true unless something else zoomed in again first — exactly the gap that made Autoplay's own first `pauseOnZoom` attempt appear to work but not actually resume/re-engage correctly around a zoom-out. Fixed by emitting only when there's an actual change (`scale !== 1` before the reset) — the overwhelming majority of these calls fire while already at scale `1`, and emitting on every no-op reset would be noisy against the "on every *change*" contract, not a fix for it.

## 5. Layout plugin (grid · tight masonry · justified)

Turns the inline gallery container into a fully managed, config-driven layout. No extra markup, no external masonry library — the host provides a container and items (DOM or dynamic mode), and picks a layout in options.

**Implemented (v1 scope)** — `type: 'grid' | 'masonry' | 'justified'`, both `orientation`s (masonry), `gutter` (number or `{x, y}`), `columns`/`columnWidth`/`min`/`maxColumnWidth`/`fill` (masonry vertical), `rowHeight`/`min`/`maxRowHeight`/`lastRow` (justified; horizontal masonry also takes `rowHeight`, as its fixed row height), `breakpoints`, `groupBy`-derived headings/`renderHeading` (including the structured `{title, subtitle}` form)/`headingOverflow`/`stickyHeadings` (grid only for the sticky part), incremental append (masonry `orientation:'vertical'` only — see §5.4 for why justified and masonry `orientation:'horizontal'` don't get it), resize-driven relayout, simple animate. `justified` + `groupBy` is real Google Photos behavior, not an approximation — sections share a row instead of each forcing its own; see §5.2. See §5.4 for exactly what shipped and what's deliberately deferred (explicit heading items in the item stream, configurable heading level, `stickyHeadings` for masonry/justified, `groupBy` + horizontal orientation, merge-across-load-boundaries for grouped appends, jump-free prepend).

### 5.1 Config

```ts
layout: {
  type: 'grid' | 'masonry' | 'justified',    // default 'justified' — the Google Photos-style row-packed layout; grid and masonry are both opt-in

  gutter: number | { x: number, y: number }, // px; default 8; 0 = tight/gap-free

  // grid
  aspectRatio: number,                       // grid only; default 1 (square); every cell's uniform shape, cropped via object-fit: cover — NOT each photo's own ratio (see §5.2 for why)

  // masonry
  orientation: 'vertical' | 'horizontal',    // default 'vertical'
  //   vertical (default): N columns, each a fixed target width, tiles pack
  //     downward into a column, container height is computed, page scrolls
  //     vertically — the classic Pinterest layout. Ragged *bottom* edge.
  //   horizontal: rows of a fixed, exact height (rowHeight below — never
  //     scaled/clamped, unlike justified's target), tiles pack left-to-
  //     right at their own true aspect ratio; the moment the next tile
  //     would push a row past the container's width, that tile starts a
  //     new row instead of stretching the finished one to close the gap —
  //     ragged *right* edge, the masonry-family transpose of vertical's
  //     ragged bottom. Container width is measured (never set); container
  //     height is computed from however many rows resulted — same input/
  //     output shape as vertical, just axes swapped, and it never needs
  //     horizontal scroll: an unbounded number of rows just makes the page
  //     taller, exactly like an unbounded column height does in vertical
  //     mode. `fill`/`minRowHeight`/`maxRowHeight` don't apply here — see
  //     their own entries below.
  columns: number | 'auto',                  // vertical only; default 'auto', derives from columnWidth
  columnWidth?: number,                      // vertical only; target px used when columns:'auto'; default 240
  minColumnWidth?: number,                   // vertical only; clamps the effective column width; default 160
  maxColumnWidth?: number,                   // vertical only; clamps the effective column width; default 480
  fill: 'shortest' | 'ordered',              // vertical only; default 'shortest' — tightest packing (shortest column) vs. round-robin reading order

  // justified (rowHeight below also doubles as horizontal masonry's fixed row height)
  rowHeight?: number,                        // target row height; default 220; justified rows scale to fit this target, horizontal-masonry rows are pinned to it exactly
  minRowHeight?: number,                     // justified only; clamps the effective row height; default 120
  maxRowHeight?: number,                     // justified only; clamps the effective row height; default 360
  lastRow?: 'justify' | 'left' | 'hide',      // default 'justify' (Flickr-style: the last row scales like any other)

  // shared
  breakpoints?: Record<number, Partial<LayoutOptions>>, // maxWidth → overrides
  animate?: boolean,                         // FLIP transitions on relayout (default true)
  autoMeasure?: boolean,                     // self-correct missing width/height by measuring the tile's own <img> once it loads (default true) — see below

  // headings / sections
  groupBy?: (item: GalleryItem) => string,   // derive section key (e.g. month from item.data)
  renderHeading?: (key: string, items: GalleryItem[]) => string | HTMLElement | { title: string, subtitle?: string },
  headingOverflow?: 'show' | 'fit' | 'wrap', // justified + the {title,subtitle} form only; default 'show' (always full content); 'fit' drops the subtitle, then breaks the offending section onto a fresh row (never wraps the label text); 'wrap' keeps 'show''s row-packing but lets the label itself wrap onto extra lines, capped at maxRowHeight (line-clamped), if it doesn't fit its available width
  stickyHeadings?: boolean,                  // grid only (v1) — headings stick while their section scrolls (default false)
}
```

v1 only implements the `groupBy`-derived path: the plugin inserts a heading whenever the group key changes across consecutive items, rendered through `renderHeading` (default: an `<h2>` with the key as plain text). The general spec's other source — **explicit heading items** in the item stream (`{ type: 'heading', title: 'July 2026' }`, useful when the server already emits grouped pages) — isn't built; `GalleryItem` has no `heading` variant yet. See §5.4.

“Tight masonry” is simply `{ type: 'masonry', gutter: 0 }` (or a small gutter) — tiles pack flush with no ragged gaps because the clamped dimension (width in vertical orientation, height in horizontal) is uniform per bucket and the free dimension comes from true aspect ratios.

The `min`/`maxColumnWidth` and `min`/`maxRowHeight` clamps exist because `'auto'` bucket counts are derived by dividing the container's cross-axis size by the target and flooring — at odd container sizes that division can land the *effective* per-bucket size well away from the target (e.g. a 601px container at `columnWidth: 200` floors to 3 columns of ~200px, but 999px floors to 4 columns of ~250px, and a narrow enough container can floor to 1 column of the full width). The clamps cap how far that effective size can drift before the bucket count itself adjusts, so columns never go stringy-narrow and rows never go stretched-tall (or vice versa) at awkward widths.

### 5.2 Algorithm & rendering

- **Deterministic, measure-free layout**: positions are computed purely from item aspect ratios (`width`/`height` in the item model; required for layout, warn + fallback to on-load measure if absent). This means the full layout — including the computed container dimension — is known before a single image loads: no reflow jumps, correct scrollbar from frame one.
- **Masonry, `orientation:'vertical'`**: bucket count from config or `containerWidth / target` (clamped per `min`/`maxColumnWidth`); each tile placed into the shortest column (`fill:'shortest'`, tightest packing) or round-robin in DOM order (`fill:'ordered'`, preserves reading order at slight tightness cost). Tiles pack downward, container gets an explicit computed height.
- **Masonry, `orientation:'horizontal'`**: structurally closer to justified's row-accumulation loop than to vertical masonry's bucket-packing — greedily accumulates tiles left-to-right at `rowHeight` (fixed, never clamped/solved) until the next tile would push the row's cumulative width past the measured `containerWidth`, then finalizes that row exactly as-is (no stretch) and starts a new one with the tile that didn't fit; a single tile wider than `containerWidth` on its own still gets its own row rather than being shrunk. `fill` doesn't apply — placement is sequential, not bucket-assignment. Container width is only ever measured; container height is the sum of however many rows resulted. Because a row isn't "committed" until a tile arrives that overflows it, an appended tile can extend what was the previous render's trailing row — same reason justified always fully relays out on any items change instead of doing an incremental append (§5.4).
- Both masonry orientations position tiles via `transform: translate()` (compositor-only moves).
- **Justified**: greedy row filler scaling each row to exactly the container width at ~`rowHeight` (Flickr-style); also “tight” by construction. `lastRow: 'left'` — a fixed-height, non-stretched, ragged-right placement for just the trailing partial row — is the single-row special case that horizontal masonry generalizes to *every* row.
  - **A real bug, reported and reproduced directly (a 360px-wide viewport, a square tile sandwiched between two wider neighbors): `resolveScaledRow`'s own shed-the-trailing-tile logic could isolate a tile into a row shorter than the container, a visible gap on the right edge.** Two tiles combined can naturally fall below `minRowHeight` — `resolveScaledRow` sheds the trailing one back onto the next row so raising the pair up to `minRowHeight` doesn't overflow the container (this file's own documented tradeoff, above). But shedding down to a *single* remaining tile only helps if that tile's own natural fill-height doesn't *itself* need `maxRowHeight` to clamp it — otherwise the shed trades an under-`minRowHeight` pair (merely a bit short) for a lone tile whose clamped row instead falls short of the *right edge* (the other documented tradeoff, same paragraph) — strictly worse, for nothing. Fixed by checking, before each shed, whether the tile that would be left alone needs `maxRowHeight` clamping; if so, keep the wider grouping and let `minRowHeight` yield for it too, extending the same yield the single-super-wide-tile case already established rather than shedding into a worse outcome. Verified both with a direct unit reproduction (`layout-justified.test.ts`) and against the real reported scenario end to end in a browser.
- **Grid**: uniform CSS grid — every cell shares the same `aspect-ratio` (`aspectRatio` option, default 1/square), cropped via `object-fit: cover`; cheapest option, no JS positioning. Deliberately uniform, not each photo's own ratio: plain CSS grid sizes a *row's* height to its tallest cell, so per-item ratios would leave a visible blank gap under every shorter tile sharing a row with a taller one — masonry/justified are the two types that preserve true per-photo aspect ratios, via their own JS packing that doesn't have this row-height problem.
- **Responsive**: single `ResizeObserver` on the container; relayout is O(n) arithmetic + n transform writes, batched in one rAF. `breakpoints` override any option below a given width. FLIP-animated relayout when `animate` (disabled under `prefers-reduced-motion`).
- **Headings/sections**: `grid` and `masonry` treat a heading as a full-cross-axis **blocking** element that terminates the current section and resets all bucket sizes — the next tile row starts flush beneath it, so each section is its own tight block (native CSS grid gives `grid`'s `grid-column: 1 / -1` heading a fresh row for free, no JS positioning at all; `masonry` segments its tile list at each heading and runs a fresh column-packing pass per segment, stacking segments by accumulating a running Y offset from each heading's measured height). `justified` is the deliberate exception — this is the real Google Photos behavior, not a simplified stand-in for it: **sections never force a row break.** Row *composition* ignores section boundaries entirely (one continuous row-fill pass over every tile, regardless of section), so a section too small to reach a full row's target width on its own — a single lone photo, say — shares that row with whatever comes right after it instead of getting stretched into its own near-empty row. A heading only marks *where* a new section starts: a compact, inline label (not full-width) positioned at the x-coordinate of the tile that starts its section, in a slim label-band above whichever row that tile landed on — more than one label shares the same band when more than one section starts within the same row. Headings are **not slides** in any type: skipped by lightbox indexing, keyboard nav, and the counter, by construction — a heading is never wrapped in a `Tile`, so `gallery.open(index)` only ever sees real item indices. `stickyHeadings` pins the active section's heading via `position: sticky` — implemented for `type: 'grid'` only (headings sit in normal document flow there); masonry/justified headings are absolutely positioned by JS like their tiles, where `position: sticky` doesn't apply meaningfully, so it's warned-and-ignored for those two types. Semantics: headings render as real `<h2>` (not yet level-configurable) so the grid remains a navigable document outline for screen readers. `groupBy` + horizontal orientation isn't supported (warns, ignored) — that pairing is expected to be rare in practice; the primary horizontal use case is a single ungrouped horizontally-scrolling strip.
- **`renderHeading`'s structured form and `headingOverflow`**: `renderHeading` can return `{ title, subtitle? }` instead of a string/`HTMLElement` — the plugin builds a real title (muted label, e.g. "Taken") + bolded subtitle (e.g. a date) itself, which is what lets it safely apply automatic overflow handling (a raw returned `HTMLElement` is opaque — never touched beyond adding the standard class/positioning). `headingOverflow` (`'show'` default, `'fit'`/`'wrap'` opt-in; `type: 'justified'` + the structured form only, ignored otherwise) controls what happens when a compact label doesn't fit its available width — the gap until the next section's label sharing its row, or the container edge: `'show'` always renders both parts in full on one line, however wide, even if it visually runs past the next label or the container edge — simple and predictable, nothing silently dropped. `'fit'` **never wraps label text** — it drops the subtitle first if title+subtitle together don't fit; if the title *alone* still doesn't fit next to whatever's sharing its row, that section is pushed onto a fresh row instead, giving its label a full row's worth of room. This means row *composition itself* responds to label width under `'fit'`, not just label content — see §5.4 for how. The one unavoidable exception is a single label wider than the entire container even alone on its own row: nothing left to break onto, so it's ellipsis-truncated (still one line, never wrapped, never overflowing). `'wrap'` is the in-between, real Google Photos behavior for its date headers: same continuous row-packing as `'show'` (row composition never reacts to label width, no section is ever pushed to a fresh row), but a label that doesn't fit wraps its own text onto extra lines instead of running past its gap — capped at `maxRowHeight` (or its default, 360) via a `-webkit-line-clamp` sized from the container's own computed line-height, ellipsis-truncating only the last visible line if it's still too tall, never growing the row unbounded.
  - **Typography is themeable via custom properties** (CLAUDE.md — no hardcoded sizes/colors), all with fallbacks matching the current default look exactly, so setting none of them changes nothing: `--shoji-layout-heading-font-family` (on `.shoji-layout-heading`, default `inherit`, covers the plain-string form too), `--shoji-layout-heading-title-font-size`/`-font-weight`/`-color` (default `0.875rem`/`400`/`#767676`), `--shoji-layout-heading-subtitle-font-size`/`-font-weight`/`-color` (default `0.875rem`/`700`/`inherit`) — title and subtitle deliberately share the same explicit `0.875rem` default (matching `.shoji-counter`'s own size elsewhere in core) rather than sizing off the plain-string heading's own browser-default `<h2>` size, which decouples the structured form from that (still-unreset, for the plain-string case) larger default entirely. `.shoji-layout-heading` itself deliberately keeps browser-default `<h2>` sizing rather than gaining its own font-size property — overriding that to `inherit` would shrink it from the UA stylesheet's larger default, a regression for hosts not using the structured form; targeting `.shoji-layout-heading` directly with normal host CSS already fully controls it.
- **Incremental updates**: append is O(new items) — bucket sizes/row state are kept, nothing before it moves. When `groupBy` is set, v1 does **not** implement the "merge across load boundaries" optimization described above — any items change while grouped (append included) does a full re-render (re-segment + re-render every heading and tile), the same simplification justified's non-grouped path already makes for the identical reason (a row/section can be completed or reshaped by later items, so there's no stable untouched prefix to preserve without a second continuation scheme) — see §5.4. **Prepend relayouts everything after it** (masonry bucket sizes shift); the plugin computes the container-dimension delta and hands it to the scroll plugin's anchoring step in the same frame, so bidirectional infinite scroll stays jump-free (§7, not yet built).
- Layout emits `layout:update { positions, height }` (or `{ positions, width }` in horizontal orientation); lazy-loading uses the computed rects (not element visibility) so `loading="lazy"`/IO thresholds work with absolutely positioned tiles.

### 5.3 Interop

- **Scroll plugin**: windowing collapses far-off tiles to positioned placeholders using the already-known rects — masonry math is unaffected by eviction.
- **Select plugin**: marquee hit-testing uses layout rects (fast AABB checks), not `getBoundingClientRect` per tile. In selection mode, headings grow a section checkbox — clicking it selects/deselects the whole section (the Google-Photos "select this day" gesture); indeterminate state when partially selected.
- **Lightbox**: clicking a tile opens the lightbox at that index as usual; zoom-from-tile transitions use the layout rect as the animation origin.

### 5.4 v1 implementation notes (`src/plugins/layout`)

`new Shoji(el, { plugins: [Shoji.Layout] })` — bare defaults give `type: 'justified'`; `layout: { type: 'grid', ... }` or `layout: { type: 'masonry', ... }` opts into the other two. Three files carry the real weight: `masonry.ts` and `justified.ts` are the pure positioning algorithms (no DOM, unit-tested directly — `layout-masonry.test.ts`, `layout-justified.test.ts`), `index.ts` is the DOM/rendering layer wired to both.

- **The plugin fully owns the container, in either mode.** Unlike autoplay (which only touches the lightbox), layout takes over `gallery.element` itself — it clears whatever was there (host markup in selector mode included) and renders its own `<a class="shoji-layout-tile"><img></a>` tiles from `gallery.items`, in both selector *and* dynamic mode. This is what "no extra markup" (§5's opening line) means in practice: the host doesn't hand-author thumbnails at all once layout is enabled, unlike every other dynamic-mode demo page. Each tile that has `item.id` gets `data-shoji-id` for free, so the zoom transition (§2.3b) finds a real origin without any extra host wiring.
- **This is why plugins now init at construction, not lazily on first `open()`** (§3.1) — layout has to render the inline grid before any `open()` call is even possible, since its tiles are what the viewer clicks to open in the first place. Autoplay's toolbar button still works exactly the same under this timing; it just happens sooner.
- **Grid** is plain CSS (`display:grid; grid-template-columns: repeat(auto-fill, minmax(...))`) with a *uniform* `aspect-ratio` set on every tile from the `aspectRatio` option (default 1) — not `item.width`/`height`. This was a real bug in an earlier version: per-item ratios sized each tile correctly on its own, but native CSS grid still sizes a *row's* height to its single tallest cell, so any row with a taller photo left every shorter tile in that row sitting in a large blank gap underneath (grid has no masonry-style packing to avoid this). No JS positioning math either way, no `ResizeObserver` (native grid already reflows itself); grid no longer needs `item.width`/`height` at all, so the missing-dimensions warning below is masonry/justified-only now.
- **Masonry** positions each tile via `transform: translate(x, y)` + explicit `width`/`height` (GPU-composited moves only, per CLAUDE.md); the container gets an explicit computed `height`. A `ResizeObserver` (batched through one `requestAnimationFrame`) triggers a full relayout of every tile on resize — only masonry needs this, so it's only attached in that mode. `containerWidth <= 0` (not yet painted — `display:none`, still detached) is a no-op, not a crash; the observer's own initial callback, which fires once real dimensions are available, self-corrects.
- **A real, reported slowdown: opening/closing the lightbox felt sluggish specifically on pages using masonry or justified.** Neither mode's own layout pass is what's slow — the actual cost lands on the *lightbox's* own `getBoundingClientRect()`/`offsetHeight` reads (`zoomTransition.ts`'s FLIP technique, §2.3b), which force the browser to flush any pending layout on the *entire page* first, not just inside the lightbox — including this container's own subtree, potentially hundreds of tiles, even though nothing in it actually changed. `layout.css` gives `.shoji-layout--masonry`/`--justified` `contain: layout style`, telling the browser this subtree's internal layout can neither affect nor be affected by anything outside it, letting that page-wide flush skip descending into it. Originally left off `--grid` on the assumption that its intrinsic (content-driven auto-height) sizing couldn't safely decouple the same way — reported again later, specifically for grid, and re-investigated: that assumption doesn't hold. Layout containment isolates a subtree from *outside* influence; it doesn't stop the box from sizing itself off its own children's normal layout, intrinsic or not. Verified directly — a 300-tile grid's rendered height and every tile's position are identical with and without `contain: layout style` applied. Now applies to all three types.
- **Missing `item.width`/`height`, with `autoMeasure` (default `true`)**: the *first* layout pass always uses the 4:3 placeholder immediately — never blocked on an image load, same layout-jump-avoidance rule as before (CLAUDE.md § "Things to be careful about") — but the tile's own `<img>` (already fetching for display; nothing is fetched twice) is then watched for its `load` event, and once it fires, its `naturalWidth`/`naturalHeight` are cached in a Layout-private `measuredAspect` `WeakMap<GalleryItem, {width,height}>`, keyed by the item — and a relayout is scheduled. Multiple corrections landing close together (several cached images resolving in the same tick is the common case) are coalesced into one relayout via `requestAnimationFrame`, never one per image; `groupingEnabled` galleries get a real `fullRender()` there instead of a plain reposition pass, since `groupBy` was evaluated once already during the *first* render using whatever width was known then — if that's exactly the field a correction just filled in, the section boundaries themselves were wrong and only a fresh `computeSections()` call fixes them. A video item with neither `thumb` nor `poster` (nothing to measure — its tile `<img>` points at the unplayable video file itself) still gets the permanent-fallback warning, same as `autoMeasure: false` restores the pre-`autoMeasure` behavior entirely (single `console.warn`, permanent 4:3, no measurement attempted) for hosts who want zero chance of any extra relayout under any circumstance. This is the same "measure the loaded image, then reflow" a host would otherwise hand-roll themselves before ever constructing the gallery (`new Image(); img.onload = () => ...`) — `autoMeasure` just does it automatically, scoped to only the images actually missing dimensions, coalesced rather than one-relayout-per-image. Real dimensions supplied up front (`item.width`/`height`, or `data-shoji-width`/`height` in selector mode) remain the zero-jank, zero-extra-work path; `autoMeasure` is the fallback for when they weren't, not a replacement for supplying them when you already can.
  - **A real bug, reported from real usage, fixed by keeping this cache Layout-private instead of writing straight onto `item.width`/`item.height` (an earlier version did exactly that, reasoning it was harmless since `aspectOf()` already reads those fields first anyway).** `item.width`/`item.height` aren't Layout-private state — RotateFlip's own fit-scale (§4.5's "fifth real bug") and `SlideManager`'s aspect-ratio open placeholder both read the exact same fields, under the contract that they mean the full photo's *true* pixel dimensions. But `autoMeasureTiles()`'s measurement comes from the *tile's* own `<img>` — `item.thumb` first, then `poster`, then `src` — a thumbnail's aspect ratio is a fine stand-in for the full photo's *for layout purposes*, close enough almost always, but not actually the same file whenever `item.thumb` is a genuinely separate, smaller image. Writing that measurement onto the shared field silently fed a thumbnail's dimensions to every other consumer expecting the real photo's, with no visible symptom in Layout itself (a tile's own aspect ratio came out right either way) — only surfacing once something else (RotateFlip) tried to use the "corrected" `item.width`/`item.height` for its own, different purpose. Fixed by moving the measurement into `measuredAspect`, read only by this plugin's own `aspectOf()`; `item.width`/`item.height` now only ever reflect what the host explicitly supplied, never a Layout-internal guess.
- **Incremental append is real, not aspirational — for masonry `orientation:'vertical'`.** `isPureAppend()` checks whether an `itemsUpdated` list is the previous list plus new entries at the end (same key prefix, `item.id ?? item.src`). If so, only the new items get new tile DOM — existing tiles are untouched (verified in tests via reference equality) — and masonry packing continues from the saved `columnHeights` rather than recomputing from index 0. Any other change (reorder, removal, prepend) triggers a full rebuild instead. This is the piece that directly answers "does it work with infinite scroll as things are appended" — yes, verified both at the algorithm level (`layout-masonry.test.ts`) and through a real `updateSlides()` call in a real browser (`demo/pages/layout.html`'s "Load more" button, which visually leaves every earlier tile exactly where it was).
- **Justified, and masonry `orientation:'horizontal'`, do not get that same optimization — always a full relayout, deliberately.** A justified row (or a horizontal-masonry row, which packs the same way — see §5.2) isn't "locked in" the way a vertical masonry column height is: the row left incomplete/trailing on the previous render can be *extended or completed* by newly-appended tiles, so there's no stable prefix of untouched positions to preserve without a second, more involved continuation scheme (tracking a pending row's accumulated width/aspect-sum across calls). `applyJustified()` and `applyMasonryHorizontal()` both always reposition every tile, on append included, and neither takes an `appendOnly` parameter at all. This is a real, honest scope cut (not a bug) — if it becomes a measured perf problem for very large galleries in either mode, the pending-row continuation is the thing to build then, not speculatively now.
- **`rowHeight`** (default 220) is a target, not a guarantee — a finalized row's actual height is whatever makes it exactly fill the container width given its tiles' combined aspect ratio, which is usually close to but not exactly `rowHeight`. **`lastRow`** (default `'justify'`) controls the trailing row when there aren't enough tiles left to naturally reach the container width on their own: `'justify'` stretches it like any other row (Flickr's actual behavior, including the edge case where a single leftover tile gets stretched to fill the entire row width alone — this is correct, not a bug, and is exactly what real Flickr/justified galleries do too); `'left'` keeps it at natural `rowHeight`-scaled size with empty space on the right; `'hide'` sets `tile.hidden = true` on that row's tiles until a future relayout (more appended items, usually) completes the row and un-hides them.
- **`groupBy`/headings** (`groupBy`, `renderHeading`, `stickyHeadings`, `headingOverflow`) are implemented for all three `type`s except the `orientation: 'horizontal'` masonry pairing (warns, ignored). Grid gets headings essentially for free — a `grid-column: 1 / -1` element inserted in DOM order, native CSS grid handles the rest, no JS positioning. **Masonry** segments `tiles[]` at each heading's `tileStart` (`headingSegments()`) and lays out each segment independently with the pure `layoutMasonry` function, stacking segments by accumulating a running `y` offset (heading height + gutter, then that segment's `containerHeight` + gutter) — a hard, full-width block break per section.
- **Justified is architecturally different, on purpose** (`applyJustifiedGrouped`, `src/plugins/layout/index.ts`) — real Google Photos behavior, where small sections share a row instead of each forcing its own. `justified.ts`'s pure algorithm still doesn't know `groupBy` exists at all (its only groupBy-related addition is a `rows: Array<{start, end, y, height}>` field on its result, so a caller can find which finalized row a given tile index landed on without re-deriving it from float `y` equality) — all section-awareness lives in `applyJustifiedGrouped`, which calls `layoutJustified` **per segment** rather than once for everything:
  - `headingOverflow: 'show'` (default) and `'wrap'`: exactly one segment, covering every tile — matches the simple "always continuous packing" behavior; `computeSegments()` only ever splits into multiple segments for `'fit'`. `'show'` leaves `layout.css`'s own `white-space: nowrap; width: auto` to render full labels with zero JS work; `'wrap'` runs `applyWrapDecisions()` per segment instead (a content-level decision within the already-fixed layout, not a row-composition one) — for each structured heading, it sets `white-space: normal` and a `max-width` from the same "gap to the next label sharing its row, or the container edge" measurement `'fit'` uses, then derives a max line count from `maxRowHeight / computedLineHeight` and applies it via `-webkit-line-clamp` (`display: -webkit-box; -webkit-box-orient: vertical; overflow: hidden`) — broadly supported cross-browser despite the vendor prefix, no unprefixed equivalent yet with comparable support. A label short enough to fit within that many lines is unaffected (the clamp has nothing to do); a longer one ellipsis-truncates its last visible line rather than growing the row past `maxRowHeight`.
  - `headingOverflow: 'fit'`: `computeSegments()` finds the largest run of sections that can share rows *without any label needing to break* — it grows a trial segment one section at a time, running a real (if throwaway) `layoutJustified` call on each trial and checking every label within it fits its row's available width (against widths batch-measured once up front, both with and without the subtitle); the moment a trial fails, the segment is finalized just before that section, which starts the *next* segment fresh — giving it the full container width back, since a new `layoutJustified` call always starts its first row at x=0. This is why row composition itself ends up responding to label width under `'fit'`, not just label content: a section that doesn't fit is never wrapped or dropped, its whole row-slot moves. Each final segment gets its own real `applyContentDecisions()` pass (drop the subtitle if needed, using the segment's *actual* computed positions, not the trial's) before its heading heights are read and everything is positioned — segments stack vertically (`cumulativeExtra` carries a running total of every prior segment's full `containerHeight`, not just label-band heights, since each segment restarts `layoutJustified`'s own local Y at 0). The one case `computeSegments` can't resolve by breaking further — a single label wider than the entire container even alone on its own row — is left as a 1-section segment with a known violation; `applyContentDecisions` catches it and falls back to `overflow: hidden; text-overflow: ellipsis` (still one line, capped at that row's available width, never wrapped, never overflowing).
  - Whichever mode, once segments are known: for each segment's rows, headings whose `tileStart` falls in `[row.start, row.end)` (segment-local, offset back to global tile indices for lookups into `tiles`/`headings`) get positioned at their own tile's x-coordinate in a shared "label-band" whose height is the *tallest* label in that row; a `lastRow: 'hide'` trailing range within a segment (tiles with no row at all) gets explicitly hidden, tiles and any orphaned heading both, since the per-row loop never touches them.
  - All heading-height reads happen in one batch *before* any tile transform is written, specifically to avoid interleaving DOM reads with writes in the same pass — doing that once measurably delayed the very first paint under `animate: true` (a `getBoundingClientRect()` read forces a layout flush, which hands freshly-inserted, not-yet-painted tiles a real "before" style to transition away from that they otherwise wouldn't have, i.e. an accidental transition-from-`translate(0,0)` on first render instead of an instant, un-animated placement). Same rule for masonry's own segments.
  - Any items change while grouped always does a full `fullRender()` (new heading + tile DOM from scratch), same append-simplification justified's non-grouped path already makes (§5.2) — there's no attempt to preserve untouched DOM across a grouped relayout the way masonry's ungrouped incremental append does.
- **Deferred, not built**: explicit heading items in the item stream (`{ type: 'heading', ... }` — `GalleryItem` has no such variant), configurable heading level (`<h2>` is hardcoded), `stickyHeadings` for masonry/justified (their headings are JS-absolutely-positioned, incompatible with `position: sticky` as currently implemented), `groupBy` + `orientation: 'horizontal'`, per-width heading-height caching (re-measured every relayout instead), "merge across load boundaries" for grouped incremental updates (justified's continuous packing makes this more involved than the masonry case it was originally scoped against — a newly appended page can reshuffle row composition arbitrarily far back, not just extend a trailing row), jump-free prepend coordination (§5.2 — the scroll-anchoring handoff this needed was scoped against the §7 infinite-scroll plugin, which is now not implementing at all, not just not-yet-built; prepending today triggers a full relayout that can shift scroll position, with no plugin on the other end that would ever call prepend in the first place under current scope). Each is a real chunk of additional work, not a small follow-up — add them when an actual use case needs them, same reasoning as autoplay's deferred `shuffle`/hover-pause (§4.1).
- Demo: `demo/pages/layout.html` — the only demo page that pre-measures image dimensions client-side (via a one-time `Image()` load) before constructing items; this is a demo-only concession (no backend to supply real dimensions from), not something the library itself ever does — see the comment at the top of `demo/pages/layout.ts`. A Grid/Masonry/Justified button row switches `layout.type` live via `gallery.reinit({...})` (§2.7) — the same instance rebuilt in place, not `destroy()` + a fresh one — and re-attaches its own `afterOpen` status listener afterward, since `reinit()` clears the event bus same as `destroy()` does. A "Group by date" checkbox assigns each demo photo a synthetic date section and toggles `groupBy`/`renderHeading` (the structured `{title, subtitle}` form, with `headingOverflow: 'fit'`) on, live, the same way — resizing the window narrow enough demonstrates the subtitle-drop-then-wrap behavior in `justified` mode.

## 8. Editor plugin (edit mode) — not implementing

Spec kept below for reference; descoped, not built.

Non-destructive image editing in the lightbox, modeled on the proven Shashin editor, generalized and de-jQuery-ified.

### 8.1 Edit state

```ts
interface EditState {
  rotation: 0|90|180|270;
  flipH: boolean; flipV: boolean;
  brightness: number;  // 1.0 = neutral, multiplicative
  contrast: number;    // ((c−0.5)·contrast)+0.5
  saturation: number;  // luma-preserving w/ red-dampening & perceptual boost >1.0
  sharpness: number;   // unsharp-mask weight, >1.0 engages
}
```

- Opens seeded from `item.edits` (host-persisted values); missing keys default to neutral.
- **Three baselines** drive button state: *neutral* (all defaults), *original* (persisted values at open), *current*. 
  - **Reset** → back to *original* (enabled iff current ≠ original).
  - **Restore** → back to *neutral* (enabled iff current ≠ neutral) and signals host to drop stored edits/derived thumbs.
  - **Save** → enabled iff current ≠ original; hands `EditState` to the host hook.
- **Flip/rotation normalization**: flipH+flipV ≡ rotate 180°. Canonicalize before comparisons and before save, per this table (rotation always normalized to `((r % 360)+360)%360`):

| flipH | flipV | rot | → canonical |
|---|---|---|---|
| ✓ | ✓ | 0   | no flips, rot 180 |
| ✓ | ✓ | 90  | no flips, rot 270 |
| ✓ | ✓ | 180 | no flips, rot 0 |
| ✓ | ✓ | 270 | no flips, rot 90 |

Comparisons for button enablement use canonical forms on both sides (this is what makes Reset/Save enablement correct when the user "undoes" via an equivalent transform).

### 8.2 Rendering pipeline

1. **Primary: WebGL** single-pass fragment shader — brightness → contrast → saturation (RGB-domain, `dot(c, [0.299,0.587,0.114])` gray; red-dampening `1 − 0.10·(s−1)` and `+0.006·(s−1)` perceptual boost when s > 1) → optional 5-tap unsharp mask (`weight = (sharpness−1)/4.5`, resolution-scaled offset `clamp(√(w·h)/512, 0.5, 2.0)`), with color adjust applied per-tap *before* combining. Order must byte-match the server implementation so preview == saved result.
2. Rotation/flip applied as CSS transform on the preview element (not in-shader), with even/odd-rotation aware max-width/height fitting to the viewport.
3. **Resource management**: per-canvas WeakMap cache of `{gl, program, buffers, texture, uniform locations, lastParams}`; `texSubImage2D` on same-size re-uploads; uniforms set only on change; `UNPACK_FLIP_Y_WEBGL`; output via `canvas.toBlob` → object URL (revoke previous URL each pass); low-quality JPEG for interactive preview, full quality only on demand.
4. **Fallback chain**: WebGL unavailable/failed → CSS-filter live preview (brightness/contrast/saturate map directly; sharpness disabled with UI hint) → optional host hook `editor.renderPreview(item, state) → dataURL/blob` for server-side rendering (Shashin's fallback path).

### 8.3 UI & shortcuts

- Overlay module over the lightbox (lightbox toolbar hidden while open); toolbar: rotate L/R, flip H/V, four sliders (brightness/contrast/saturation/sharpness) with center-tick snap and icon-click-to-reset per slider, Restore, Reset, Save, Close; disabled-state styling via custom properties.
- Busy model: spinner + all controls disabled during a render pass; close blocked while busy.
- Shortcuts: `←/→` rotate, `↑/↓` flip H/V, `R` reset, `O` restore, `S` save, `Escape` close. Click outside tool areas closes (when idle).
- "Current settings" info toast shows persisted values with non-neutral ones highlighted.
- Scroll locking of the page while editor is open; full state cleanup + GL/object-URL disposal on close.

### 8.4 Host integration

```ts
editor: {
  source: (item) => string | Blob,          // full-res original fetcher (cache-busted)
  save:   (item, state, blob?) => Promise,  // persist EditState (+ optional rendered blob)
  restore:(item) => Promise,                // drop stored edits/derived assets
  renderPreview?: (item, state) => Promise<Blob>,  // server fallback
}
```

After save/restore, editor emits `edit:save`/`edit:restore` and calls `updateSlides` so the lightbox and thumbnails refresh.

## 9. Styling & theming

- Single `shoji.css` + optional per-plugin css; all colors, spacing, z-layers, easing, and typography (`--shoji-font-family`) via `--shoji-*` custom properties; dark default theme; light theme = one class (`.shoji-light`). `.shoji-outer` always mounts directly on `document.body` (§2.6), never nested inside the host's gallery container — so `.shoji-light`/any `--shoji-*` override must be applied to `<body>`/`<html>`/another real ancestor of the mount point, not the gallery container itself, or it silently has no effect (custom properties only inherit down real DOM ancestry). There is currently no general per-instance theming option (e.g. a `className` on `GalleryOptions` applied to `.shoji-outer`) — a `<body>`-level theme applies to every gallery instance on the page. `backdropOpacity` (`GalleryOptions`, below) is the one narrow exception: a 0-1 real-alpha value, clamped, set as an inline `--shoji-backdrop-opacity` custom property directly on that instance's own `.shoji-outer` in `Gallery.ts`'s `ensureLightbox()` — `.shoji-backdrop { opacity: var(--shoji-backdrop-opacity) }`. `--shoji-color-backdrop` (`shoji.css`) is a fully opaque hue by default (`#000000` dark / `#ffffff` light) specifically so this opacity value alone is the real, honest alpha — `1` is genuinely fully opaque, not capped at some baked-in color alpha (see the real bug under `backdropOpacity` below). Left unset (the default), the CSS custom property (default `1`, both themes) goes untouched, so a host theming it directly in CSS — including per-instance via a real ancestor selector, same caveat as every other `--shoji-*` override above — is unaffected either way.
- `--shoji-font-family` defaults to the system-font stack (`-apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, ...`) — zero webfont download, renders instantly, looks native per-platform. Applied once on `.shoji-dialog` and inherited by everything inside it (counter, caption, future toolbar button labels), so it's independent of whatever font the host page happens to have set, while still overridable via the custom property.
- Icon set: inline SVG sprites (stroke = `currentColor`), overridable per-button.
- No !important; layered z-index scale documented (`backdrop:0 · slides:10 · overlay:20 · toolbar:30 · toast:40`) — that scale only orders those layers *against each other*, inside the stacking context `.shoji-outer` itself establishes. `.shoji-outer`'s own page-level z-index is the separate `--shoji-z-base` (default `9000`) — real host pages routinely put sticky navbars/sidebars/toast containers at 1000-9999, so the lightbox needs real headroom above the page, not the small internal scale. Override `--shoji-z-base` if your own stack goes higher still.

## 10. Packaging, performance budgets & testing

**Distribution** — the primary artifact is a single-file pair:

- `dist/shoji.js` + `dist/shoji.css` (and minified variants): core + **all** official plugins in one JS and one CSS file. Plugins ship registered-but-inert — nothing activates until enabled via options, so the all-in-one bundle adds zero runtime cost for unused features. UMD wrapper (global `Shoji`) so the same file works via `<script>` tag or `import`. Sourcemaps included.
- Secondary: per-plugin ESM entries (`shoji/core`, `shoji/plugins/zoom`, …) + `.d.ts` for bundler users who want tree-shaking. Same source, same version, built in the same `npm run build`.
- CSS mirrors this: one `shoji.css` concatenating core + all plugin styles (safe because everything is namespaced `.shoji-*` / `--shoji-*` and plugin styles are inert without their plugin's DOM), with per-plugin css files as the secondary output.
